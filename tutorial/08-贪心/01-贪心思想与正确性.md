# 01 贪心思想与正确性

> **一句话理解**：贪心就是"每一步都选当前最优，并且**永不反悔**"——它的正确性不靠代码，靠**交换论证**：证明"当前最优的那个选择，一定存在于某个全局最优解里"。
> 两个前提缺一不可：**贪心选择性质**（当前最优可选）和**最优子结构**（选完之后的子问题还是同型问题）。

---

## 一、什么时候能用贪心（判定标准）

### 1.1 两个前提

| 前提 | 含义 | 不满足会怎样 |
| --- | --- | --- |
| **贪心选择性质** | 存在一个全局最优解，**包含**当前这一步的贪心选择 | 贪心选的东西根本不在任何最优解里 → 必然错 |
| **最优子结构** | 做完这一步选择后，剩下的问题**还是同一种问题**，且可以独立求解 | 剩下的问题变了型，贪心的局部结论不能复用 |

补充一条**极易被忽略**的第三条件：

| 隐形前提 | 含义 |
| --- | --- |
| **无后效性 / 选择不可撤销但可控** | 当前选择对未来的影响是**单调、可预测**的（比如"右端点越小，留给后面的空间越大"）。如果当前选择会让未来"时好时坏"，就必须 DP |

### 1.2 什么时候**不能**用：三句话否证法

```
① 反例否证：只要能构造一组输入，贪心解 ≠ 最优解，就立刻放弃贪心。
   （找零钱 {1,3,4} 凑 6 就是最经典的一组）

② 后效性否证：问"这一步选 A 之后，下一步是不是可能因为选过 A 而失去更优的选择？"
   如果答案是"是"，就必须 DP。

③ 规模否证：题目问"有多少种方案"，而不是"最少/最多"。
   贪心只能给出"一个"答案，不能给出"所有方案" → 必须 DP / 回溯。
```

### 1.3 一句话判断表

| 题目问法 | 贪心？ | 原因 |
| --- | --- | --- |
| 最少需要几个区间 / 几次操作 | ✅ 通常可贪心 | "最少"= 每步都选最划算的，可以交换论证 |
| 最多能安排多少个活动 | ✅ | 右端点排序后取最早结束，交换论证成立 |
| 有多少种凑法 / 方案数 | ❌ | 贪心无法枚举所有方案，用 DP |
| 0-1 背包最大价值 | ❌ | 容量约束下"性价比最高"会浪费空间 |
| 括号 / 表达式能否合法 | ✅ 常见 | 用计数器做贪心匹配（如 `<` 就加，不合法就反转） |

## 二、为什么贪心常常需要**先排序**

贪心的核心是"当前最优"。而"当前最优"在无序数据里无法定义——**排序是把"当前最优"变成一个确定位置的手段**。

```
未排序：[3,1,4,1,5]        "当前最优"是谁？说不清。
排序后：[1,1,3,4,5]        最后一个 = 最大；第一个 = 最小。
                          → "拿最大的" = 从右往左，规则确定。
```

**排序关键字 = 贪心选择的表达式。** 所以每道贪心题都该问自己：

```
我到底在比较什么？那个比较的值，就是排序关键字。
```

| 题目 | 比较的是什么（= 排序关键字） | 方向 |
| --- | --- | --- |
| 455 分发饼干 | 饼干大小 / 孩子胃口 | 都升序 |
| 435 无重叠区间 | 区间**右端点** | 升序 |
| 56 合并区间 | 区间**左端点** | 升序 |
| 1029 两地调度 | `costA - costB`（去 A 省下的钱） | 升序 |
| 179 最大数 | `a + b` 与 `b + a` 的字典序 | 自定义 |
| 406 身高重建队列 | 身高**降序**，人数升序 | 自定义 |
| 1005 K 次取反 | 绝对值 | 降序 |

> ⚠️ **关键字选错是全盘皆错**。区间题典型的坑：435（要最多的不重叠区间）必须按**右端点**排序，按左端点排序就错了；而 56（合并）必须按**左端点**排序。**同一个"区间"，因为目标不同，关键字也不同。**

## 三、Java 通用模板：贪心四步骨架

贪心题没有"万能代码"，但有一个**万能流程**。先把它背下来，再填具体题目的细节。

```java
/**
 * 贪心四步骨架（可直接当作所有贪心题的起手式）
 *
 * Step 1  明确"每一步在选什么"（决策点）
 * Step 2  写出"当前最优"的表达式 → 它决定了排序关键字
 * Step 3  排序
 * Step 4  一次扫描，用少量变量维护状态（不回头修改）
 */
public int greedyTemplate(int[][] intervals) {
    // Step 1 & 2：本题每步选"下一个区间"，当前最优 = 右端点最小
    //             → 排序关键字 = 右端点
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));

    // Step 4：状态变量：上一个选中区间的右端点 + 计数器
    int lastEnd = Integer.MIN_VALUE;   // 初值：保证第一个区间一定可选
    int count = 0;

    for (int[] cur : intervals) {
        if (cur[0] >= lastEnd) {       // 与上一个选中的区间不冲突（相切算不冲突）
            count++;                   // 选中它，且永不反悔
            lastEnd = cur[1];
        }
        // 否则跳过它 —— 贪心会自动跳过"右端点太大"的区间
    }
    return count;
}
```

**逐条解释易错点**：

| 细节 | 为什么这样写 | 写错会怎样 |
| --- | --- | --- |
| 排序用 `Integer.compare` 而不是 `a[1] - b[1]` | 减法可能溢出（差超过 `int` 范围） | `Integer.MIN_VALUE` 参与排序时结果错乱 |
| `lastEnd` 初值取 `Integer.MIN_VALUE` | 让第一个区间无需特判就能被选中 | 取 `0` 时，若区间从负数开始会漏掉 |
| 判断用 `>=` 还是 `>` | 435 中"相切"算不重叠，用 `>=`；452 中"相切"算重叠（箭能穿透），用 `>` | 452 用 `>=` 会少用箭 → 答案偏大 |
| 不写"撤销"逻辑 | 贪心的本质就是**不回头**。如果需要回头，说明该用 DP | 写着写着变成 DP，复杂度失控 |

> **模板适用边界**：这个骨架只能处理"选一个子集，使数量最大"的题型。如果需要"覆盖到某个目标"（视频拼接），要把 `lastEnd` 换成"当前覆盖右端 + 最远可达"，见 [02 区间问题](02-区间问题.md)。

## 四、典型例题

### 4.1 1029. 两地调度 —— 完整的交换论证示范

**题意**：`2n` 个人，每人去 A 城花费 `cost[i][0]`，去 B 城花费 `cost[i][1]`。要求**恰好 n 人去 A、n 人去 B**，求最小总花费。

**暴力**：枚举所有"选 n 个人去 A"的组合，`C(2n, n)` → 指数级，不可行。

**贪心思路**：先让所有人去 B，然后"把 n 个人改派到 A"。对第 `i` 个人，改派的代价是

```
d[i] = cost[i][0] - cost[i][1]
```

`d[i]` 越小（越负），说明"他去 A 比去 B 省得越多"。**显然应该优先改派 `d` 最小的 n 个人。**

**交换论证（完整版，面试请背这一段）**：

```
设最优解 OPT 中存在两个人 i、j：
      i 被派去了 B
      j 被派去了 A
   且 d[i] < d[j]（i 比 j 更有理由去 A）

现在交换两人的去向，构造 OPT'：
   OPT  在这两人上的花费 = cost[i][1] + cost[j][0]
   OPT' 在这两人上的花费 = cost[i][0] + cost[j][1]
   两者之差 = (cost[i][0] + cost[j][1]) - (cost[i][1] + cost[j][0])
            = (cost[i][0] - cost[i][1]) - (cost[j][0] - cost[j][1])
            = d[i] - d[j] < 0

说明 OPT' 比"最优解" OPT 还便宜 → 矛盾。
所以最优解里不可能出现"d 小的人去 B、d 大的人去 A"。
即：按 d 升序排序后，前 n 个必然去 A，后 n 个必然去 B。∎
```

```java
public int twoCitySchedCost(int[][] costs) {
    // 关键字 = d = costA - costB，升序；d 最小的 n 个人去 A
    Arrays.sort(costs, (a, b) -> (a[0] - a[1]) - (b[0] - b[1]));

    int n = costs.length / 2;
    int result = 0;
    for (int i = 0; i < n; i++) {
        result += costs[i][0];         // 前 n 个去 A 城
        result += costs[i + n][1];     // 后 n 个去 B 城
    }
    return result;
}
```

> 参考实现：[src/greedy/TwoCitySchedCost.java](../src/greedy/TwoCitySchedCost.java)

**复杂度**：时间 `O(n log n)`（排序主导），空间 `O(1)`（原地排序，不算排序栈空间）。

**为什么贪心省掉了冗余**：暴力需要枚举"哪 n 个人去 A"这个组合空间；交换论证告诉我们"顺序已经完全由 `d` 决定"，于是组合空间坍缩成**一次排序**。

*两地调度是【排序 + 交换论证】，关键突破点是发现排序关键字 `costA - costB`，边界是前 n 个给 A、后 n 个给 B，别写成 `i < n` 与 `i >= n` 错位。*

### 4.2 435. 无重叠区间 —— 从 DP 到贪心的完整推演

**题意**：给定一组区间，移除最少几个区间，使剩下的区间两两不重叠（**相切算不重叠**，即 `[1,2]` 和 `[2,3]` 可以共存）。等价于"最多能留下几个不重叠区间"，答案 = `n - 最多留下数`。

**思路演进**：

```
① 暴力：枚举所有子集，检查两两不重叠 → O(2^n)，不可行

② DP（仓库版本的做法，O(n^2)）：
   按左端点排序
   dp[i] = 以第 i 个区间结尾的最长不重叠链长度
   dp[i] = max(dp[i], dp[j] + 1)   对所有 j < i 且 intervals[j].right <= intervals[i].left
   答案 = n - max(dp)

③ 贪心（O(n log n)）：
   按右端点排序，每次选"右端点最小且不与上一个冲突"的区间
   答案 = n - 选中的个数
```

**贪心为什么对（交换论证）**：

```
设贪心第一个选中区间是 g（右端点最小的那个），
最优解第一个区间是 x。

因为 g.right <= x.right（g 是右端点最小的），
所以 [x.right, +∞) ⊆ [g.right, +∞)：
    在 x 之后还能放的区间，在 g 之后一定也能放。

→ 把最优解里的 x 换成 g，剩下的区间一个都不用删，仍然合法。
→ 存在一个包含 g 的最优解。
→ 对剩下的子问题归纳，贪心每一步都成立。∎
```

注意关键一步：**`g.right <= x.right` 让"剩余可用空间"单调变大**——这就是"无后效性"的具体体现。

```java
public int eraseOverlapIntervals(int[][] intervals) {
    if (intervals.length <= 1) return 0;              // 边界：0 或 1 个区间，删 0 个
    // 关键字 = 右端点，升序；用 Integer.compare 防减法溢出
    Arrays.sort(intervals, (a, b) -> Integer.compare(a[1], b[1]));

    int keep = 1;                                     // 至少能留下排序后的第一个
    int lastEnd = intervals[0][1];
    for (int i = 1; i < intervals.length; i++) {
        if (intervals[i][0] >= lastEnd) {             // 相切算不重叠 → >=
            keep++;
            lastEnd = intervals[i][1];
        }
    }
    return intervals.length - keep;
}
```

> 参考实现（DP 版本，`O(n^2)`）：[src/array/MinInterval.java](../src/array/MinInterval.java)

**关于仓库版本的说明**：

| 项 | 仓库版本 `MinInterval` | 推荐版本 |
| --- | --- | --- |
| 算法 | `O(n^2)` DP，按**左端点**排序 | `O(n log n)` 贪心，按**右端点**排序 |
| 返回 | `n - dp[n-1]` | `n - keep` |
| 备注 | 中间有一行 `System.out.println(Arrays.toString(dp));` 调试输出，**提交时必删** | 无调试输出 |

仓库版本的 `n - dp[n-1]` 恰好正确（因为按左端点排序后，最长链总能"搬"到最后一个区间上结束），但这个性质很隐蔽、很脆弱——**不要依赖它，用贪心版本**。

**复杂度**：时间 `O(n log n)`，空间 `O(1)`。DP 版本是时间 `O(n^2)`、空间 `O(n)`。

*无重叠区间是【区间调度的右端点贪心】，关键突破点是证明"右端点最小者一定在某个最优解里"，边界是"相切不算重叠"要用 `>=`。*

### 4.3 646. 最长数对链 —— 同一模板的另一种问法

**题意**：`pairs[i] = [a, b]`（`a < b`），选最多的数对组成链，要求 `b1 < a2`（**这里是严格小于，相切算冲突**）。这题和 435 是同一个模板，只差一个边界符号。

```java
public int findLongestChain(int[][] pairs) {
    // 关键字仍然是右端点，升序
    Arrays.sort(pairs, (a, b) -> Integer.compare(a[1], b[1]));

    int count = 0;
    int lastEnd = Integer.MIN_VALUE;          // 哨兵：保证第一个数对一定可选
    for (int[] p : pairs) {
        if (p[0] > lastEnd) {                 // 646 要求严格大于 → 相切算冲突
            count++;
            lastEnd = p[1];
        }
    }
    return count;
}
```

> 参考实现（DP 版本，`O(n^2)`）：[src/dp/LongestChain.java](../src/dp/LongestChain.java)

**435 vs 646 对照表（只差一个符号）**：

| 项 | 435 无重叠区间 | 646 最长数对链 |
| --- | --- | --- |
| 目标 | 最少删几个 | 最多选几个 |
| 排序关键字 | 右端点升序 | 右端点升序 |
| 相接判据 | `cur[0] >= lastEnd` | `cur[0] > lastEnd` |
| 返回 | `n - count` | `count` |
| 仓库文件 | [MinInterval.java](../src/array/MinInterval.java)（DP） | [LongestChain.java](../src/dp/LongestChain.java)（DP） |

**复杂度**：时间 `O(n log n)`，空间 `O(1)`。

*最长数对链是【区间调度模板】，关键突破点是识别出它与 435 同构，边界是"相接算冲突"必须用 `>`。*

### 4.4 860. 柠檬水找零 —— 贪心 vs "看起来更聪明"的模拟

**题意**：一杯柠檬水 5 元，顾客只会给 5 / 10 / 20 元，你必须**当场**找零（初始没有零钱），判断能否全部找开。

**贪心规则**：

```
收到 5  ：five++
收到 10 ：必须找一个 5    → five--, ten++
收到 20 ：优先找一个 10 + 一个 5；否则找三个 5
          （因为 5 元更"通用"，能应付 10 元顾客；10 元只对 20 元顾客有用）
```

**为什么优先花 10 元？** 这是本题唯一的"贪心选择"，也是一次典型的交换论证：5 元可以给 10 元顾客找零，也可以给 20 元顾客找零；10 元**只能**给 20 元顾客找零。所以 10 元是"专用资源"，能花就花，把更通用的 5 元留到后面。

```java
public boolean lemonadeChange(int[] bills) {
    int five = 0, ten = 0;
    for (int bill : bills) {
        if (bill == 5) {
            five++;
        } else if (bill == 10) {
            if (five == 0) return false;   // 找不开
            five--;
            ten++;
        } else {                           // bill == 20
            if (ten > 0 && five > 0) {     // 优先 10 + 5
                ten--;
                five--;
            } else if (five >= 3) {        // 否则三个 5
                five -= 3;
            } else {
                return false;
            }
        }
    }
    return true;
}
```

> 参考实现：[src/array/LemonChange.java](../src/array/LemonChange.java)

**仓库版本对比**：

| 方法 | 做法 | 复杂度 | 评价 |
| --- | --- | --- | --- |
| `lemonadeChange` | 用**最大堆**模拟"优先用最大的零钱" | `O(n log n)` | 仓库注释直接写了"**超时**"；逻辑虽然正确，但常数大、代码绕 |
| `lemonadeChange2` | 只数 `five` / `ten` 两个变量 | `O(n)`、`O(1)` | **推荐版本**，与上面的代码同构 |

**这题的启发**：贪心的"数据结构"往往可以退化。用堆是"通用模拟"，用两个计数变量才是"看透了贪心规则"。**能用计数就别用堆。**

*柠檬水找零是【优先花专用资源】，关键突破点是"10 元只服务 20 元顾客，所以优先花掉"，边界是 20 元要靠 `five >= 3` 兜底。*

### 4.5 455. 分发饼干 —— 双指针匹配的贪心

**题意**：`g[i]` 是第 i 个孩子的胃口，`s[j]` 是第 j 块饼干的大小。饼干 `j` 能满足孩子 `i` 当且仅当 `s[j] >= g[i]`，每块饼干只能用一次。求最多满足几个孩子。

**贪心规则**：**用最大的饼干去满足胃口最大的孩子**；满足不了，就放弃这个孩子（他不可能被任何饼干满足了）。

```java
public int findContentChildren(int[] g, int[] s) {
    Arrays.sort(g);                    // 胃口升序
    Arrays.sort(s);                    // 饼干升序
    int child = g.length - 1, cookie = s.length - 1, count = 0;
    while (child >= 0 && cookie >= 0) {
        if (s[cookie] >= g[child]) {   // 最大的饼干能满足最大的胃口
            count++;
            child--;
            cookie--;
        } else {
            child--;                   // 这块饼干满足不了他，且他也无法被更小的饼干满足
        }
    }
    return count;
}
```

> 参考实现：[src/greedy/CookiesAndChildren.java](../src/greedy/CookiesAndChildren.java)

**为什么"从大到小"贪心能行（交换论证）**：设最优解用饼干 `s[cookie]` 满足了某个孩子 `t`（`t <= g[child]`）。因为 `s[cookie] >= g[child] >= t`，把 `s[cookie]` 改去满足 `g[child]`，再把原来满足 `g[child]` 的饼干（如果存在）去满足 `t`，依然合法且满足人数不变。所以"最大的饼干给最大的胃口"不会丢解。

**等价写法（从小到大）**：也可以让小饼干优先满足小胃口，`s[cookie] >= g[child]` 时双双前进，否则只前进饼干指针。**两种写法答案相同**——贪心的方向可以翻转，只要关键字和指针方向自洽。

| 写法 | 指针移动 | 放弃谁 |
| --- | --- | --- |
| 从大到小（仓库 & 推荐） | 都从末尾开始 | 饼干不够时放弃**孩子** |
| 从小到大 | 都从 0 开始 | 饼干不够时放弃**饼干** |

**复杂度**：时间 `O(n log n + m log m)`，空间 `O(1)`（不含排序开销）。

*分发饼干是【排序 + 双指针匹配】，关键突破点是"最大的饼干优先满足最大的胃口"，边界是任一数组为空时返回 0。*

### 4.6 134. 加油站 —— 反证法与归纳法的双重证明

**题意**：`gas[i]` 是第 i 站能加的油，`cost[i]` 是从第 i 站开到第 i+1 站的耗油。求能绕环路一圈的**唯一**起点下标，不存在返回 `-1`。

**暴力（仓库版本）**：枚举每个 `gas[i] >= cost[i]` 的起点，模拟一圈。时间 `O(n^2)`。

**贪心思路（一次扫描）**：

```
观察 1（必要性）：总油量 total = Σ(gas[i] - cost[i]) < 0 时，一定无解。
观察 2（关键）：从 start 出发，若开到 i 时油量 cur < 0，
               那么 [start, i] 中的任何一点都不能作为起点。
               证明：设中途点 k ∈ (start, i]。从 start 到 k-1 时油量 >= 0（否则早已失败），
                     所以从 k 出发时"少攒了这一段非负的油"，到 i 时油量只会更少 → 必然失败。
观察 3：由观察 2，一旦 cur < 0 就把起点重置为 i + 1，且 cur 清零，继续往后扫。
```

```java
public int canCompleteCircuit(int[] gas, int[] cost) {
    int total = 0;      // 全程净油量（用于判定有无解）
    int cur = 0;        // 从当前 start 出发累计的油量
    int start = 0;
    for (int i = 0; i < gas.length; i++) {
        int diff = gas[i] - cost[i];
        total += diff;
        cur += diff;
        if (cur < 0) {          // 从 start 出发开不到 i
            start = i + 1;      // 观察 2：[start, i] 都不可能是起点
            cur = 0;            // 从新起点重新累计
        }
    }
    return total >= 0 ? start : -1;   // 总油量非负 → start 一定是那个唯一解
}
```

> 参考实现（`O(n^2)` 暴力枚举起点）：[src/dp/CompleteCircuit.java](../src/dp/CompleteCircuit.java)

**正确性（归纳法）**：循环不变量——"扫描到下标 `i` 时，`start` 是 `[0, i]` 中唯一可能成为答案的候选取值，且 `cur` 是从 `start` 到 `i` 的净油量"。基例 `i = 0` 显然；归纳步骤用观察 2 排除区间内所有点；扫描结束后由观察 1 判定。

**复杂度**：时间 `O(n)`，空间 `O(1)`。暴力版本是时间 `O(n^2)`、空间 `O(1)`。

*加油站是【一次扫描 + 起点重置】，关键突破点是"某个起点失败则区间内所有点都失败"，边界是总油量为负时返回 `-1`，且 `total >= 0` 时答案必然唯一。*

### 4.7 反例课：找零钱为什么不能贪心

**题意（322 零钱兑换）**：`coins` 是硬币面额，用**最少**的硬币凑出 `amount`。

**贪心（错的）**：每次拿"不超过余额的最大面额"。

```
面额 {1, 3, 4}，amount = 6
贪心：6 - 4 = 2 → 2 - 1 = 1 → 1 - 1 = 0    用了 3 枚 ❌
最优：3 + 3                                  用了 2 枚 ✅
```

**贪心错在哪？** "拿 4" 破坏了 `6 = 3 + 3` 这个组合。这里的后效性是**坏的**：当前最优（面额最大）会让后续可用面额变差。这正是 2.1 节"隐形前提"不满足的样子。

**正确做法：DP（完全背包）**

```java
public int coinChange(int[] coins, int amount) {
    int[] dp = new int[amount + 1];
    Arrays.fill(dp, amount + 1);        // 哨兵：用 amount+1 表示"不可达"
    dp[0] = 0;
    for (int x = 1; x <= amount; x++) {
        for (int coin : coins) {
            if (coin <= x) {
                dp[x] = Math.min(dp[x], dp[x - coin] + 1);
            }
        }
    }
    return dp[amount] > amount ? -1 : dp[amount];
}
```

> 参考实现（518 零钱兑换 II，同为背包类 DP）：[src/dp/ChangeCoins.java](../src/dp/ChangeCoins.java)

**贪心什么时候用在这里是对的？** 当面额满足"规范币制"（canonical coin system）时，比如 `{1, 5, 10, 25}`。但**证明这一点很难**，面试遇到找零钱默认写 DP。

**对比表**：

| 项 | 贪心 | DP |
| --- | --- | --- |
| 面额 `{1,3,4}`、amount=6 | 3 枚（错） | 2 枚（对） |
| 面额 `{1,5,10,25}` | 对（规范币制） | 对 |
| 时间 | `O(amount)` | `O(amount × k)` |
| 能否证伪 | 一组反例就够 | 转移方程天然覆盖所有情况 |

*找零钱是【贪心失效的经典反例】，关键突破点是发现"最大面额会破坏后续组合"，边界是 `dp` 用 `amount + 1` 当哨兵并在最后判 `> amount`。*

## 五、易错点清单

| 易错点 | 后果 | 正确做法 |
| --- | --- | --- |
| 没证明就贪心 | 样例过、隐藏用例挂 | 写出交换论证或归纳法的关键一句 |
| 排序关键字选错（435 按左端点） | 答案偏大或偏小 | 435/646 按**右端点**；56 按**左端点** |
| 边界符号写反（`>` 与 `>=`） | 相差 1 个区间 | 明确"相切算不算重叠"，435 用 `>=`，646 用 `>` |
| `lastEnd` 初值取 `0` | 负数区间被漏掉 | 取 `Integer.MIN_VALUE` 哨兵，或"选中第一个再循环" |
| 比较器用 `a - b` | 差值溢出导致排序错乱 | `Integer.compare(a, b)` 或 `Comparator.comparingInt(...)` |
| 贪心里藏了"撤销" | 复杂度爆炸 / 逻辑混乱 | 需要撤销就改 DP，不要硬凑贪心 |
| 忘记删调试输出 | 提交代码有额外 IO，可能超时 | 提交前全局搜一遍 `System.out.println` |
| 把"方案数"题当贪心做 | 只能得到一个方案 | 问"有多少种"一律 DP / 回溯 |
