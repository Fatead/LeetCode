## 零、Agent 岗位画像与市场现状

### 0.1 三类 Agent 岗位

| 岗位 | 做什么 | 面试重点 |
| --- | --- | --- |
| **Agent 应用开发** | 客服、办公、营销、代码等具体场景 | 场景落地、工具设计、效果与成本 |
| **Agent 平台** | 编排引擎、工具市场、多租户、可观测 | 架构、隔离、可靠性、评测 |
| **Agent Infra** | 运行时、沙箱、长任务、状态持久化 | 分布式、容错、资源调度 |

**判断方法**：JD 里出现"编排/平台/工具市场/多租户"→ 平台岗；出现"客服/知识库/业务流程"→ 应用岗。

### 0.2 市场现状：三个明显变化

| 变化 | 2023-2024 | **2025-2026** |
| --- | --- | --- |
| 技术路线 | 追求"全自主 Agent" | **Workflow + Agent 混合**，该确定的地方用代码 |
| 工程重点 | 能不能跑通 | **可评测、可回滚、成本可控** |
| 协议生态 | 各家自定义 | **MCP 成为工具接入事实标准**，A2A 探索中 |

**面试话术**："我们现在不会追求『全自主』，而是**把不确定性关在盒子里**——流程用状态机固定，只在需要判断的节点调用模型。"

## 一、Agent 到底是什么：定义、边界与能力模型

### 1.1 一个可用的定义 ⭐⭐

> **Agent = 以 LLM 为决策核心，能够自主地调用工具、观察结果、调整策略，并在多步之后完成目标的系统。**

拆成四个关键词：

| 关键词 | 含义 | 没有它会怎样 |
| --- | --- | --- |
| **LLM 决策** | 由模型决定下一步做什么 | 那就是普通工作流 |
| **工具** | 能对外部世界产生影响/查询 | 那只是聊天机器人 |
| **观察反馈** | 用工具结果修正下一步 | 那是"一次性生成" |
| **多步自主** | 步数不预先固定 | 那是固定流程 |

### 1.2 Agent vs Workflow：2025 年最重要的区分 ⭐⭐⭐

| 维度 | Workflow（工作流） | Agent（智能体） |
| --- | --- | --- |
| 控制流 | 代码写死 | 模型决定 |
| 可预测性 | **高** | 低 |
| 成本 | 低且可控 | 高且波动 |
| 调试 | 容易 | 难（轨迹长） |
| 适用 | 步骤明确、规则清晰 | 步骤不确定、需要判断 |
| 例子 | 发票 OCR → 校验 → 入库 | "帮我把这周的报销整理好" |

**工程共识**：

```
能用 workflow 解决的，不要用 agent
必须用 agent 的，也要把"确定性部分"抽出来用代码做
→ 1 个 agent 节点 + 9 个确定性节点，比 10 个 agent 节点可靠得多
```

**面试话术**："我们的原则是**『确定性下沉，不确定性上浮』**——数据校验、权限判断、金额计算全部用代码；只有『用户想干什么』『这段文本是什么意思』才交给模型。"

### 1.3 能力模型：一个 Agent 要具备什么

```
① 理解目标（意图识别、任务分解）
② 感知环境（工具返回值、文档、状态）
③ 决策（选工具、定参数、判断是否继续）
④ 执行（调用工具、处理错误）
⑤ 记忆（记住中间结果和用户偏好）
⑥ 反思（发现错了能改）
⑦ 终止（知道什么时候算完成）
```

**面试追问**："Agent 最难的是哪一环？"
→ **终止判断**。模型很容易"觉得还没完成"而无限循环，或者过早结束。所以要有**明确的完成条件 + 最大步数 + 人工确认**。

### 1.4 什么时候**不该**用 Agent ⭐⭐⭐

| 场景 | 原因 | 替代方案 |
| --- | --- | --- |
| 步骤完全固定 | Agent 只会增加成本和不确定性 | Workflow |
| 要求强一致（转账、扣库存） | 模型不可靠，不能承担事务责任 | 代码 + 事务 |
| 延迟敏感（< 500ms） | 多步调用必然慢 | 规则/小模型 |
| 数据敏感且不能出域 | 工具调用可能泄露 | 私有化 + 白名单 |
| 责任要求可追溯 | 模型决策难以审计 | 规则引擎 + 人工 |

**面试加分**："我会先问『**如果模型这一步判断错了，后果是什么**』。后果不可接受的地方，一律不让模型做决定。"

## 二、Agent 的五大组件

```
        ┌─────────────┐
        │   规划 Plan  │
        └──────┬──────┘
               ↓
┌──────┐  ┌─────────┐  ┌──────┐
│ 记忆 │←→│  LLM    │←→│ 工具 │
└──────┘  └─────────┘  └──────┘
               ↓
        ┌─────────────┐
        │ 执行环境     │
        └─────────────┘
```

### 2.1 推理核心（LLM）⭐⭐

| 关注点 | 说明 |
| --- | --- |
| 能力边界 | 复杂推理选强模型；分类/抽取选小模型 |
| 上下文 | 决定能带多少工具结果与记忆 |
| 稳定性 | 同输入不同输出 → 必须做校验与重试 |
| 结构化输出 | 用 JSON schema / function calling 约束 |
| 成本 | 多步 Agent 的 token 是单轮的 5~20 倍 |

### 2.2 工具（Tools）⭐⭐⭐

**工具设计的七条原则**：

| 原则 | 说明 |
| --- | --- |
| **单一职责** | 一个工具只做一件事（`get_order` 而不是 `handle_order`） |
| **描述即契约** | 描述里写清"什么时候用/什么时候不要用/参数格式" |
| **参数少而明确** | 超过 5 个参数考虑拆工具或用对象 |
| **返回值精简** | 只返回模型需要的信息，避免噪声淹没上下文 |
| **错误可读** | 返回结构化错误（code + message + 建议），模型能据此修正 |
| **幂等** | 写操作必须幂等（模型会重试） |
| **权限最小** | 工具按用户身份鉴权，不信任模型 |

**工具返回的错误设计**：

```json
{
  "success": false,
  "error_code": "ORDER_NOT_FOUND",
  "message": "订单号 2024xxx 不存在，请确认是否为 18 位",
  "retryable": false,
  "suggestion": "让用户核对订单号，或改用手机号查询"
}
```

**为什么错误信息要"可读"**：模型会读它来决定下一步。返回一个 `NullPointerException` 栈，模型只会瞎猜。

### 2.3 记忆（Memory）⭐⭐

| 类型 | 存什么 | 存储 | 生命周期 |
| --- | --- | --- | --- |
| **短期/工作记忆** | 当前任务的中间结果 | 上下文 / 状态对象 | 单次任务 |
| **对话记忆** | 最近 N 轮 | 上下文 | 会话 |
| **长期事实记忆** | 用户偏好、历史结论 | 向量库/DB | 长期 |
| **情景记忆** | 过去类似任务的轨迹 | 向量库 | 长期 |
| **程序性记忆** | 成功的操作步骤 | 规则/SOP | 长期 |

**记忆的四个工程问题**：

```
① 写什么：不是所有对话都值得记（要抽取、去重）
② 怎么取：按相关性 + 时效性检索
③ 怎么忘：过期、冲突、用户要求删除（合规）
④ 怎么隔离：多租户/多用户绝不能串
```

### 2.4 规划（Planning）⭐⭐⭐

| 方式 | 说明 | 适用 |
| --- | --- | --- |
| 隐式规划 | ReAct 边想边做 | 步骤少、探索性 |
| 显式规划 | 先输出步骤列表再执行 | 步骤多、可并行 |
| 层次规划 | 高层目标 → 子目标 → 原子动作 | 复杂任务 |
| 搜索式 | ToT/MCTS 探索多条路径 | 需要试错 |

**追问**："显式规划的最大风险？"
→ **规划错误会传播**。所以要有 **replan（重新规划）**：每执行几步就检查目标是否还可达。

### 2.5 执行环境 ⭐⭐

| 环境 | 用途 | 风险 |
| --- | --- | --- |
| 本地进程 | 开发调试 | 权限过大 |
| 容器沙箱 | 代码执行 | 逃逸、资源耗尽 |
| 浏览器 | 网页操作（Computer Use） | 账号安全、验证码 |
| 远程 API | 调用外部系统 | 限流、数据出境 |

**原则**：**最小权限 + 资源限制 + 网络白名单 + 审计**。

## 三、架构范式：从 ReAct 到多智能体

### 3.1 ReAct ⭐⭐⭐

```
Thought: 我需要先查订单状态
Action: query_order({"order_id": "2024..."})
Observation: {"status": "已发货", ...}
Thought: 已发货，需要查物流
Action: query_logistics({"order_id": "2024..."})
Observation: ...
Thought: 信息够了，可以回答
Answer: ...
```

| 优点 | 缺点 |
| --- | --- |
| 简单、可解释 | 步数多、易跑偏 |
| 天然支持工具 | 每步都要一次模型调用（贵、慢） |
| 失败可恢复 | 没有全局规划，可能绕远路 |

**实现要点**：

- 每步只允许**一个** action（并行会难以调试）。
- Observation 要截断（否则上下文爆炸）。
- 强制 `max_steps`（如 10）。
- 检测重复 action（相同工具 + 相同参数连续出现 → 中止）。

### 3.2 Plan-and-Execute ⭐⭐⭐

```
① Planner：把目标拆成步骤 [S1, S2, S3]
② Executor：逐个执行（可以用较小模型）
③ Replanner：根据结果决定继续/修改计划
```

| 优点 | 缺点 |
| --- | --- |
| 全局视角、可并行 | 规划错了全错 |
| 执行可用小模型，省钱 | 计划粒度难把握 |
| 进度可见 | 不适合高度探索性任务 |

**追问**："什么时候用 Plan-and-Execute 而不是 ReAct？"
→ 任务**步骤可预判**（如"总结这份合同 + 提取条款 + 生成风险清单"）时，用 Plan；任务**需要边做边看**（如排查一个线上问题）时，用 ReAct。

### 3.3 Reflection / Reflexion ⭐⭐

```
执行 → 自我评估（或外部评审）→ 生成改进建议 → 重新执行
```

**变体**：

| 变体 | 说明 |
| --- | --- |
| Self-Refine | 同一个模型自我批评并修改 |
| Reflexion | 把失败经验写入"记忆"，下次避免 |
| 外部评审 | 用另一个模型/规则检查 |

**代价**：成本翻倍、延迟增加。**只在高价值输出（写作、代码、方案）上用。**

### 3.4 Tree of Thoughts（ToT）⭐

```
把问题拆成多个"思考节点"，每个节点生成多个候选
→ 评估 → 保留最好的几个 → 继续展开
```

**适用**：需要搜索/试错的推理题（规划、谜题、创意）。**不适用**普通业务流程（成本爆炸）。

### 3.5 Multi-Agent ⭐⭐⭐

**四种协作模式**：

| 模式 | 说明 | 例子 |
| --- | --- | --- |
| **Orchestrator-Worker** | 主 Agent 分派子任务 | 研究助手：分派给搜索/写作子 Agent |
| **Pipeline** | 顺序流水线 | 需求 → 设计 → 代码 → 测试 |
| **Debate** | 多角色辩论后投票 | 方案评审 |
| **Hierarchical** | 多层级管理 | 大型任务分解 |

**什么时候值得上多 Agent**：

```
① 子任务需要不同的系统提示/工具集（隔离上下文）
② 子任务可并行
③ 需要独立评审（减少自我偏见）
```

**什么时候不该**：

```
① 只是"看起来高级"（协调成本 > 收益）
② 上下文不能共享（子 Agent 看不到全局）
③ 成本敏感（N 个 Agent = N 倍 token）
```

**面试话术**："我们只在**上下文需要隔离**时才拆多 Agent——比如一个负责读长文档，一个负责写结论。否则单 Agent + 状态机更便宜也更好调。"

### 3.6 混合架构：生产环境真实形态 ⭐⭐⭐

```
用户请求
  → 意图识别（小模型/规则）
  → 路由
      ├─ 简单问题 → 规则/FAQ（0 次 LLM）
      ├─ 知识问答 → RAG（1 次 LLM）
      ├─ 业务操作 → 状态机 + 工具（确定性流程 + 关键节点模型判断）
      └─ 复杂任务 → Agent（ReAct/Plan）
  → 结果校验 → 输出
```

**这张图是面试的"杀手锏"**：它说明你不是"什么都说 Agent"，而是**按成本和可靠性分层**。

## 四、工具调用与 MCP 协议

### 4.1 Function Calling 的完整链路 ⭐⭐⭐

```
① 应用把工具定义（JSON Schema）随请求发给模型
② 模型决定调用哪个工具、参数是什么（返回 tool_calls）
③ 应用执行工具（本地/远程）
④ 把结果作为 tool 消息回传给模型
⑤ 模型继续（可能再调用，或生成最终答案）
```

**关键细节**：

| 细节 | 说明 |
| --- | --- |
| `tool_choice` | `auto` / `none` / 强制某个工具 |
| **并行调用** | 一次返回多个 tool_calls，可并行执行（注意依赖关系） |
| `strict` 模式 | 强制符合 schema（部分厂商支持） |
| 参数校验 | 服务端必须校验（类型、范围、权限） |
| 结果顺序 | 多个 tool 结果要按 tool_call_id 对应 |
| 上下文增长 | 每次工具结果都进上下文 → 要截断/摘要 |

**并行调用的坑**：模型可能同时请求"创建订单"和"取消订单"。**有依赖或互斥的操作必须串行 + 人工确认。**

### 4.2 工具设计进阶 ⭐⭐

| 问题 | 方案 |
| --- | --- |
| 工具太多（> 20） | 分组 + 两阶段选择（先选类目，再选工具） |
| 名称相似 | 命名要有区分度（`search_docs` vs `search_orders`） |
| 参数复杂 | 用对象/枚举，少用自由文本 |
| 返回值大 | 分页 + 摘要 + 只返回必要字段 |
| 需要多步 | 拆成原子工具，而不是一个"万能工具" |

**工具描述模板**：

```text
name: refund_order
description: |
  对已支付的订单发起退款。
  使用场景：用户明确要求退款，且订单状态为「已支付」或「已发货」。
  不要用于：订单未支付（应调用 cancel_order）、超过 30 天的订单（需人工）。
parameters:
  order_id: 18 位订单号
  amount: 退款金额（分），不能超过实付金额
  reason: 退款原因，枚举 [质量问题, 七天无理由, 商家原因, 其他]
returns: 退款单号 + 预计到账时间
errors: ORDER_NOT_FOUND / AMOUNT_EXCEEDED / STATUS_INVALID
```

### 4.3 Structured Output vs Function Calling ⭐⭐

| 维度 | Structured Output | Function Calling |
| --- | --- | --- |
| 目的 | 让模型输出**固定结构** | 让模型**触发动作** |
| 结果 | 直接作为数据 | 需要应用执行 |
| 校验 | schema 校验 | 参数校验 + 权限 |
| 场景 | 抽取、分类、表单 | 查询、操作 |

**实践中经常组合**：用 structured output 让模型先"规划"（输出步骤 JSON），再逐步执行。

### 4.4 MCP：协议层的关键设计

**MCP（Model Context Protocol）** 用统一协议把外部能力暴露给模型应用。

```
Host（IDE/Agent 平台）
  └── MCP Client ──(JSON-RPC)──→ MCP Server ──→ 外部系统（DB/Git/文件）
```

| 原语 | 方向 | 说明 |
| --- | --- | --- |
| **tools** | Server → Client | 可调用的函数 |
| **resources** | Server → Client | 可读取的数据（文件、记录） |
| **prompts** | Server → Client | 预置提示模板 |
| sampling | Server → Client | 反向请求 Host 调模型 |
| roots | Client → Server | 限定可访问的目录/范围 |

**传输**：

| 传输 | 场景 |
| --- | --- |
| stdio | 本地进程（IDE 插件常见） |
| Streamable HTTP | 远程服务（推荐，替代旧 SSE） |

**生命周期**：

```
initialize（协商能力）→ initialized 通知 → tools/list → tools/call → ... → 关闭
```

**为什么 MCP 重要**：

```
之前：每个 AI 应用 × 每个外部系统 = N×M 个连接器
之后：每个系统实现 1 个 MCP Server，每个应用实现 1 个 Client = N+M
```

**MCP 的安全风险（必答）**：

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 工具投毒 | 恶意 Server 提供带后门的工具 | 白名单、来源审计 |
| 权限过大 | 工具能读整个库 | 最小权限、scope |
| 提示注入 | 工具返回内容含恶意指令 | 结果当数据、不当指令；输出过滤 |
| 本地提权 | stdio Server 继承宿主权限 | 沙箱、独立用户、只读挂载 |
| 数据外泄 | 工具把数据发到外部 | 网络白名单、DLP |

**面试话术**："MCP 解决的是**连接器的标准化**，但它把安全边界从『应用内部』推到了『协议边界』——所以我们必须做工具白名单 + 参数校验 + 审计，不能默认任何 Server 可信。"

### 4.5 A2A（Agent-to-Agent）简介 ⭐

Google 2025 提出的 Agent 间协作协议，核心概念：

| 概念 | 说明 |
| --- | --- |
| Agent Card | 描述 Agent 的能力、端点、认证方式 |
| Task | 一个可异步执行的任务（有状态） |
| Message/Artifact | 交互消息与产物 |

**面试定位**：知道它解决"跨厂商 Agent 协作"，但生态尚早，**不要吹成已大规模落地**。

## 五、记忆与上下文工程

### 5.1 上下文工程（Context Engineering）⭐⭐⭐

2025 年的新热词，本质是：**在有限窗口里放最有用的信息**。

| 手段 | 说明 |
| --- | --- |
| **选择** | 只放相关工具结果/文档片段 |
| **压缩** | 摘要、抽取关键字段 |
| **排序** | 重要信息放开头/结尾（Lost in the Middle） |
| **结构化** | 用 XML/JSON 分区（指令/数据/历史） |
| **外置** | 把长内容放"文件/记忆"，用时再取（类似虚拟内存） |

**"上下文腐化"**：对话越长，模型越容易忘记早期约束、被无关信息干扰。解决：**定期摘要 + 重述关键约束**。

### 5.2 记忆系统的实现 ⭐⭐

```
写入：对话 → 抽取事实/偏好 → 去重 → 向量化 + 元数据 → 存储
读取：当前任务 → 检索相关记忆 → 排序 → 注入上下文
维护：过期、冲突合并、删除（合规）
```

**冲突处理**：

| 情况 | 处理 |
| --- | --- |
| 新事实与旧事实冲突 | 以时间新的为准（带时间戳） |
| 用户明确纠正 | 标记旧记忆失效 |
| 多来源 | 保留来源与置信度 |

### 5.3 长任务的上下文管理 ⭐⭐⭐

| 问题 | 方案 |
| --- | --- |
| 超出窗口 | 分段处理 + 中间结果落盘 |
| 需要全局视角 | 维护"任务状态摘要"，每步更新 |
| 子任务隔离 | 子 Agent 只带必要上下文 |
| 失败重来 | 持久化状态，从断点恢复 |

**"文件系统当内存"技巧**：让 Agent 把中间结果写成文件/笔记，需要时再读——这是长任务的常用手法。

### 6.1 Spring AI 的工具调用骨架 ⭐⭐

```java
@Configuration
class ToolConfig {
    @Bean
    @Description("根据订单号查询订单状态，仅在用户提供 18 位订单号时使用")
    Function<OrderQuery, OrderStatus> queryOrder(OrderService service) {
        return q -> service.query(q.orderId());
    }
}

record OrderQuery(String orderId) {}
record OrderStatus(String status, String logistics, String eta) {}

@RestController
class ChatController {
    private final ChatClient chatClient;

    @GetMapping("/chat")
    String chat(@RequestParam String q) {
        return chatClient.prompt()
                .system("""
                    你是订单助手。只能依据工具返回的事实回答。
                    如果工具报错，向用户说明原因并给出下一步建议。
                    不要编造物流信息。
                    """)
                .user(q)
                .tools("queryOrder")
                .call()
                .content();
    }

```

**注意**：真正的多步 Agent 不要用这种"一次调用"，而是**自己管理循环**，才能做步数、预算、审计。

### 6.2 自研 Agent 循环（可控版）⭐⭐⭐

```java
public class AgentLoop {
    private static final int MAX_STEPS = 10;
    private static final int MAX_TOKENS = 50_000;

    public AgentResult run(String goal, String userId) {
        State state = State.start(goal, userId);
        int steps = 0;
        int tokens = 0;

        while (steps++ < MAX_STEPS && tokens < MAX_TOKENS) {
            // ① 组装上下文（系统提示 + 目标 + 历史 + 工具结果摘要）
            Prompt prompt = state.buildPrompt();

            // ② 调模型
            LlmResponse resp = llm.chat(prompt);
            tokens += resp.usage().total();

            // ③ 有工具调用 → 执行
            if (resp.hasToolCall()) {
                ToolCall call = resp.toolCall();
                if (state.isRepeated(call)) {
                    return AgentResult.fail("检测到重复动作，已中止", state);
                }
                ToolResult result = toolRegistry.invoke(call, userId);  // 内部做鉴权/超时/幂等
                state.append(call, result);
                state.persist();          // 关键：每步持久化，支持断点续跑
                continue;
            }

            // ④ 没有工具调用 → 视为最终答案
            return AgentResult.ok(resp.content(), state);
        }
        return AgentResult.fail("超过步数或预算", state);
    }
}
```

**这段代码要能解释四个设计**：

| 设计 | 为什么 |
| --- | --- |
| `MAX_STEPS` | 防死循环 |
| `MAX_TOKENS` | 防烧钱 |
| `isRepeated` | 模型陷入循环的典型特征 |
| `persist()` | 断点续跑与审计 |

### 6.3 状态机编排 ⭐⭐⭐

```java
enum Stage { PARSE, LOOKUP, CONFIRM, EXECUTE, DONE, FAILED }

// 每个阶段：输入 → 处理 → 输出 + 下一阶段
// 模型只在"需要判断"的边（如 PARSE 的意图、CONFIRM 的话术）参与
```

**为什么用状态机**：

- 可测试（每个状态单独测）
- 可回放（记录状态转移）
- 可恢复（从持久化状态继续）
- 可插入人工节点（`WAITING_HUMAN`）

### 6.4 长任务与断点续跑

| 能力 | 实现 |
| --- | --- |
| 状态持久化 | DB 存 `task_id + stage + context + history` |
| 续跑 | 按 `task_id` 加载状态，从 `stage` 继续 |
| 幂等 | 每步有 `step_id`，重复执行结果一致 |
| 超时 | 单步超时 + 总时长超时 |
| 取消 | 标记 cancel，循环检查 |
| 人工介入 | 状态置 `WAITING_HUMAN`，UI 提供操作 |

**分布式下的坑**：同一个 task 被两个 worker 同时处理 → **用分布式锁或状态版本号（CAS）保证只有一个执行者**。

### 6.5 并发、限流与成本 ⭐⭐

| 维度 | 做法 |
| --- | --- |
| 并发 | 按用户/租户限制同时运行的 Agent 数 |
| 限流 | RPM + TPM（token/分钟） |
| 排队 | 高峰排队，返回"任务已接受" |
| 预算 | 单任务 token 上限 + 租户日预算 |
| 熔断 | 模型错误率超阈值 → 降级到模板/人工 |

### 6.6 可观测（Agent 版）⭐⭐

```
一次 Agent 执行的 trace：
  span: agent.run
    ├── span: llm.call (step 1)  tokens=1200
    ├── span: tool.query_order   120ms
    ├── span: llm.call (step 2)  tokens=900
    ├── span: tool.refund        300ms
    └── span: llm.call (step 3)  tokens=600
```

**必须记录的字段**：

```
task_id, user_id, tenant_id
每步：输入摘要、工具名、参数、结果、耗时、token
总：步数、总 token、总耗时、是否成功、失败原因
```

## 七、可靠性与安全

### 7.1 六类失败模式与防线 ⭐⭐⭐

| 失败模式 | 表现 | 防线 |
| --- | --- | --- |
| **格式错误** | 输出不是合法 JSON | schema 校验 + 重试 + 兜底 |
| **工具失败** | 超时/报错 | 重试（幂等）+ 降级 + 明确错误反馈 |
| **死循环** | 反复调同一工具 | 最大步数 + 重复检测 + 预算 |
| **跑偏** | 做了不该做的事 | 目标校验 + 步骤白名单 + 人工确认 |
| **成本失控** | token 暴涨 | 单任务预算 + 租户配额 + 告警 |
| **数据泄露** | 越权/串租户 | 工具鉴权 + 检索过滤 + 输出脱敏 |

### 7.2 安全：OWASP LLM Top 10 里与 Agent 相关的四项 ⭐⭐⭐

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **Prompt Injection** | 工具返回/文档含恶意指令 | 指令与数据分离、结果不执行、输出过滤 |
| **Excessive Agency** | 模型权限过大 | 最小权限、写操作人工确认 |
| **Insecure Output Handling** | 模型输出被直接执行 | 不 `eval`、参数校验、转义 |
| **Sensitive Info Disclosure** | 泄露系统提示/用户数据 | 输出过滤、PII 脱敏、租户隔离 |

**"最小权限"的落地**：

```
工具分三级：
  L1 只读（可自动执行）：查订单、查文档
  L2 低风险写（需参数校验 + 幂等）：发消息、加备注
  L3 高风险写（必须人工确认）：退款、改价、删除
```

### 7.3 沙箱与代码执行 ⭐⭐

| 风险 | 缓解 |
| --- | --- |
| 执行恶意代码 | 容器隔离、无网络、只读挂载 |
| 资源耗尽 | CPU/内存/时间限制 |
| 逃逸 | 非 root、seccomp、gVisor/Kata |
| 数据泄露 | 不挂载敏感目录、出站白名单 |

**面试话术**："代码执行我们不放在业务容器里，而是单独的沙箱服务——短生命周期容器、无外网、限制 CPU/内存/时长，执行完立即销毁。"

### 7.4 人工介入（Human-in-the-loop）⭐⭐

| 模式 | 说明 |
| --- | --- |
| 事前确认 | 高风险操作前让用户确认 |
| 事中接管 | 卡住时转人工 |
| 事后审核 | 批量抽检 |

**设计要点**：确认信息要**结构化**（操作、对象、金额、后果），不能只给一段自然语言。

## 八、评测体系

### 8.1 四层评估 ⭐⭐⭐

| 层 | 指标 | 方法 |
| --- | --- | --- |
| **组件** | 工具选择准确率、参数正确率 | 标注轨迹 |
| **单步** | 每步决策是否合理 | LLM-as-judge + 规则 |
| **任务** | 成功率、平均步数、成本 | 端到端跑评测集 |
| **线上** | 完成率、转人工率、满意度、成本/任务 | 埋点 |

### 8.2 评测集怎么建 ⭐⭐⭐

```
① 收集真实任务（100~500 个），覆盖：
   - 高频简单任务
   - 多步复杂任务
   - 边界（信息缺失、工具报错、歧义）
   - 对抗（注入、越权请求）
② 定义成功标准（终态，不是路径）
③ 记录期望：必须调用的工具、禁止的操作、最终答案要点
④ 版本化，每次改动跑回归
```

**关键**：**任务型评测看终态**，不要求路径一致（同一个目标可能有多条路）。

### 8.3 LLM-as-judge 的正确用法 ⭐⭐

| 做法 | 说明 |
| --- | --- |
| 固定 rubric | 明确评分维度与分值 |
| 交换顺序 | 消除位置偏见 |
| 多次采样 | 取多数/平均 |
| 人工校准 | 抽 10% 人工复核，检查 judge 是否可靠 |
| 避免自我偏好 | 用不同模型评审 |

### 8.4 常用基准（知道即可）⭐

| 基准 | 衡量 |
| --- | --- |
| SWE-bench | 真实代码修复 |
| WebArena | 网页操作 |
| τ-bench | 工具调用 + 业务流程（客服） |
| GAIA | 通用助手任务 |
| AgentBench | 多环境综合 |

**面试提醒**：不要背分数，说明"基准和真实业务的差距"，反而加分。

## 十、系统设计题（5 道）

### 10.1 设计一个 Agent 平台

**需求**：业务方自助配置 Agent（提示词、工具、知识库），平台统一运行与观测。

| 模块 | 设计 |
| --- | --- |
| 配置 | Agent 定义（DSL/JSON）、版本管理、灰度 |
| 编排 | 状态机/DAG 引擎，支持人工节点 |
| 工具市场 | 注册、版本、鉴权、配额、审计 |
| 运行时 | 沙箱、超时、预算、并发控制 |
| 观测 | trace、token、成本、成功率 |
| 多租户 | 隔离、配额、计费 |

**关键决策**：

```
① Agent 定义用 DSL 还是代码？→ DSL（安全、可热更新），复杂逻辑用代码节点
② 工具如何隔离？→ 每租户独立凭证 + 网络策略
③ 如何防一个租户拖垮平台？→ 配额 + 隔离队列 + 熔断
```

### 10.2 设计一个长任务 Agent 系统

```
需求：任务可能跑几十分钟，要能中断恢复、进度可见
设计：
  - 任务表（状态机 + 版本号）
  - 步骤日志（每步输入输出）
  - 调度器（领取任务、心跳、超时重派）
  - 幂等（step_id）
  - 人工节点（WAITING_HUMAN）
  - 通知（完成/失败/需确认）
```

**难点**：重复执行、超时重派、状态一致性、取消。

### 10.3 设计一个工具网关（Tool Gateway）

```
统一接入工具 → 鉴权 → 限流 → 参数校验 → 执行 → 审计 → 返回精简结果
```

**价值**：工具不暴露给模型直连；统一做权限、配额、脱敏、可观测。

### 10.4 设计一个 Agent 评测平台

```
评测集管理 → 任务执行（并发）→ 结果判定（规则 + LLM judge）
→ 指标看板 → 回归对比 → badcase 回流
```

**难点**：评测成本（LLM judge 也烧钱）、结果稳定性、人工校准。

### 10.5 设计一个多 Agent 协作系统

```
Orchestrator（规划/分派/汇总）
  ├── Worker A（搜索）
  ├── Worker B（写作）
  └── Reviewer（评审）
共享：任务状态、中间产物
```

**难点**：上下文同步、冲突合并、成本、死锁（互相等待）。

### 12.1 四周路线

| 1 | 概念与范式 | 能手写 ReAct 循环（不含框架） |

| 4 | 评测与安全 | 20 个任务的评测集 + 红队用例 |

### 12.2 避坑清单（面试中能体现经验）

| 坑 | 正确做法 |
| --- | --- |
| 一上来就多 Agent | 先单 Agent + 状态机 |
| 没有最大步数 | 必须有，且要能解释取值 |
| 工具返回值全塞回上下文 | 精简 + 分页 + 摘要 |
| 让模型算钱/算库存 | 用代码算，模型只做判断 |
| 写操作不幂等 | 幂等键 + 唯一索引 |
| 没有人工确认 | 高风险操作必须确认 |
| 只测"能不能跑" | 建评测集 + 回归 |
| 用 Agent 做固定流程 | 用 workflow |
| 不做成本核算 | 单任务预算 + 租户配额 |
| 信任工具返回内容 | 当数据不当指令 |

## 写在最后

Agent 面试的分水岭不是"你知道多少范式"，而是：

1. **你知道什么时候不用 Agent**（这是判断力）。
2. **你能把不确定性关进笼子**（状态机、步数、预算、确认）。
3. **你能证明它有效**（评测集、成功率、成本）。
4. **你能对它负责**（回滚、审计、安全）。

如果只记一句话：**"Agent 不是一个更聪明的聊天框，而是一个需要被工程化约束的、会调用工具的、不稳定的决策组件。"**
