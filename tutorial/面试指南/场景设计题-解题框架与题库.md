## 零、场景题的四种类型与评分标准

### 0.1 四种类型，答题重心完全不同

| 类型 | 典型问法 | 答题重心 | 时间分配 |
| --- | --- | --- | --- |
| **系统设计** | "设计一个秒杀系统" | 架构 + 取舍 + 失败模式 | 澄清 3 / 设计 15 / 兜底 5 |
| **方案选择** | "用 Redis 还是本地缓存？" | 判据 + 对比 + 结论 | 判据 5 / 对比 8 / 结论 3 |
| **故障排查** | "接口突然变慢，怎么查？" | 工具 + 路径 + 根因 | 现象 2 / 排查 12 / 修复 5 |
| **演进改造** | "单体怎么拆微服务？" | 现状 + 目标 + 路径 + 风险 | 现状 4 / 路径 12 / 风险 5 |

**最常见的失分**：把"方案选择"答成"系统设计"（讲了 20 分钟架构，却没回答"为什么选 A"）。

### 0.2 评分标准（面试官心里的表）

| 维度 | 权重 | 3 分 | 5 分 |
| --- | --- | --- | --- |
| **澄清** | 10% | 直接开答 | 主动问清规模/一致性/预算 |
| **结构** | 15% | 想到哪说到哪 | 分层清晰、有框架 |
| **深度** | 25% | 只讲组件 | 讲清关键机制与数字 |
| **取舍** | 25% | 只说优点 | 说清代价与适用边界 |
| **兜底** | 15% | 没考虑失败 | 有失败模式与降级 |
| **演进** | 10% | 一步到位 | 有 V1/V2 与迁移路径 |

> **注意**：深度和取舍各占 25%，加起来一半。**"我知道怎么做"只能拿 3 分，"我知道为什么这么做、代价是什么"才是 5 分。**

### 0.3 一个残酷的事实

面试官通常**不关心你的方案是否完美**，而关心：

```
① 你有没有先问清需求（而不是假设）
② 你的方案在什么规模下会崩
③ 崩了怎么办
④ 如果预算只有一半，你会砍哪里
```

**能回答第 ④ 个问题的候选人，极少。**

## 一、通用答题框架：4S 法

### 1.1 4S 法（背下来）

```
S1 · Scenario（澄清场景）      2~3 min
  - 功能边界：做什么、不做什么
  - 规模：DAU/QPS/数据量/增长
  - 约束：一致性、延迟、预算、合规
  - 输出：复述一遍需求，确认理解

S2 · Scale（量级估算）          2 min
  - QPS、存储、带宽、连接数、机器数
  - 用数字驱动设计（"因为 10 万 QPS，所以必须分片"）

S3 · Solution（方案设计）       10~12 min
  - 先画主链路（能跑通）
  - 再讲关键决策（每个给"选项→判据→结论→代价"）
  - 分层：接入 / 应用 / 缓存 / 存储 / 依赖

S4 · Stress（压力与失败）      5 min
  - 单点在哪？热点在哪？瓶颈在哪？
  - 每个失败模式给"检测 + 兜底"
  - 演进：V1 怎么上线，V2 加什么
```

### 1.2 S1：澄清清单（照着问，显得专业）

| 维度 | 要问的问题 | 为什么要问 |
| --- | --- | --- |
| 功能 | 核心功能是什么？哪些可以不做？ | 避免过度设计 |
| 规模 | DAU/峰值 QPS/数据量/增长率？ | 决定架构复杂度 |
| 读写比 | 读多还是写多？ | 决定存储与缓存 |
| 一致性 | 允许旧数据吗？允许多久？ | 决定是否要分布式事务 |
| 延迟 | P99 要求？ | 决定同步/异步 |
| 成本 | 有预算约束吗？ | 决定自研还是采购 |
| 合规 | 数据敏感吗？要审计吗？ | 决定隔离与加密 |
| 生命周期 | 一次性活动还是长期产品？ | 决定投入 |

**话术模板**：

> "在开始设计前，我想确认几个点：这个系统的峰值 QPS 大概多少？数据需要保留多久？一致性上，是允许秒级延迟，还是必须强一致？另外有成本约束吗？"

**只问 3 个最关键的就够**，问太多显得没主见。

### 1.3 S2：估算公式库（背这几条）

```
QPS = DAU × 人均请求数 / 86400 × 峰值系数(3~10)
并发数 = QPS × RT(秒)                       （Little's Law）
存储 = 单条大小 × 日增条数 × 保留天数 × 副本数 × 1.5（索引/碎片）
带宽 = QPS × 平均响应大小 × 8
连接数 = QPS × RT
机器数 = 峰值 QPS / 单机容量 / 水位(0.6~0.7)
缓存容量 = 热数据量 × 1.2
```

**示例（必须能口算）**：

```
日订单 100 万，峰值系数 5
→ 平均 QPS = 100万/86400 ≈ 11.6
→ 峰值 QPS ≈ 58
→ 大促再 ×5 ≈ 290

单条订单 2KB，保留 3 年
→ 100万 × 365 × 3 × 2KB ≈ 2.1TB（不含索引）
→ 加索引和副本 ≈ 6TB
```

### 1.4 S3：架构分层模板

```
① 接入层    DNS / CDN / LB / 网关（限流、鉴权、路由）
② 应用层    无状态服务（水平扩展）
③ 缓存层    本地缓存 + Redis（多级）
④ 存储层    MySQL（分库分表）/ NoSQL / 对象存储
⑤ 异步层    MQ（削峰、解耦）
⑥ 支撑层    注册中心、配置中心、监控、链路追踪
```

**画图时从"用户请求"开始，一条线走到底**，不要一上来画所有组件。

### 1.5 S4：失败模式清单（逐条过一遍，显得老练）

| 失败模式 | 检测 | 兜底 |
| --- | --- | --- |
| **单点** | 健康检查 | 多实例、多可用区 |
| **热点** | 分片 QPS/CPU 不均 | 本地缓存、key 打散 |
| **雪崩** | 错误率、RT | 熔断、限流、降级 |
| **击穿** | 缓存命中率骤降 | 互斥重建、逻辑过期 |
| **穿透** | DB QPS 异常 | 布隆过滤器、空值缓存 |
| **脑裂** | 双主写入 | 多数派、fencing token |
| **数据丢失** | 对账、校验 | 副本、事务消息、补偿 |
| **幂等** | 重复请求 | 唯一键、去重表、状态机 |
| **时钟** | 时间跳变 | 逻辑时钟、版本号 |
| **容量** | 水位 | 扩容、限流、降级 |

**面试时至少说 3 条**，并说明"怎么发现"。

### 1.6 取舍表达模板（最重要的话术）

```
"这里有两个选择：A 和 B。
 判据是【一致性要求 / 成本 / 延迟】。
 选 A 的话，能拿到【收益】，代价是【成本】。
 我的结论是【A】，因为【业务能接受这个代价】。
 如果【条件变化】，我会改成 B。"
```

**举例**：

> "库存扣减有两个选择：DB 乐观锁和 Redis + Lua。判据是并发量和一致性要求。DB 乐观锁简单可靠，但 1 万 QPS 下 DB 会扛不住；Redis 方案能扛 10 万，但需要处理缓存与 DB 的最终一致。我选 Redis + Lua + 异步落库 + 对账，因为秒杀场景能接受秒级不一致，而且我们有不超卖的兜底（DB 唯一约束 + 超卖退款）。如果是对账要求极高的金融场景，我会选 DB 乐观锁 + 排队。"

## 二、高并发场景（8 题）

> 这类题的核心是：**把流量挡在离用户最近的地方，把一致性放到最不重要的地方**。

### 2.1 秒杀：100 万人抢 1000 件商品

**澄清**：峰值 QPS？是否允许超卖？用户是否要看到实时库存？是否需要防刷？

**估算**：

```
100 万人 / 10s 集中涌入 → 峰值 10 万 QPS
库存 1000 件 → 99.9% 的请求注定失败 → 尽早拦截
```

**方案（分层拦截）**：

```
① 前端：按钮置灰、倒计时、验证码、静态化
② 网关：限流（用户/ip/接口）、黑名单、防重放
③ 应用：
   - 库存预热到 Redis
   - Lua 原子扣减（判断 + 扣减 + 记录用户）
   - 扣减成功才发 MQ
④ 异步：MQ 削峰 → 订单服务落库
⑤ 兜底：DB 乐观锁（`WHERE stock > 0`）+ 对账
```

**Lua 脚本（原子）**：

```lua
-- KEYS[1]=stock:{skuId}  KEYS[2]=bought:{skuId}  ARGV[1]=userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2                       -- 重复购买
end
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
if stock <= 0 then
    return -1                       -- 售罄
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return stock - 1
```

**关键决策**：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 扣库存位置 | Redis | DB 扛不住 10 万 QPS |
| 是否超卖 | 不超卖 | Lua 原子 + DB 兜底 |
| 下单方式 | 异步（MQ） | 削峰、解耦 |
| 用户如何知道结果 | 轮询/推送 | 同步等待会拖垮连接 |
| 防刷 | 用户维度去重 + 风控 | 黄牛 |

**失败模式**：

| 失败 | 兜底 |
| --- | --- |
| Redis 挂了 | 降级到 DB 乐观锁 + 限流 |
| MQ 堆积 | 扩消费者、临时降级非核心 |
| 超卖 | 唯一约束 + 超卖退款 + 告警 |
| 库存预热错 | 预热校验 + 对账 |

**追问**："Redis 扣了但订单落库失败怎么办？" → MQ 重试 + 定时对账（Redis 已扣但无订单 → 回补库存或补单）。

### 2.2 抢红包

**核心差异**：金额要**拆分且不超发**（原子性比库存更敏感）。

**方案**：

```
① 红包预先拆好（二倍均值法），存入 Redis List
② 抢红包 = LPOP（原子，天然不重复）
③ 抢到后异步落库
④ 金额校验：总额 = Σ 拆分金额
```

**二倍均值法**：

```
每次随机金额 ∈ [1分, 剩余金额/剩余人数 × 2]
保证：不会有人抢到 0，也不会提前抢完
```

**追问**："为什么不用 `DECR` 扣总额？"
→ 因为还要保证"每个人只抢一次"和"金额可追溯"，`LPOP` + 用户去重更简单；而且拆分好的金额天然满足"总额守恒"。

**追问**："Redis 挂了会超发吗？"
→ 会（如果降级）。所以要有**总金额上限**的唯一约束 + 事后对账。

### 2.3 点赞 / 计数

**需求**：单条内容百万赞，要判重、要计数、要看"我赞过没"。

**方案**：

```
① Redis Hash：like:{postId} → {userId: 1}，HLEN 计数，HGET 判重
② 大 key 拆分：按 postId 分片（hash tag）
③ 异步落库：MQ → 批量写 DB（点赞明细 + 计数）
④ 计数缓存：content 表存冗余计数，定时校准
```

**关键决策**：

| 决策 | 说明 |
| --- | --- |
| 精确 vs 近似 | 点赞要精确（可展示"谁赞了"） |
| 计数一致性 | 允许短暂不准，定时校准 |
| 防刷 | 用户维度限流 + 风控 |

**追问**："100 万赞的 Hash 会不会阻塞？"
→ 会。`HLEN` 是 O(1)，但 `HGETALL` 是 O(N)。所以**只存需要判重的用户 ID**，展示列表另存 ZSet（按时间），并且分页。

### 2.4 排行榜

**需求**：日榜/周榜/总榜，Top N + 我的排名。

```bash
ZINCRBY rank:2024-06-01 10 user:123
ZREVRANGE rank:2024-06-01 0 99 WITHSCORES
ZREVRANK rank:2024-06-01 user:123
```

**关键决策**：

| 问题 | 方案 |
| --- | --- |
| 同分排序 | score 拼接时间戳小数，或 member 用 `时间戳:uid` |
| 海量用户 | 只维护 Top 1 万，其余离线算 |
| 分页 | `ZREVRANGE` 区间，`O(log N + M)` |
| 榜单周期 | key 带日期 + 定时归档 |
| 多维度 | 每个维度一个 ZSet |

**追问**："1 亿用户的榜单，Redis 放得下吗？"
→ 放不下（1 亿 × 约 100B = 10GB+）。所以用**分桶 + 归并**：按 uid 哈希 100 桶，每桶 Top 100，查询时归并 100 个 Top100。

### 2.5 Feed 流（朋友圈/关注）

**推拉模式对比**：

| 模式 | 写 | 读 | 适用 |
| --- | --- | --- | --- |
| 推（写扩散） | 写所有粉丝收件箱 | 快 | 普通用户 |
| 拉（读扩散） | 只写自己 | 慢（要合并） | 大 V |
| **推拉结合** | 普通用户推、大 V 拉 | 合并 | **主流** |

**方案**：

```
发内容 → 判断是否大 V
  ├─ 否 → 写入粉丝收件箱（Redis ZSet，按时间）
  └─ 是 → 只写自己，读时单独拉取并合并
读 → 从收件箱取 + 合并大 V 内容 + 分页（游标）
```

**追问**："分页用 offset 还是游标？"
→ **游标**。offset 在 feed 场景会因新内容插入而重复/遗漏。

### 2.6 多仓库存扣减

**需求**：一个 SKU 分布在多个仓，下单要选仓 + 扣减 + 避免超卖。

**方案**：

```
① 库存维度：sku × 仓
② 选仓策略：就近/有货优先/成本优先
③ 扣减：Redis 分仓库存 + Lua；或 DB 分仓行锁
④ 跨仓订单：拆单（每个仓一个子单）
⑤ 兜底：缺货时调拨/取消子单
```

**追问**："用户下单时某仓刚好没货？"
→ 预占（Try）时按优先级尝试多个仓；全失败则提示"部分缺货"，允许拆单或等待调拨。

### 2.7 防重复下单 / 幂等

**四层防护**：

```
① 前端：按钮防抖 + 提交后禁用
② 网关/应用：token（一次一用）+ 分布式锁（用户维度）
③ 服务：唯一索引（user_id + 商品 + 时间窗口）或业务幂等键
④ DB：状态机（只有待支付能变成已支付）
```

**幂等键设计**：

| 场景 | 幂等键 |
| --- | --- |
| 创建订单 | `request_id`（客户端生成） |
| 支付回调 | `商户订单号 + 支付流水号` |
| MQ 消费 | `msg_id` 或业务唯一键 |

**追问**："分布式锁能防重复吗？"
→ 只能防**并发**重复，防不了**重试**（锁释放后重试仍会重复）。所以必须靠**幂等键 + 唯一索引**。

### 2.8 抽奖

**需求**：奖品有限、概率可控、不能超发、可审计。

**方案**：

```
① 奖品库存：Redis 扣减（Lua 原子）
② 概率：别名算法（Alias Method）O(1) 采样，或分段随机
③ 用户维度：每日次数限制（Redis）
④ 中奖记录：异步落库 + 唯一约束
⑤ 兜底：库存不足时降级为"谢谢参与"或积分
```

**追问**："概率怎么保证公平？"
→ 概率表配置化 + 抽样算法固定 + 中奖记录可审计；**不要用 `Math.random()` 手写分段**（容易错）。

## 三、数据一致性场景（6 题）

> 这类题的核心是：**先定义一致性级别，再选方案；不要一上来就说"强一致"。**

### 3.1 缓存与数据库一致

**先问**：允许旧数据吗？允许多久？

**方案对比**：

| 方案 | 一致性 | 复杂度 | 适用 |
| --- | --- | --- | --- |
| 先更 DB 再删缓存 | 秒级 | 低 | 大多数业务 |
| 延迟双删 | 秒级 | 中 | 并发写多 |
| Canal 订阅 binlog | 秒级 | 中高 | 多写路径 |
| 分布式锁串行化 | 强 | 高 | 极少数 |
| 不用缓存 | 强 | — | 强一致场景 |

**关键细节**：

```
为什么删而不是改：避免并发覆盖 + 懒加载
为什么先 DB 后删：反过来会把旧值回填
极小窗口：读请求在 DB 更新前读、删之后回填 → 延迟双删兜底
```

**追问**："延迟双删的延迟怎么定？"
→ 大于一次读的耗时（读 DB + 回填）+ 主从延迟，用 P99 来估，通常 500ms~1s。

### 3.2 下单扣库存的分布式事务

**四个方案的取舍**：

| 方案 | 一致性 | 性能 | 侵入 | 适用 |
| --- | --- | --- | --- | --- |
| 本地事务（同库） | 强 | 好 | 低 | 单库 |
| TCC | 强 | 中 | 高 | 资金 |
| 事务消息 | 最终 | 好 | 低 | 有 MQ |
| 本地消息表 | 最终 | 好 | 中 | 通用 |

**推荐（大多数电商）**：

```
订单服务：订单表 + 本地消息表（同一事务）
  → 定时发 MQ
  → 库存服务消费，幂等扣减（唯一索引 order_id）
  → 失败重试 + 对账补偿
```

**追问**："为什么要本地消息表，不直接发 MQ？"
→ 因为"写 DB 成功 + 发 MQ 失败"会导致数据不一致；本地消息表把两件事放进同一个本地事务。

### 3.3 支付回调的幂等与对账

**回调处理**：

```java
@Transactional
public void onPayCallback(PayNotify notify) {
    // ① 验签
    if (!sign.verify(notify)) return;
    // ② 幂等：唯一索引（渠道流水号）
    if (payFlowMapper.exists(notify.getChannelFlowNo())) {
        return ACK;                        // 已处理，直接成功
    }
    // ③ 状态机：只有待支付才能改成已支付
    int n = orderMapper.pay(notify.getOrderNo(), PENDING, PAID);
    if (n == 0) return ACK;                // 状态不对，幂等忽略
    // ④ 记账 + 发消息（本地消息表）
}
```

**对账（T+1）**：

```
下载渠道账单 → 与本地流水逐笔比对
  ├─ 长款（渠道有、本地无）→ 补单
  ├─ 短款（本地有、渠道无）→ 冲正/挂账
  └─ 金额不符 → 人工
```

**追问**："回调丢了怎么办？"
→ **主动查询**（定时轮询渠道订单状态）+ 对账兜底；不要只依赖回调。

### 3.4 主从延迟导致"下单后查不到"

**现象**：写完主库，立刻读从库，读不到 → 用户以为失败，重复下单。

**方案**：

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| 强制走主库 | 关键读走主 | 主库压力 |
| 写后标记 | 写时在缓存标记"该用户近期写过"，读时走主 | 实现复杂 |
| 会话粘性 | 同一会话读主 | 复杂 |
| 前端延迟 | 提示"处理中" | 体验 |
| 半同步复制 | 减少延迟 | RT 增加 |

**面试话术**："我们的做法是**写后 1 秒内该用户的读走主库**（用 Redis 标记），1 秒后恢复正常读写分离。"

### 3.5 分库分表后的跨库查询

**问题**：分片键是 `user_id`，但要按 `status` 查、按商家查、做统计。

**方案**：

| 需求 | 方案 |
| --- | --- |
| 按非分片键查询 | **异构索引表**（status → order_id） |
| 多条件组合 | 搜索引擎（ES）同步 |
| 统计报表 | 数仓/OLAP |
| 全局分页 | 游标分页 / 二次查询 |
| 跨片 join | 冗余字段 / 广播表 / 应用层 join |

**追问**："异构索引表怎么保证一致？"
→ binlog/CDC 异步同步 + 定时对账；允许短暂不一致（索引只用于定位 ID，最终查主表）。

### 3.6 数据迁移（双写/灰度）

**四阶段**：

```
① 双写（新老都写，读老）
② 数据同步（全量 + 增量，校验）
③ 灰度读新（1% → 10% → 50% → 100%）
④ 停写老（观察后下线）
```

**关键点**：

| 点 | 说明 |
| --- | --- |
| 幂等 | 重放不产生重复 |
| 校验 | 全量对比 + 增量对比 |
| 回滚 | 随时能切回老 |
| 一致性 | 双写失败的处理（补偿/告警） |

**追问**："双写不一致怎么办？"
→ 以**新库为准**（迁移期），用 binlog 回补 + 对账；双写失败记录到补偿表。

## 四、稳定性与容量场景（6 题）

### 4.1 流量突增 10 倍

**先判断**：是**预期内**（大促）还是**突发**（热点/攻击）。

**应对顺序**：

```
① 限流（保命）——网关 + 应用 + DB
② 降级（弃车保帅）——关非核心
③ 扩容（如果资源允许）
④ 缓存（挡读）
⑤ 异步（削峰）
```

**关键**：**限流要分层**（用户/接口/全局），且**阈值要提前压测**。

**追问**："扩容来不及怎么办？"
→ 限流 + 降级 + 排队；**不要指望扩容救急**（JVM 预热、连接池建立都要时间）。

### 4.2 依赖服务故障

**四板斧**：

```
① 超时（必须设，且逐层递减）
② 重试（幂等 + 退避 + 次数上限）
③ 熔断（错误率/慢调用 → 快速失败）
④ 降级（兜底数据/关闭功能）
```

**追问**："重试会不会放大故障？"
→ 会。3 层各重试 2 次 = 27 倍流量。所以**只在最外层重试**，或统一在 RPC 框架里重试。

### 4.3 缓存雪崩

**三种成因**：

```
① 大量 key 同时过期（批量预热 + 统一 TTL）
② Redis 实例故障
③ 缓存服务重启/主从切换
```

**方案**：

| 成因 | 方案 |
| --- | --- |
| 同时过期 | TTL 加随机抖动（±20%） |
| 实例故障 | 集群、多副本、本地缓存兜底 |
| 切换 | 客户端重试 + 熔断 |
| 通用 | 预热分片、DB 限流、降级兜底 |

### 4.4 MQ 积压

**四步**：算缺口 → 找瓶颈 → 组合处理 → 防复发（详见中间件文档 4.6）。

**关键数字**：

```
消费能力 = 实例数 × (1000 / 单条耗时ms)
追平时间 = 积压量 / (消费能力 - 生产速率)
```

**降级策略**：只处理核心消息、丢弃可丢消息、临时落库后离线处理。

### 4.5 机房故障 / 单可用区

**分级**：

| 级别 | 要求 | 方案 |
| --- | --- | --- |
| 同城双活 | RTO 分钟级 | 双机房部署 + 数据同步 |
| 两地三中心 | RTO 小时级 | 异地灾备 |
| 异地多活 | RTO 秒级 | 单元化 + 流量调度 |

**关键问题**：**数据同步方式**（同步 vs 异步）、**切换决策**（谁来决定切）、**回切**（切回来更难）。

### 4.6 大促保障

**五阶段**（详见进阶版 8.8）：

```
容量（1 个月前）→ 稳定性（2 周前）→ 演练（1 周前）→ 值守（当天）→ 复盘
```

**面试重点**：**压测找拐点** + **降级预案可执行** + **一键切流**。

## 五、架构演进场景（5 题）

### 5.1 单体拆微服务

**先问**：为什么要拆？（团队规模、发布效率、技术栈、故障隔离）

**拆分原则**：

```
① 按业务能力（DDD 限界上下文），不是按技术分层
② 先拆"变更频繁且独立"的模块
③ 共享数据库是最大的坑 → 逐步拆库
④ 先做接口化（模块内 RPC），再做进程拆分
```

**路径**：

```
V1：模块化（代码分层，单库）
V2：抽公共服务（用户/订单/支付）
V3：拆库 + 分布式事务/最终一致
V4：治理（网关、注册中心、链路追踪）
```

**追问**："拆完变慢了怎么办？"
→ ① 减少跨服务调用（聚合层/BFF）；② 并行调用；③ 缓存；④ 数据冗余。

### 5.2 分库分表

**判断是否真的需要**：先索引优化、冷热分离、分区表，最后才分片。

**分片键选择**：

```
① 覆盖 80% 查询
② 分布均匀（避免热点）
③ 尽量单分片内完成事务
```

**扩容**：预分片（1024 片映射到物理库）> 一致性哈希 > 取模。

### 5.3 读写分离

**收益**：读扩展、隔离。
**代价**：延迟、一致性、运维复杂。

**适用**：读多写少（> 5:1），且能接受秒级延迟。

### 5.4 多机房 / 单元化

**核心**：**按用户分片，让同一用户的数据只在一个单元写**。

```
路由：uid → 单元（一致性哈希）
数据：单元内闭环，跨单元异步同步
切流：DNS/网关/客户端
```

**难点**：跨单元操作（转账、全局库存）、数据同步冲突、切流回滚。

### 5.5 重构 vs 重写

| 维度 | 重构 | 重写 |
| --- | --- | --- |
| 风险 | 低（渐进） | 高（一次性） |
| 周期 | 长 | 短（但可能延期） |
| 业务中断 | 无 | 有 |
| 适用 | 核心系统、有流量 | 边缘系统、无人用 |

**推荐**：**绞杀者模式**（Strangler Fig）——新功能写新系统，老功能逐步迁移，最后下线老系统。

**追问**："怎么保证重构不改变行为？"
→ ① 契约测试；② 双跑对比（影子流量）；③ 灰度切流；④ 可回滚。

## 六、故障排查场景（8 题）

> 所有排查题都用同一个骨架：**现象 → 影响 → 定位 → 根因 → 修复 → 预防**。
> 关键是**说清用什么工具、看什么指标、排除了什么**。

### 6.1 接口突然变慢

```
① 看监控：是全部慢还是部分慢？P99 还是平均？什么时候开始？
② 看链路：trace 找最慢的 span（DB/RPC/缓存/GC）
③ 看资源：CPU、内存、IO、连接池、线程池
④ 看依赖：下游 RT、错误率
⑤ 看变更：最近有没有发布/配置/DDL
```

**常见根因**：慢 SQL、缓存击穿、线程池打满、连接池耗尽、下游超时、Full GC、锁竞争。

### 6.2 CPU 100%

```bash
top -Hp <pid>                      # 找线程
printf "%x\n" <tid>                # 转 16 进制
jstack <pid> | grep -A 30 <hex>    # 定位栈
# 或
arthas> thread -n 3                # 最忙的 3 个线程
```

**根因**：死循环、频繁 GC、正则回溯、序列化、锁自旋、大量反射。

### 6.3 内存泄漏 / OOM

```bash
jstat -gcutil <pid> 1000 20        # 老年代持续上涨 + Full GC 频繁
jmap -histo:live <pid> | head -30  # 对象直方图
jmap -dump:format=b,file=/tmp/heap.hprof <pid>
# MAT：支配树找大对象
```

**常见根因**：缓存无界、ThreadLocal 未清理、监听器未注销、连接未关闭、大对象、类加载器泄漏。

### 6.4 连接池耗尽

**现象**：接口超时，日志里 `Connection is not available, request timed out`。

**排查**：

```
① 连接池指标：active / idle / waiting
② 谁占着连接：慢 SQL？事务太长？忘记关闭？
③ DB 侧：`SHOW PROCESSLIST` 看连接状态
```

**根因**：慢查询、长事务、连接泄漏、池太小、DB 连接数上限。

### 6.5 死锁

```bash
jstack <pid> | grep -A 20 "Found one Java-level deadlock"
# 或
SHOW ENGINE INNODB STATUS;   -- LATEST DETECTED DEADLOCK
```

**根因**：加锁顺序不一致、大事务、间隙锁冲突、并发更新多行。

### 6.6 消息重复消费

**定位**：看日志里同一 msgId 出现次数；查消费位点是否回退；看是否 Rebalance。

**根因**：ack 丢失、消费超时、Rebalance、重试。

**修复**：幂等（唯一索引 + 去重表）——**不要试图"消灭重复"**，要"容忍重复"。

### 6.7 数据不一致

**排查步骤**：

```
① 确定范围：哪些数据、多少条、什么时候开始
② 对比：缓存 vs DB、主 vs 从、A 库 vs B 库
③ 找写路径：有哪些地方会写这份数据？
④ 找时间点：对齐变更/发布/故障时间
⑤ 修复：先止血（停止错误写入），再修数据（脚本 + 校验）
```

**常见根因**：缓存删除失败、双写不一致、事务未提交、消息丢失、并发覆盖。

### 6.8 磁盘满

**排查**：

```bash
df -h
du -sh /* | sort -rh | head
# 找大文件
lsof +L1        # 已删除但仍被占用的文件
```

**常见根因**：日志未轮转、binlog/redo 未清理、临时文件、大 key、消息堆积。

**预防**：磁盘水位告警（80%）、日志轮转、定期清理。

## 七、业务设计场景（6 题）

### 7.1 优惠券系统

**核心**：**发放、核销、回滚、防超发、防重复**。

| 环节 | 设计 |
| --- | --- |
| 模板 | 类型（满减/折扣/立减）、门槛、有效期、库存 |
| 发放 | 领取（限次）+ 定向发放；Redis 扣库存 |
| 使用 | 校验（有效期/门槛/互斥）+ 锁定 + 核销 |
| 回滚 | 订单取消 → 退回（幂等） |
| 对账 | 发放数 = 使用数 + 剩余 + 过期 |

**追问**："优惠券叠加怎么算？"
→ 规则引擎（优先级、互斥组、最大优惠）；**金额计算用整数（分）**。

### 7.2 订单状态机

```
待支付 → 已支付 → 已发货 → 已完成
   ↓        ↓
 已取消   退款中 → 已退款
```

**关键**：

- 状态只能单向流转（用 `WHERE status = ?` CAS）。
- 每次流转记录流水（谁、何时、为什么）。
- 超时自动取消（延时消息 + 状态校验）。

### 7.3 会员积分

| 问题 | 方案 |
| --- | --- |
| 并发扣减 | 乐观锁/Redis |
| 流水可追溯 | 积分流水表（只增不改） |
| 过期 | 按批次记录，定时清理 |
| 对账 | 余额 = Σ 流水 |

### 7.4 消息推送

```
① 渠道：APNs/FCM/厂商通道/短信
② 去重：用户维度 + 消息维度
③ 频控：每日上限、免打扰
④ 触达率：失败重试 + 降级渠道
⑤ 合规：退订、隐私
```

### 7.5 搜索

**三层**：

```
① 召回：倒排（ES）+ 向量（语义）+ 规则
② 排序：粗排（规则/模型）→ 精排
③ 重排：多样性、去重、业务加权
```

**追问**："搜索和 RAG 的区别？"
→ 搜索返回**列表**，重召回与排序；RAG 返回**生成答案**，重上下文与引用。工程上有大量复用（倒排、向量、rerank）。

### 7.6 内容审核

```
接入 → 机审（规则 + 模型）→ 人审（抽检/可疑）→ 处置（通过/拒绝/限流）
```

**关键**：异步审核（先发后审 vs 先审后发）、误杀申诉、审核日志。

## 八、开放取舍题（5 题）

### 8.1 自研 vs 采购

| 判据 | 自研 | 采购 |
| --- | --- | --- |
| 是否是核心能力 | 是 | 否 |
| 规模是否够大 | 大（摊薄成本） | 小 |
| 团队是否有能力 | 有 | 无 |
| 是否需要深度定制 | 是 | 否 |
| 合规要求 | 高（必须可控） | 低 |

**话术**："非核心能力优先采购，把人力投在核心链路上；但**数据和流量的入口**要自己掌控。"

### 8.2 同步 vs 异步

| 判据 | 同步 | 异步 |
| --- | --- | --- |
| 用户是否需要立即结果 | 是 | 否 |
| 链路是否可容忍失败 | 否 | 是 |
| 并发量 | 低 | 高 |
| 一致性 | 强 | 最终 |

### 8.3 强一致 vs 最终一致

**决策链**：

```
问业务：不一致的后果是什么？
  ├─ 资损/合规 → 强一致（事务/锁/对账）
  ├─ 体验问题 → 最终一致（消息/补偿）
  └─ 无所谓 → 异步/离线
```

**关键**：**强一致有明确成本**（性能、可用性），要能说出代价。

### 8.4 成本优化

**四步**：

```
① 度量：钱花在哪（计算/存储/带宽/中间件）
② 找大头：80/20
③ 优化：降配、合并、冷热分离、弹性
④ 验证：稳定性不降级
```

**话术**："降本不能只砍资源，要同时重算容量基线和限流阈值，否则是把稳定性换成成本。"

### 8.5 技术债处理

**分级**：

| 级别 | 表现 | 处理 |
| --- | --- | --- |
| P0 | 随时可能引发故障 | 立即修 |
| P1 | 阻碍需求交付 | 排期修 |
| P2 | 可维护性差 | 顺手修 |
| P3 | 风格问题 | 不修 |

**话术**："我每个月留 20% 的迭代容量还技术债，并且**把技术债写进需求池**，否则永远排不上。"

## 九、答题模板与话术

### 9.1 系统设计模板（可直接背）

```
"我先确认几个约束：规模、一致性、延迟、预算。
 按【峰值 X QPS、数据 Y TB】估算，需要【Z 台/分片】。
 整体分四层：接入、应用、缓存、存储。
 主链路是……（画图）。
 这里有个关键决策：A 还是 B，我选 A，因为……，代价是……。
 失败模式我考虑三个：单点、热点、雪崩，分别用……兜底。
 V1 先……，V2 再……。"
```

### 9.2 方案选择模板

```
"先明确判据：一致性、性能、成本、团队熟悉度。
 A 的优势是……，劣势是……；B 反之。
 在这个场景下，因为【X 是硬约束】，所以选 A。
 如果【条件变化】，我会切到 B。"
```

### 9.3 故障排查模板

```
"现象是……，影响面是……。
 我会先看【监控指标】，再【链路追踪】，再【现场工具】。
 从目前信息看，可能排除……，重点怀疑……。
 如果是【原因 1】，处理是……；如果是【原因 2】，处理是……。
 止血之后再做根因修复和预防。"
```

### 9.4 不会的时候怎么说

```
"这块我没有直接做过，但我会这样推：
 先看【关键约束】是什么，再比较【两种方案】的代价。
 如果是我，我会先做一个最小验证，因为【最大不确定性】在这里。"
```

**不要编造具体数字**（"我们当时是 10 万 QPS"），可以说"按经验量级估算是……"。

## 十一、训练方法

### 11.1 三步训练法

```
① 拆解（看答案前）
   拿到题目，先写：澄清问题 3 个、估算 1 组、架构 1 张、取舍 2 个、失败 2 个
   限时 10 分钟，只写关键词

② 对照（看答案后）
   对比差距：少了哪个维度？哪个数字估错？哪个取舍没说代价？

③ 复述（第二天）
   不看笔记，3 分钟口述一遍，录音
   检查：是否有结构？是否有数字？是否说了"代价"？
```

### 11.2 每周一次模拟

```
找同事/朋友，随机抽 2 题
45 分钟：1 道设计 + 1 道故障
全程录音，回放时标记：
  - 哪里卡壳超过 10 秒
  - 哪里说了"应该可以"（没有依据）
  - 哪里没有说代价
```

### 11.3 场景题的"肌肉记忆"

| 反应 | 触发词 |
| --- | --- |
| 先问规模 | 任何设计题 |
| 先定一致性 | 任何涉及数据同步 |
| 先说失败模式 | 任何架构方案 |
| 先说代价 | 任何选型 |
| 先算数字 | 任何性能问题 |
| 先止血 | 任何故障 |

**这六个"先"，就是场景题的得分点。**
