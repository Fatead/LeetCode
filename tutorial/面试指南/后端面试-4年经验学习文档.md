## 零、先搞清楚：4 年经验到底在面什么

### 0.1 能力画像：面试官心里的"4 年"

| 维度 | 应届 / 1 年 | **4 年（你）** | 7 年+ |
| --- | --- | --- | --- |
| 编码 | 能写对 | **能写对 + 考虑边界 + 可维护** | 能设计框架 |
| 知识 | 知道是什么 | **知道为什么、什么时候不用** | 知道演进历史与权衡 |
| 排障 | 加日志 | **定位到根因（JVM/DB/中间件）** | 建监控体系 |
| 设计 | 完成需求 | **能对一个小系统做技术选型与容量估算** | 架构演进 |
| 协作 | 完成任务 | **能主导一个模块、带人、推动落地** | 跨团队 |

**核心结论**：4 年经验的淘汰线通常不是"不会某个知识点"，而是这三条：

1. **只会用，不懂原理** —— 追问两层就露馅（比如"Redis 为什么快"只会答"内存 + 单线程"）
2. **没有深度项目** —— 项目全是 CRUD，说不出任何技术难点与量化收益
3. **不会排查问题** —— 线上 CPU 100%、接口变慢、消息堆积，说不出排查路径

所以本文档每个知识点都按 **「原理 → 场景 → 追问 → 踩坑」** 四层组织，而不是罗列定义。

## 一、Java 基础与集合源码

> 这一章是"地基"。4 年经验不需要背 API，但**集合的扩容、哈希、并发安全**必须张口就来，因为它们是其他所有问题的前置知识。

### 1.1 String 为什么不可变？⭐

**面试官想听什么**：不是"final"，而是"不可变带来了什么"。

**回答骨架**：

1. **实现层面**：`String` 内部是 `private final char[] value`（JDK9 起是 `byte[] value` + `coder` 编码标记），且类被 `final` 修饰、不提供修改方法。
2. **三个收益**：
   - **字符串常量池可行**：同样的字面量可以共享同一份内存（`"a" + "b"` 与 `"ab"` 在编译期就合并）。
   - **hashCode 可缓存**：`String` 的 `hash` 字段首次计算后缓存，所以 `HashMap` 的 key 用 String 很快。
   - **线程安全 + 可安全作为参数传递**。
3. **代价**：每次拼接都产生新对象 → 循环内拼接要用 `StringBuilder`。

**深挖追问**：

| 追问 | 回答要点 |
| --- | --- |
| `String s = new String("a")` 创建几个对象？ | 常量池有 "a" 则 1 个（堆里的 String 对象）；没有则 2 个 |
| `intern()` 干什么？ | 把字符串放进常量池并返回池中引用，JDK7 后常量池在堆里 |
| `String s = "a" + "b"` 编译期还是运行期？ | 编译期优化成 `"ab"`；但含变量则是运行期 `StringBuilder` |
| `StringBuilder` 和 `StringBuffer` 区别？ | 前者非线程安全但快；后者方法加 `synchronized` |

**踩坑**：`StringBuilder` 默认容量 16，循环拼接大数据量时要预估容量，否则多次扩容（每次 `2 * old + 2`）。

### 1.2 HashMap 全解（最高频）⭐⭐⭐

这一题能追问 20 分钟，必须滚动式掌握。

#### （1）结构演进

| 版本 | 结构 | 问题 |
| --- | --- | --- |
| JDK7 | 数组 + 链表，**头插法** | 并发扩容会成环 → CPU 100% |
| JDK8 | 数组 + 链表 + **红黑树**，尾插法 | 并发下不再成环，但仍会丢数据 |

#### （2）关键参数（背这个表）

```java
static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;  // 16
static final int MAXIMUM_CAPACITY = 1 << 30;
static final float DEFAULT_LOAD_FACTOR = 0.75f;
static final int TREEIFY_THRESHOLD = 8;      // 链表 -> 红黑树
static final int UNTREEIFY_THRESHOLD = 6;    // 红黑树 -> 链表
static final int MIN_TREEIFY_CAPACITY = 64;  // 树化的前提：数组长度 >= 64
```

**为什么是 8？** 源码注释给了泊松分布：在理想哈希下，一个桶里链表长度到 8 的概率约 `0.00000006`，小于这个值几乎不可能，此时树化是为了**兜底**（防止恶意哈希攻击）；而**退化阈值取 6 而不是 8**，是为了在 7 附近留缓冲区，避免频繁树化/退化抖动。

**为什么负载因子是 0.75？** 空间与时间的折中：太小浪费空间，太大冲突多。0.75 是源码注释里按泊松分布算出的经验值。

#### （3）为什么容量必须是 2 的幂？

```java
// 定位桶的写法
(n - 1) & hash
```

- **当 n 是 2 的幂时**，`(n-1)` 的二进制是全 1（如 15 = 1111），`&` 运算等价于 `hash % n`，但位运算快得多。
- **且分布均匀**：`hash` 的低位会被完整保留。
- 如果 n 不是 2 的幂，`(n-1)` 会出现 0 位，某些桶永远用不到。

**所以**：`tableSizeFor()` 把你传入的容量向上取整到最近的 2 的幂（如传 10 → 16）。

**顺带**：`hash()` 做了扰动

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

因为桶定位只用低位，把高 16 位异或到低 16 位，**让高位也参与运算**，减少碰撞。

#### （4）put 流程（能口述）

```
put(key, value)
  → 若 table 为空则 resize() 初始化
  → (n-1)&hash 定位桶 i
     ├─ 桶为空：直接 new Node 放入
     ├─ 桶首节点 key 相同：覆盖 value
     ├─ 桶是红黑树：走 treeify 插入
     └─ 桶是链表：尾插遍历，找到相同 key 覆盖；否则插入尾部
                  → 链表长度 > 8 且 table.length >= 64 则树化，否则 resize
  → ++size > threshold 则 resize()
```

#### （5）resize 的巧妙之处

JDK8 扩容时**不需要重新计算 hash**。因为容量翻倍后，元素要么留在原位置 `i`，要么移动到 `i + oldCap`，只需看 `hash & oldCap` 是否为 0：

```java
if ((e.hash & oldCap) == 0) {
    // 留在低位链
} else {
    // 移到高位链：原位置 + oldCap
}
```

这个设计让扩容时的节点分配变成 O(1) 判断，且**保持了节点相对顺序**（不会像 JDK7 那样反转链表导致成环）。

#### （6）为什么线程不安全？

- JDK7：并发 `resize` 时头插法导致链表**成环**，`get` 死循环 → CPU 打满。
- JDK8：改尾插后不成环，但 `putVal` 中 `size++`、链表插入、resize 都无同步 → **数据覆盖**、size 不准。

> **面试话术**："JDK8 之后 HashMap 已经不会死循环了，但依然会丢数据，所以多线程必须用 ConcurrentHashMap。如果只读且初始化后不再修改，可以用 `Collections.unmodifiableMap`。"

#### （7）ConcurrentHashMap（JDK8）

| 维度 | JDK7 | JDK8 |
| --- | --- | --- |
| 并发粒度 | Segment（默认 16 段），**分段锁** | **单个桶头结点**，锁粒度更细 |
| 锁实现 | ReentrantLock | CAS + `synchronized` |
| 计数 | 遍历 Segment | `baseCount` + `CounterCell[]` 分段累加 |
| 扩容 | 段内扩容 | **多线程协助扩容**（`helpTransfer`） |

**关键点**：

- `put` 时桶为空 → CAS 放入；桶非空 → `synchronized` 锁住头结点。
- `size()` 不准确：类似 `LongAdder` 的分段计数，`sumCount()` 求和，并发下是**近似值**（`mappingCount()` 返回 long）。
- **不允许 null key / null value**（避免并发下 get 返回 null 的二义性）。

#### （8）追问清单

| 追问 | 一句话答案 |
| --- | --- |
| HashMap 为什么用红黑树不用 AVL？ | 红黑树插入/删除旋转次数少，查询略慢但综合更优 |
| 链表转树为什么还要求容量 ≥ 64？ | 小容量时冲突多是因为 table 太小，应优先扩容而不是树化 |
| HashMap 的 key 可以为 null 吗？ | 可以，hash 取 0，放在 0 号桶 |
| 遍历 HashMap 时删除会怎样？ | `fail-fast` 抛 `ConcurrentModificationException`，要用 `Iterator.remove()` |
| 如何让 HashMap 线程安全？ | `Collections.synchronizedMap`（全表锁）、`ConcurrentHashMap`（推荐）、`Hashtable`（已淘汰） |

### 1.3 ArrayList / LinkedList / CopyOnWriteArrayList ⭐⭐

| 维度 | ArrayList | LinkedList | CopyOnWriteArrayList |
| --- | --- | --- | --- |
| 底层 | 动态数组 | 双向链表 | 数组（写时复制） |
| 随机访问 | `O(1)` | `O(n)` | `O(1)` |
| 头部插入 | `O(n)` | `O(1)` | `O(n)`（复制整个数组） |
| 扩容 | **1.5 倍**（`old + (old >> 1)`） | 无 | 每次写都复制 |
| 线程安全 | 否 | 否 | 是（写加锁、读无锁） |
| 适用 | 读多、尾部增删 | 头尾增删多 | **读多写极少**（如白名单、监听器列表） |

**ArrayList 扩容细节**：

- 默认容量 10（**首次 add 时才分配**，不是 `new` 时）。
- 扩容：`newCapacity = oldCapacity + (oldCapacity >> 1)`，即 1.5 倍。
- 用 `ensureCapacity(n)` 预分配可避免多次复制。

**为什么 ArrayList 不是 2 倍？** 1.5 倍在空间浪费和复制次数之间更平衡，且旧数组更容易被后续分配复用。

**CopyOnWrite 的坑**：写操作要复制整个数组（内存峰值翻倍），且**只能保证最终一致性**，不适合实时性要求高的场景。

### 1.4 泛型与类型擦除 ⭐

**回答骨架**：

1. Java 泛型是**编译期**特性，编译后泛型参数被擦除为 `Object`（或上界），并插入强制类型转换。
2. 所以：`List<String>` 和 `List<Integer>` 在运行时是同一个类；不能 `new T[]`；不能对泛型做 `instanceof`。
3. **桥接方法**：子类重写泛型父类方法时，编译器会生成桥接方法保证多态。
4. **为什么这样设计**：为了兼容 JDK5 之前的代码（二进制兼容）。

**追问**：
- 如何绕过擦除拿到泛型？→ 通过**匿名子类**（`new TypeReference<List<User>>(){}`）在运行时保留签名，Jackson、MyBatis-Plus 都这么干。
- `List<? extends T>` 和 `List<? super T>` 的区别？→ PECS 原则：**生产者用 extends，消费者用 super**。

## 二、并发编程

> **4 年经验里最容易拉开差距的一章。** 面试官不满足于"线程池有 7 个参数"，会追问"你线上线程池怎么配的、出过什么问题、怎么监控"。

### 2.1 Java 内存模型（JMM）⭐

**一句话**：JMM 规定了**多线程之间如何通过内存通信**，核心是三条性质 + happens-before 规则。

```
线程 A 工作内存          主内存          线程 B 工作内存
  [拷贝]  ←────────→  [共享变量]  ←────────→  [拷贝]
```

- **原子性**：一个操作不可分割（`i++` 不是原子操作，要 `AtomicInteger`）。
- **可见性**：一个线程的修改何时对另一个线程可见（`volatile`、`synchronized`、`final`）。
- **有序性**：禁止指令重排影响结果（`volatile`、`synchronized`）。

**happens-before 八条**（记熟的 4 条即可）：

1. 程序次序：单线程内前面的代码先于后面的。
2. 监视器锁：解锁先于后续加锁。
3. `volatile`：写先于后续读。
4. 线程启动/终止：`start()` 先于线程内任何操作；线程内操作先于 `join()` 返回。
5. 传递性：A hb B，B hb C ⇒ A hb C。

> **为什么需要 JMM**：现代 CPU 有缓存和指令重排，不加以约束会导致程序结果不可预期。JMM 是"给程序员的承诺"。

### 2.2 volatile 到底做了什么？⭐⭐

**两个语义**：

1. **可见性**：写操作立即刷新到主内存，读操作直接从主内存读（底层是 `lock` 前缀指令 / 内存屏障，使其他 CPU 的缓存行失效）。
2. **禁止重排**：在写前后插入 `StoreStore` + `StoreLoad` 屏障，读前后插入 `LoadLoad` + `LoadStore` 屏障。

**关键结论**：

- `volatile` **不保证原子性**（`i++` 依然不安全，要 `AtomicInteger` 或加锁）。
- 典型正确用法：**状态标志位**、**双重检查锁单例的实例引用**。

```java
// DCL 单例：instance 必须 volatile
private static volatile Singleton instance;

public static Singleton getInstance() {
    if (instance == null) {                      // 第一次检查（避免每次都加锁）
        synchronized (Singleton.class) {
            if (instance == null) {              // 第二次检查
                instance = new Singleton();      // 这行不是原子操作！
            }
        }
    }
    return instance;
}
```

**为什么必须 volatile？** `instance = new Singleton()` 分三步：①分配内存 ②初始化对象 ③引用指向内存。若 ②③ 重排，另一个线程会看到**非 null 但未初始化完成**的对象。`volatile` 禁止了这个重排。

### 2.3 synchronized 原理与锁升级 ⭐⭐⭐

#### （1）底层实现

- **同步代码块**：`monitorenter` / `monitorexit` 字节码指令。
- **同步方法**：方法访问标志 `ACC_SYNCHRONIZED`。
- **对象头 Mark Word** 记录锁状态；重量级锁关联 `ObjectMonitor`（含 `entryList`、`waitSet`、`owner`、`recursions`）。

#### （2）锁升级过程（重点）

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁（不可逆）
```

| 阶段 | 触发条件 | 实现 | 开销 |
| --- | --- | --- | --- |
| 偏向锁 | 只有一个线程反复进入 | Mark Word 记录线程 ID | 几乎无（CAS 一次） |
| 轻量级锁 | 有第二个线程竞争 | 栈帧中 Lock Record + CAS 自旋 | 自旋消耗 CPU |
| 重量级锁 | 自旋失败 / 竞争激烈 | 操作系统互斥量，线程阻塞 | 用户态↔内核态切换 |

> ⚠️ **注意**：JDK15（JEP 374）起偏向锁默认关闭并标记废弃，后续版本已移除。面试时说明这一点是加分项："偏向锁因为撤销成本高、收益在高版本已不明显，被 JEP 374 废弃了。"

**为什么要有锁升级？** 大多数场景锁竞争很低，直接上重量级锁代价太大；分级让低竞争场景几乎无开销。

#### （3）synchronized vs ReentrantLock

| 维度 | synchronized | ReentrantLock |
| --- | --- | --- |
| 实现 | JVM 层面（monitor） | JDK 层面（AQS） |
| 可中断 | 否 | **是**（`lockInterruptibly`） |
| 超时获取 | 否 | **是**（`tryLock(timeout)`） |
| 公平锁 | 否 | **可选** |
| 条件队列 | 一个（wait/notify） | **多个**（`newCondition()`） |
| 自动释放 | 是（异常也释放） | 否，必须 `finally { unlock(); }` |

**选择建议**：无特殊需求优先 `synchronized`（JVM 持续优化、代码简单）；需要超时/中断/多条件/公平时用 `ReentrantLock`。

### 2.4 AQS（AbstractQueuedSynchronizer）⭐⭐

**一句话**：AQS 是一个**用 `volatile int state` + **CLH 双向队列**实现的同步器框架，`ReentrantLock`、`Semaphore`、`CountDownLatch`、`ReadWriteLock` 都基于它。

**三大核心**：

```java
volatile int state;                 // 同步状态（锁重入次数 / 许可数 / 计数）
Node head, tail;                    // CLH 变体双向队列
Thread exclusiveOwnerThread;        // 独占模式下的持有者
```

**工作流程**：

```
lock() → tryAcquire() 尝试 CAS 改 state
   ├─ 成功：设置 owner，返回
   └─ 失败：包装成 Node 入队，park() 挂起
unlock() → tryRelease() 改 state
   └─ 成功后 unpark() 唤醒后继节点
```

**独占 vs 共享**：

- 独占：`ReentrantLock`，`tryAcquire` 返回 boolean。
- 共享：`Semaphore`、`CountDownLatch`，`tryAcquireShared` 返回值 `>= 0` 表示成功。

**公平 vs 非公平**：

- 非公平：`lock()` 直接 CAS 抢，抢不到才排队 → **吞吐高**（默认）。
- 公平：先检查队列是否有前驱 → `hasQueuedPredecessors()`，有则老实排队 → 避免饥饿但吞吐低。

**Condition 原理**：每个 `Condition` 有一个条件队列，`await()` 把节点从同步队列移到条件队列并释放锁，`signal()` 再移回同步队列。

**高频追问**："AQS 为什么用双向队列？"→ 需要从尾部入队、从头部唤醒，且取消节点时要能 `prev` 回溯（单向做不到 O(1) 删除）。

### 2.5 ThreadPoolExecutor ⭐⭐⭐

#### （1）七个参数（必须按顺序说）

```java
new ThreadPoolExecutor(
    corePoolSize,        // 核心线程数
    maximumPoolSize,     // 最大线程数
    keepAliveTime,       // 非核心线程空闲存活时间
    unit,                // 时间单位
    workQueue,           // 任务队列
    threadFactory,       // 线程工厂（一定要自定义名字！）
    handler              // 拒绝策略
);
```

#### （2）执行流程（背下来）

```
submit(task)
  → 若 当前线程数 < corePoolSize        → 新建核心线程执行
  → 否则 尝试入 workQueue
       ├─ 入队成功 → 空闲线程来取
       └─ 入队失败（队列满）
            → 若 当前线程数 < maximumPoolSize → 新建非核心线程
            → 否则 执行拒绝策略
```

> **反直觉点**：**先入队，队列满了才扩线程**。所以用无界队列（`LinkedBlockingQueue` 默认容量 `Integer.MAX_VALUE`）时 `maximumPoolSize` 永远不生效，这也是 `Executors.newFixedThreadPool` 会 OOM 的根因。

#### （3）四种拒绝策略

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 需要感知失败 |
| `CallerRunsPolicy` | 由提交任务的线程自己执行 | **降级、天然限速**（推荐用于非核心业务） |
| `DiscardPolicy` | 静默丢弃 | 可丢的任务（埋点日志） |
| `DiscardOldestPolicy` | 丢队首最老的，再提交 | 时效性强的任务 |

#### （4）线程数怎么配？

| 任务类型 | 公式 | 示例 |
| --- | --- | --- |
| CPU 密集 | `N + 1` | 计算、序列化 |
| IO 密集 | `N * (1 + 等待时间 / 计算时间)` 或 `2N ~ 4N` | 调 RPC、查 DB |
| 混合 | 拆成两个池分别处理 | — |

> `N` = CPU 核数（`Runtime.getRuntime().availableProcessors()`）。
> **面试加分**：说明"公式只是起点，最终要靠压测 + 监控（活跃线程数、队列长度、拒绝次数）调优"。

#### （5）为什么不推荐 `Executors`？

| 工厂方法 | 隐患 |
| --- | --- |
| `newFixedThreadPool` | 无界队列 → 任务堆积 → OOM |
| `newSingleThreadExecutor` | 同上 |
| `newCachedThreadPool` | 最大线程 `Integer.MAX_VALUE` → 创建过多线程 → OOM |
| `newScheduledThreadPool` | 无界 `DelayedWorkQueue` → OOM |

**规范**：手动 `new ThreadPoolExecutor`，指定**有界队列** + **自定义线程名** + **明确拒绝策略**。

#### （6）线程池的五个状态

```
RUNNING      → 接受新任务 + 处理队列
SHUTDOWN     → 不接受新任务，处理完队列（shutdown()）
STOP         → 不接受 + 不处理队列 + 中断进行中的（shutdownNow()）
TIDYING      → 所有任务终止，执行 terminated()
TERMINATED   → terminated() 执行完毕
```

`ctl` 是 `AtomicInteger`：**高 3 位存状态，低 29 位存线程数**（所以最大线程数约 5 亿）。

### 2.6 ThreadLocal ⭐⭐

**结构**：`Thread` 内部有 `ThreadLocalMap`，key 是 **`ThreadLocal` 的弱引用**，value 是强引用。

```
Thread → ThreadLocalMap → Entry[] { WeakReference<ThreadLocal>, Object value }
```

**内存泄漏原因**：

1. key 是弱引用，GC 后 key 变 null，但 **value 仍被 Entry 强引用**（Entry 继承 WeakReference，value 是普通字段）。
2. 如果线程一直活着（**线程池复用**），这些 value 就永远回收不了。
3. 虽然 `get/set` 时会顺带清理 key 为 null 的 Entry，但**不保证一定触发**。

**正确用法**：`try { ... } finally { threadLocal.remove(); }`

**追问**：

| 追问 | 答案 |
| --- | --- |
| 为什么 key 用弱引用？ | 让 ThreadLocal 对象本身能被回收（否则即使外部不再使用也泄漏） |
| InheritableThreadLocal 的坑？ | 线程池中线程复用，父子线程传递会失效；要用 `TransmittableThreadLocal`（TTL） |
| 实际用途 | 用户上下文、链路 traceId、`SimpleDateFormat` 线程隔离、事务连接绑定 |

### 2.7 CAS 与原子类 ⭐

**原理**：`Unsafe.compareAndSwapInt(obj, offset, expect, update)` 底层是 CPU 的 `cmpxchg` 指令（加 `lock` 前缀保证原子）。

**三个问题**：

| 问题 | 说明 | 解决 |
| --- | --- | --- |
| ABA | A→B→A，CAS 认为没变 | `AtomicStampedReference`（加版本号） |
| 自旋开销 | 高竞争下大量空转 | `LongAdder` 分段累加 / 改锁 |
| 只能保证单个变量 | 多个变量无法原子 | `AtomicReference` 封装对象 / 锁 |

**LongAdder 为什么比 AtomicLong 快？** 高并发下 `AtomicLong` 所有线程 CAS 同一个 value，冲突严重；`LongAdder` 用 `Cell[]` 数组**分段累加**，最后 `sum()` 汇总，空间换时间。

### 2.8 并发容器与阻塞队列 ⭐

| 容器 | 特点 | 场景 |
| --- | --- | --- |
| `ConcurrentHashMap` | 分段/CAS + 桶锁 | 高并发 Map |
| `CopyOnWriteArrayList` | 写复制，读无锁 | 读多写极少 |
| `ConcurrentLinkedQueue` | CAS 无锁队列 | 高并发队列 |
| `ArrayBlockingQueue` | **有界**，数组，单锁双条件 | 线程池队列（推荐） |
| `LinkedBlockingQueue` | 可选有界（默认无界！） | 注意指定容量 |
| `SynchronousQueue` | 不存储，直接移交 | `newCachedThreadPool` |
| `PriorityBlockingQueue` | 无界优先级堆 | 优先级任务 |
| `DelayQueue` | 延迟到期才能取 | 订单超时、定时任务 |

**阻塞队列的四组方法**：

| | 抛异常 | 返回特殊值 | 阻塞 | 超时 |
| --- | --- | --- | --- | --- |
| 插入 | `add` | `offer` | `put` | `offer(e, t, u)` |
| 取出 | `remove` | `poll` | `take` | `poll(t, u)` |

### 2.9 死锁与排查 ⭐

**四个必要条件**：互斥、持有并等待、不可剥夺、循环等待。

**预防**：统一加锁顺序、`tryLock` 超时、减少锁粒度、避免嵌套锁。

**排查命令**：

```bash

# 或
jcmd <pid> Thread.print
```

输出会直接给出 `waiting to lock` / `locked` 的持有关系。

### 2.10 CompletableFuture（4 年经验加分项）

```java
CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> userService.get(id), pool);
CompletableFuture<Order> orderFuture = CompletableFuture.supplyAsync(() -> orderService.list(id), pool);

// 并行聚合 + 异常兜底 + 超时
User user = userFuture
    .thenCombine(orderFuture, (u, o) -> { u.setOrders(o); return u; })
    .exceptionally(ex -> User.empty())          // 兜底
    .get(500, TimeUnit.MILLISECONDS);           // 超时控制
```

**坑**：

- 默认用 `ForkJoinPool.commonPool()`，**IO 任务一定要传自定义线程池**，否则拖垮整个 JVM。
- `thenApply` 和 `thenCompose` 区别：前者是同步映射（`Function`），后者是扁平化（返回 `CompletableFuture`，类似 `flatMap`）。
- `get()` 会抛受检异常，`join()` 抛非受检。

## 三、JVM

> 4 年经验对 JVM 的要求：**不用会调优，但必须会看**。线上 CPU 飙高、内存溢出、接口变慢，你要能独立定位。

### 3.1 运行时数据区 ⭐⭐

| 区域 | 线程私有 | 存储内容 | 异常 |
| --- | --- | --- | --- |
| 程序计数器 | ✅ | 当前字节码行号 | 无（唯一不 OOM 的区域） |
| 虚拟机栈 | ✅ | 栈帧（局部变量表、操作数栈、动态链接、返回地址） | `StackOverflowError` / `OOM` |
| 本地方法栈 | ✅ | native 方法 | 同上 |
| 堆 | ❌ | 对象实例、数组 | `OutOfMemoryError: Java heap space` |
| 方法区（元空间） | ❌ | 类元信息、常量、静态变量、JIT 代码 | `OOM: Metaspace` |
| 直接内存 | ❌ | NIO `DirectByteBuffer` | `OOM: Direct buffer memory` |

**关键演进**：JDK8 用**元空间（本地内存）**替代永久代，解决了 `PermGen OOM` 和字符串常量池的回收问题。字符串常量池在 JDK7 已移到堆中。

**常见参数**：

```bash
-Xms4g -Xmx4g                 # 堆初始/最大（生产建议相等，避免动态扩容抖动）
-Xmn2g                        # 新生代大小（G1 不推荐显式设置）
-Xss512k                      # 单线程栈大小
-XX:MetaspaceSize=256m -XX:MaxMetaspaceSize=512m
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
```

### 3.2 对象的内存布局 ⭐

```
| Mark Word (8B) | Klass Pointer (4B，压缩后) | 实例数据 | 对齐填充 |
```

- **Mark Word**：存 hashcode、GC 分代年龄（4 bit，最大 15）、锁标志位、偏向线程 ID。这也是锁升级的载体。
- **Klass Pointer**：指向方法区的类元数据。
- **指针压缩**：`-XX:+UseCompressedOops`（默认开），引用从 8B 压到 4B，但**堆超过 32GB 就失效**（因为 4B 要寻址 32GB 需要 8 倍对齐）。这也是"堆不要超过 32G"的由来。

**对象创建过程**：类加载检查 → 分配内存（指针碰撞 / 空闲列表，取决于是否规整）→ 零值初始化 → 设置对象头 → 执行 `<init>`。

**分配优化**：

- **TLAB**（Thread Local Allocation Buffer）：每个线程在 Eden 预分配一小块，避免指针碰撞的同步开销。
- **逃逸分析**：对象没逃出方法 → **栈上分配** / **标量替换**，减少 GC 压力。

### 3.3 垃圾回收 ⭐⭐⭐

#### （1）怎么判断对象已死？

**可达性分析**：从 **GC Roots** 出发不可达即可回收。

**GC Roots 包括**：

- 虚拟机栈中引用的对象
- 方法区中**静态属性**引用的对象
- 方法区中**常量**引用的对象
- 本地方法栈 JNI 引用的对象
- 活跃线程
- 同步锁 `synchronized` 持有的对象

> **为什么不用引用计数？** 无法解决循环引用。

#### （2）分代模型

```
堆
├── 新生代 (Young)  1/3
│   ├── Eden        8
│   └── Survivor S0/S1  1:1（合计 1/10）
└── 老年代 (Old)    2/3
```

**为什么 8:1:1？** 新生代对象绝大多数朝生夕死，只需 10% 的空间做复制即可完成回收，浪费最小。

**对象晋升老年代的四种情况**：

1. 年龄达到 `MaxTenuringThreshold`（默认 15，Mark Word 中 4 bit 上限）。
2. **动态年龄判定**：Survivor 中同龄对象总和 > 一半，则 ≥ 该年龄的直接晋升。
3. **大对象**直接进老年代（`-XX:PretenureSizeThreshold`）。
4. **Survivor 放不下**，通过分配担保进入老年代。

#### （3）三种基础算法

| 算法 | 做法 | 优点 | 缺点 | 用在哪 |
| --- | --- | --- | --- | --- |
| 标记-清除 | 标记后直接清除 | 简单 | **碎片化** | CMS |
| 标记-复制 | 存活对象复制到另一半 | 无碎片、快 | 浪费一半空间 | 新生代 |
| 标记-整理 | 标记后向一端移动 | 无碎片 | 移动成本高 | 老年代 |

#### （4）收集器对比（重点）

| 收集器 | 分代 | 算法 | 特点 | 适用 |
| --- | --- | --- | --- | --- |
| Serial | 新生代 | 复制 | 单线程，STW | 客户端/小内存 |
| ParNew | 新生代 | 复制 | Serial 多线程版 | 配合 CMS |
| Parallel Scavenge | 新生代 | 复制 | **吞吐量优先** | 后台批处理 |
| Serial Old | 老年代 | 标记-整理 | 单线程 | — |
| Parallel Old | 老年代 | 标记-整理 | 吞吐优先 | 配合 PS |
| **CMS** | 老年代 | 标记-清除 | **低延迟**，4 阶段 | JDK8 及之前 |
| **G1** | 不分代（逻辑分代） | 复制+整理 | **可预测停顿**，Region | JDK9+ 默认 |
| ZGC | — | 染色指针+读屏障 | **亚毫秒停顿**，TB 级堆 | JDK15+ 生产可用 |
| Shenandoah | — | Brooks 指针 | 低延迟 | OpenJDK |

**CMS 的四个阶段**（标记-清除，只有 ①③ 需要 STW）：

```
① 初始标记 (STW)   标记 GC Roots 直接关联的对象，很快
② 并发标记          与用户线程并行，遍历整个对象图，最慢
③ 重新标记 (STW)    修正并发期间变动的对象（增量更新）
④ 并发清除          与用户线程并行
```

**CMS 的三大问题**：

- **CPU 敏感**：并发阶段占用线程。
- **浮动垃圾**：并发清除期间产生的新垃圾只能下次回收。
- **内存碎片**：标记-清除导致碎片，大对象分配失败触发 **Full GC（Serial Old 兜底）**，停顿很长。

**G1 的核心设计**：

- 堆划分成约 **2048 个 Region**（每个 1~32MB），逻辑上仍有 Eden/Survivor/Old。
- **Humongous** 区存大对象（> 50% Region）。
- **RSet（Remembered Set）** 记录跨 Region 引用，避免全堆扫描。
- **SATB**（Snapshot At The Beginning）保证并发标记正确性。
- **Mixed GC**：根据 `-XX:MaxGCPauseMillis`（默认 200ms）预测停顿，优先回收**垃圾最多**的 Region（Garbage First 的由来）。

### 3.4 类加载机制 ⭐

**五个阶段**：加载 → 验证 → 准备 → 解析 → 初始化。

- **准备**：为静态变量分配内存并设**零值**（`static int a = 10` 在此阶段 `a = 0`，赋值在 `<clinit>`）。
- **解析**：符号引用 → 直接引用。
- **初始化**：执行 `<clinit>`，即静态变量赋值 + 静态代码块（**父类先于子类**）。

**什么时候触发初始化？**（主动引用）

1. `new`、读写静态字段、调用静态方法。
2. 反射 `Class.forName`。
3. 初始化子类时先初始化父类。
4. 虚拟机启动时的主类。
5. `MethodHandle` 解析结果。

**双亲委派**：

```
Bootstrap ClassLoader（C++ 实现，加载 rt.jar / java.base）
        ↑
Extension / Platform ClassLoader
        ↑
Application ClassLoader（加载 classpath）
        ↑
自定义 ClassLoader
```

**流程**：收到加载请求 → 先委派父加载器 → 父加载器无法完成才自己加载。

**好处**：① 避免类重复加载；② 保证核心类安全（你写的 `java.lang.String` 永远不会被加载）。

**打破双亲委派的三个场景**：

| 场景 | 怎么打破 | 原因 |
| --- | --- | --- |
| **SPI**（JDBC） | 线程上下文类加载器 `Thread.currentThread().getContextClassLoader()` | 核心类要加载第三方实现（`DriverManager` 加载 MySQL Driver） |
| **Tomcat** | 每个 webapp 一个 `WebAppClassLoader`，**先自己加载再委派** | 不同应用需要隔离自己的类版本 |
| **热部署 / OSGi** | 自定义 ClassLoader 动态替换 | 模块化与热更新 |

## 四、MySQL

> MySQL 是后端面试的**第二大块**。核心集中在：**索引为什么用 B+ 树、为什么索引会失效、事务与 MVCC、锁、慢 SQL 优化**。

### 4.1 索引：为什么是 B+ 树 ⭐⭐⭐

| 结构 | 为什么不用 |
| --- | --- |
| 二叉搜索树 | 可能退化成链表 |
| AVL / 红黑树 | 树太高，磁盘 IO 次数多（每层一次 IO） |
| B 树 | **非叶子节点也存数据**，单页能放的索引键少 → 树更高；且范围查询要中序遍历，跨层跳跃 |
| **B+ 树** | ✅ 非叶子只存键 → 单页（16KB）能放上千个键 → 3~4 层可存千万级；叶子节点用**双向链表**串联 → 范围查询和排序极快；数据都在叶子 → 查询稳定 |

**估算**：假设主键 bigint 8B + 指针 6B = 14B，一页 16KB 可放约 1170 个键；叶子页每行 1KB 可放 16 条。

- 两层：`1170 * 16 ≈ 1.8 万`
- 三层：`1170 * 1170 * 16 ≈ 2190 万`

**所以"千万级表 3 层 B+ 树"是有依据的。**

#### 聚簇索引 vs 二级索引

| 类型 | 叶子存什么 | 说明 |
| --- | --- | --- |
| **聚簇索引**（主键） | **整行数据** | 一张表只有一个；InnoDB 必须有主键 |
| **二级索引**（普通索引） | **主键值** | 查到主键后要**回表** |

**回表**：二级索引找到主键 → 再走聚簇索引查整行。**多一次 B+ 树查找**。

**覆盖索引**：查询的列都在索引里 → **不用回表**。这是最重要的优化手段之一。

```sql
-- 有索引 idx_name_age(name, age)
SELECT name, age FROM user WHERE name = 'tom';   -- 覆盖索引，Extra: Using index
SELECT * FROM user WHERE name = 'tom';           -- 需要回表
```

**为什么推荐自增主键？**

- 自增 → 顺序插入 → 只在最右侧页分裂，**页利用率高**。
- UUID 随机 → 随机插入 → 频繁页分裂 + 页碎片 + 索引更大。

**没有主键怎么办？** InnoDB 会选第一个非空唯一索引，都没有则隐式创建 6 字节的 `row_id`。

### 4.2 索引失效的场景（背这张表）⭐⭐⭐

| 场景 | 例子 | 原因 |
| --- | --- | --- |
| **左模糊** | `LIKE '%abc'` | 无法利用 B+ 树有序性 |
| **列上做函数/运算** | `WHERE YEAR(create_time) = 2024`、`WHERE id + 1 = 5` | 索引存的是列原值 |
| **隐式类型转换** | `WHERE phone = 13800000000`（phone 是 varchar） | 相当于对列做 `CAST` |
| **OR 连接非索引列** | `WHERE a = 1 OR b = 2`（b 无索引） | 只能全表扫 |
| **不满足最左前缀** | 索引 `(a,b,c)`，`WHERE b = 1` | B+ 树按 a 排序 |
| **范围查询后的列失效** | `WHERE a > 1 AND b = 2` | a 是范围，b 无法继续用索引（有 ICP 可部分缓解） |
| `!=` / `NOT IN` | `WHERE status != 1` | 优化器认为全表扫更快（低区分度时） |
| `IS NULL`（部分情况） | — | 取决于列是否 NOT NULL 和数据分布 |
| 联合索引中间列缺失 | `(a,b,c)` 上 `WHERE a = 1 AND c = 3` | c 用不上（但 a 能用） |

> **例外**：MySQL 8.0 支持**函数索引**（`CREATE INDEX idx ON t ((YEAR(create_time)))`），可以解决函数失效，但要注意维护成本。

**最左前缀的本质**：联合索引 `(a,b,c)` 是先按 a 排序、a 相同再按 b、再按 c。你跳过 a 直接查 b，B+ 树里的 b 是**全局乱序**的。

**但注意**：`WHERE a = 1 AND c = 3` 中，a 能用索引，c 用不上；而 `WHERE a = 1 AND b = 2 AND c = 3` 可以用满。

### 4.3 索引下推（ICP）⭐

MySQL 5.6+ 引入。没有 ICP 时，存储引擎按索引找到记录就回表，再由 Server 层过滤；有 ICP 后，**能在索引上判断的条件下推到存储引擎层过滤**，减少回表次数。

```sql
-- 索引 idx_name_age(name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
```

- 无 ICP：按 name 前缀找到一批主键 → 全部回表 → Server 层过滤 age。
- 有 ICP：在索引里直接用 age 过滤 → 只回表符合条件的。

`EXPLAIN` 的 `Extra` 会显示 `Using index condition`。

### 4.4 事务与隔离级别 ⭐⭐⭐

**ACID**：

| 特性 | 靠什么保证 |
| --- | --- |
| 原子性 A | **undo log**（回滚） |
| 一致性 C | 由 A + I + D 共同保证（业务层也有责任） |
| 隔离性 I | **锁 + MVCC** |
| 持久性 D | **redo log**（WAL） |

**四种隔离级别与问题**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | ✅ 会 | ✅ 会 | ✅ 会 |
| READ COMMITTED | ❌ | ✅ 会 | ✅ 会 |
| **REPEATABLE READ（MySQL 默认）** | ❌ | ❌ | ⚠️ 部分解决（快照读靠 MVCC，当前读靠间隙锁） |
| SERIALIZABLE | ❌ | ❌ | ❌ |

> **MySQL 的 RR 为什么能"基本"解决幻读？** 因为 ① 快照读用 MVCC（读的是事务开始时的快照）；② 当前读用**临键锁（Next-Key Lock）**锁住间隙，阻止插入。但**如果事务 A 先快照读、事务 B 插入并提交、A 再当前读（`for update`）**，就会出现幻读——这是 RR 下仍存在幻读的经典场景。

**隔离级别与 MVCC 的关系**：

- **RC**：每次 `SELECT` 都生成新的 ReadView → 能看到别人已提交的修改 → 不可重复读。
- **RR**：只在**第一次** `SELECT` 时生成 ReadView，之后复用 → 可重复读。

### 4.5 MVCC 原理 ⭐⭐⭐

**三个组件**：

1. **隐藏字段**：`DB_TRX_ID`（最后修改的事务 ID）、`DB_ROLL_PTR`（指向 undo log 的回滚指针）。
2. **undo log 版本链**：每次修改都把旧值写入 undo log，通过 `DB_ROLL_PTR` 串成链表。
3. **ReadView**：
   - `m_ids`：生成时活跃（未提交）的事务 ID 列表
   - `min_trx_id`：`m_ids` 最小值
   - `max_trx_id`：生成时下一个要分配的事务 ID
   - `creator_trx_id`：当前事务 ID

**可见性判断（顺着版本链找）**：

```
对每个版本的 trx_id：
  ① trx_id == creator_trx_id            → 可见（自己改的）
  ② trx_id <  min_trx_id                → 可见（事务已提交）
  ③ trx_id >= max_trx_id                → 不可见（ReadView 之后才开启）
  ④ min_trx_id <= trx_id < max_trx_id   → 看是否在 m_ids 中
       在 m_ids  → 不可见（还活跃）
       不在      → 可见（已提交）
不可见则沿 DB_ROLL_PTR 找上一个版本，直到找到可见版本或链表结束
```

**快照读 vs 当前读**：

| 类型 | 语句 | 读什么 |
| --- | --- | --- |
| 快照读 | 普通 `SELECT` | ReadView 对应的历史版本（MVCC） |
| 当前读 | `SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE` / `UPDATE` / `DELETE` / `INSERT` | 最新版本，**加锁** |

### 4.6 锁 ⭐⭐

**按粒度**：表锁、行锁、意向锁（IS/IX，表级，用于快速判断表里是否有行锁）。

**行锁的三种形态**（InnoDB，加在索引上）：

| 锁 | 锁什么 | 作用 |
| --- | --- | --- |
| **记录锁** Record Lock | 单条索引记录 | 防止修改该记录 |
| **间隙锁** Gap Lock | 索引记录之间的**开区间** | **阻止插入**，防幻读（仅 RR 有） |
| **临键锁** Next-Key Lock | 记录 + 之前的间隙（左开右闭） | RR 的默认行锁，记录锁 + 间隙锁 |

**插入意向锁**：插入前先加，表明"我要在这个间隙插入"，与间隙锁互斥。

**关键结论**：

- **行锁加在索引上**。如果 `WHERE` 条件没走索引，会退化成**表锁**（锁住所有记录 + 间隙）。
- 唯一索引等值查询命中时，临键锁退化为**记录锁**（因为唯一，不需要锁间隙）。
- 唯一索引等值查询**未命中**时，退化为**间隙锁**。

**死锁**：

```sql
-- 事务 A
UPDATE t SET x = 1 WHERE id = 1;   -- 持有 id=1 的锁
UPDATE t SET x = 1 WHERE id = 2;   -- 等待 id=2
-- 事务 B（并发）
UPDATE t SET x = 1 WHERE id = 2;   -- 持有 id=2
UPDATE t SET x = 1 WHERE id = 1;   -- 等待 id=1 → 死锁
```

**排查**：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`；`innodb_deadlock_detect` 默认开启，会**主动回滚代价小的事务**（`innodb_lock_wait_timeout` 默认 50s）。

**预防**：按固定顺序访问、缩短事务、降低隔离级别到 RC（很多互联网公司这么做，代价是接受部分幻读）、拆分大事务。

### 4.7 三大日志 ⭐⭐⭐

| 日志 | 层级 | 类型 | 作用 | 写方式 |
| --- | --- | --- | --- | --- |
| **redo log** | InnoDB | **物理**日志（页的修改） | **崩溃恢复**（持久性） | 循环写，固定大小 |
| **undo log** | InnoDB | **逻辑**日志（反向 SQL） | 回滚 + **MVCC** | 随机写 |
| **binlog** | Server | **逻辑**日志（SQL/行变更） | **主从复制 + 数据恢复** | 追加写 |

**WAL（Write-Ahead Logging）**：修改数据时先写 redo log（顺序写、快），再异步刷脏页（随机写变顺序写），是 InnoDB 高性能的关键。

**两阶段提交**（保证 redo log 与 binlog 一致）：

```
① 写 redo log，状态置为 prepare
② 写 binlog
③ 提交事务，redo log 状态置为 commit
```

**为什么需要两阶段？** 如果没有 ②，崩溃后 redo 有记录但 binlog 没有 → 从库丢数据；如果先写 binlog 再写 redo，崩溃后 binlog 有但主库没有 → 主从不一致。两阶段保证：**崩溃恢复时，redo 处于 prepare 且 binlog 完整则提交，否则回滚**。

**关键参数**：

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `innodb_flush_log_at_trx_commit` | redo 刷盘策略（1 每次提交刷、0 每秒、2 写 OS 缓存） | **1**（不丢数据）；性能敏感可 2 |
| `sync_binlog` | binlog 刷盘策略（1 每次提交、0 由 OS 决定） | **1**（配合上一条即"双 1"） |
| `binlog_format` | STATEMENT / ROW / MIXED | **ROW**（主从一致、可恢复误删，但日志大） |

> **"双 1 配置"** 是面试常问的：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`，保证崩溃不丢数据，代价是每次提交两次 fsync。

### 4.8 慢 SQL 优化 ⭐⭐⭐

**步骤**：

```
① 开启慢查询日志 slow_query_log=ON, long_query_time=1
② 找 TOP SQL（mysqldumpslow / pt-query-digest）
③ EXPLAIN 分析
④ 优化（加索引 / 改写 SQL / 减少回表 / 分页优化）
⑤ 复测
```

**EXPLAIN 关键字段**：

| 字段 | 关注点 |
| --- | --- |
| `type` | **system > const > eq_ref > ref > range > index > ALL**，至少要到 `range`；`ALL` 要优化 |
| `key` | 实际用的索引，为 NULL 说明没走索引 |
| `key_len` | 用了索引的多少列（判断联合索引用了几列） |
| `rows` | 预估扫描行数，越小越好 |
| `filtered` | 过滤比例 |
| `Extra` | **Using index**（覆盖索引，好）、**Using where**、**Using filesort**（要优化）、**Using temporary**（要优化）、Using index condition（ICP） |

**深分页优化**（高频）：

```sql
-- ❌ 慢：要扫描 100 万行再丢弃
SELECT * FROM order ORDER BY id LIMIT 1000000, 20;

-- ✅ 方案一：延迟关联（先用覆盖索引拿主键，再 join 回表）
SELECT o.* FROM order o
JOIN (SELECT id FROM order ORDER BY id LIMIT 1000000, 20) t ON o.id = t.id;

-- ✅ 方案二：游标分页（记录上一页最后一个 id，要求连续翻页）
SELECT * FROM order WHERE id > 1000000 ORDER BY id LIMIT 20;

-- ✅ 方案三：业务限制（只允许翻到前 N 页）
```

**其他优化手段**：

- 只查需要的列（避免 `SELECT *`，提高覆盖索引命中率）。
- 用 `EXISTS` 代替 `IN`（子查询大时）。
- 批量操作代替循环单条（`INSERT ... VALUES (...),(...)`）。
- 避免 `ORDER BY RAND()`（全表排序）。
- 大表 `ALTER` 用 `pt-online-schema-change` / `gh-ost`。
- 热点数据放 Redis，读多写少的表加缓存。

### 4.9 主从复制与分库分表 ⭐⭐

**主从复制流程**：

```
主库写 binlog → 从库 IO 线程拉取写入 relay log → 从库 SQL 线程重放
```

**主从延迟的原因**：从库 SQL 线程单线程重放（MySQL 5.7+ 支持并行复制，按组提交/库并行）、大事务、从库压力大、网络。

**延迟的应对**：

- 强制走主库（关键读，如支付后立即查订单）。
- 半同步复制（`rpl_semi_sync_master`）。
- 缓存 + 异步补偿。
- 拆分大事务。

**分库分表**：

| 方式 | 说明 | 问题 |
| --- | --- | --- |
| 垂直分库 | 按业务拆（订单库、用户库） | 跨库 join |
| 垂直分表 | 冷热字段拆分 | — |
| **水平分表** | 按 hash/range 拆同一张表 | 跨分片查询、分布式事务、全局 ID |

**分片键选择**：要保证**查询能命中分片**（如按 user_id 分片，则所有查询必须带 user_id），否则要扫全部分片。

**中间件**：ShardingSphere-JDBC（客户端）、MyCat（代理）。

**全局 ID 方案**：雪花算法、号段模式（美团 Leaf）、Redis `INCR`、数据库自增步长。

## 五、Redis

> Redis 是 4 年经验面试的**必考区**。核心五问：**为什么快 / 数据结构 / 持久化 / 缓存一致性 / 分布式锁**。

### 5.1 Redis 为什么快？⭐⭐⭐

四层回答（从浅到深，面试官喜欢听完整版）：

1. **纯内存操作**，避免磁盘 IO。
2. **单线程执行命令**，无锁竞争、无上下文切换（Redis 6.0 起网络 IO 多线程，但**命令执行仍是单线程**）。
3. **IO 多路复用**（epoll），单线程处理大量连接。
4. **高效的数据结构**（SDS、跳表、listpack、渐进式 rehash）。

**追问**："单线程为什么还能扛高并发？"
→ 因为瓶颈通常在**网络和内存**，而不在 CPU；单线程省去了锁和线程切换开销，配合 pipeline 可以达到 10 万+ QPS。

**追问**："Redis 6.0 为什么引入多线程？"
→ 只把**网络读写和协议解析**交给多线程，命令执行仍是单线程，保证原子性；因为网卡带宽上来了，网络 IO 成了瓶颈。

### 5.2 五大基础类型与底层结构 ⭐⭐

| 类型 | 底层结构 | 典型场景 |
| --- | --- | --- |
| **String** | SDS（简单动态字符串，预分配 + 二进制安全 + O(1) 取长度） | 缓存、计数器、分布式锁、Session |
| **Hash** | listpack（元素少）/ hashtable（渐进式 rehash） | 对象存储、购物车 |
| **List** | quicklist（listpack 组成的双向链表） | 消息队列、栈、最新列表 |
| **Set** | intset（全整数）/ hashtable | 去重、共同好友、抽奖 |
| **ZSet** | **跳表 + 哈希表** | 排行榜、延时队列 |
| Bitmap | String 的位操作 | 签到、布隆过滤器 |
| HyperLogLog | 概率算法，12KB 估基数 | UV 统计（有误差） |
| GEO | ZSet + GeoHash | 附近的人 |
| Stream | 类似 Kafka 的结构 | 消息队列（支持消费者组） |

**跳表为什么不用红黑树？**（高频追问）

- 跳表实现简单、**范围查询天然有序**（`ZRANGE` 友好）。
- 插入删除只需改指针，**无需旋转**。
- 并发/内存控制更容易（可通过参数调层数）。
- 缺点：空间换时间（平均 1.33 层指针）。

**ZSet 何时用 listpack？** 元素个数 ≤ `zset-max-listpack-entries`（默认 128）且元素长度 ≤ `zset-max-listpack-value`（默认 64）时用 listpack，否则转跳表。

**渐进式 rehash**：哈希表扩容不是一次性搬完，而是每次操作搬一部分，用 `rehashidx` 记录进度，**避免单次阻塞**（这是"单线程也要避免长阻塞"的典型设计）。

### 5.3 持久化 ⭐⭐⭐

| 方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **RDB** | fork 子进程，**写时复制（COW）** 生成二进制快照 | 文件小、恢复快 | 可能丢数据（两次快照之间） |
| **AOF** | 追加写命令日志 | 数据更安全（可配 everysec） | 文件大、恢复慢 |
| **混合持久化**（4.0+） | AOF 重写时前半部分存 RDB 格式 | 兼顾恢复速度与安全性 | 兼容性要求 4.0+ |

**AOF 三种刷盘策略**：

| 策略 | 行为 | 丢数据 | 性能 |
| --- | --- | --- | --- |
| `always` | 每条命令 fsync | 几乎不丢 | 最差 |
| **`everysec`**（默认/推荐） | 每秒 fsync | 最多丢 1 秒 | 好 |
| `no` | 交给 OS | 可能丢很多 | 最好 |

**AOF 重写**：`BGREWRITEAOF` 触发，fork 子进程根据当前内存状态生成最小命令集（如 100 次 `INCR` 只写一条 `SET`），重写期间的新命令写入 **AOF 重写缓冲区**，完成后追加。

> **fork 的代价**：fork 本身会短暂阻塞（与内存页表大小相关），且 COW 期间写操作会复制页 → **内存可能翻倍**。这是"Redis 单实例不要超过 10~16G"的原因之一。

### 5.4 过期删除与内存淘汰 ⭐⭐

**过期删除策略**（两者结合）：

- **惰性删除**：访问时才检查是否过期（对 CPU 友好，但可能长期占内存）。
- **定期删除**：每 100ms 随机抽一批 key 检查，删除过期 key（默认 `hz=10`）。

> **为什么不用定时器每个 key 一个？** 太耗 CPU。

**八种淘汰策略**（`maxmemory-policy`）：

| 策略 | 淘汰范围 | 算法 |
| --- | --- | --- |
| `noeviction`（默认） | — | 不淘汰，写入报错 |
| `allkeys-lru` | 所有 key | LRU（近似，采样） |
| `allkeys-lfu` | 所有 key | LFU（4.0+，按访问频率） |
| `allkeys-random` | 所有 key | 随机 |
| `volatile-lru` | 设置了过期时间的 | LRU |
| `volatile-lfu` | 设置了过期时间的 | LFU |
| `volatile-random` | 设置了过期时间的 | 随机 |
| `volatile-ttl` | 设置了过期时间的 | 剩余 TTL 最小 |

**LRU 是近似实现**：每个对象有 24 bit 的 `lru` 字段（时钟），淘汰时**随机采样 5 个**取最久未用的，避免维护全局链表（单线程下链表操作太重）。

**LFU 的坑**：新 key 初始计数为 5，容易"一夜爆红"后被误淘汰；Redis 用 `lfu-log-factor` 和 `lfu-decay-time` 调节。

### 5.5 高可用：主从、哨兵、Cluster ⭐⭐

**主从复制**：

```
① 全量同步：从库 PSYNC，主库 BGSAVE 生成 RDB + 缓冲区命令
② 增量同步：主库把写命令写入 repl_backlog，从库按 offset 拉取
③ 断线重连：offset 在 backlog 内则增量，否则全量
```

**哨兵（Sentinel）**：

- **主观下线**（单个哨兵认为挂了）→ **客观下线**（超过 quorum 个哨兵认同）。
- 选举 Leader 哨兵（Raft）→ 选新主（优先级 > offset > runid）→ 通知客户端。
- 至少 **3 个哨兵**、奇数个。

**Cluster**：

- **16384 个槽位**（`CRC16(key) % 16384`），每个主节点负责一部分。
- **Gossip 协议**交换节点状态。
- 至少 **3 主 3 从**。
- **跨槽操作报错** `CROSSSLOT`，用 **hash tag** `{user1000}.name` 强制同槽。
- 集群模式只支持 **db0**。

**为什么是 16384 个槽？** 心跳包要携带槽位 bitmap，16384 bit = 2KB，若用 65536 则 8KB，心跳太占带宽；且 16384 个节点足够（官方建议不超过 1000 节点）。

### 5.6 缓存三大问题 ⭐⭐⭐

| 问题 | 现象 | 原因 | 解决方案 |
| --- | --- | --- | --- |
| **缓存穿透** | 查不存在的数据，请求全打到 DB | 恶意攻击 / 业务查询不存在 | ① **缓存空值**（短 TTL）② **布隆过滤器** ③ 参数校验 |
| **缓存击穿** | 某个**热点 key 过期**瞬间，大量请求打到 DB | 热点 key + 过期 | ① **互斥锁**（只让一个线程重建）② **逻辑过期**（不设 TTL，异步刷新）③ 热点 key 永不过期 |
| **缓存雪崩** | **大量 key 同时过期**或 Redis 宕机，DB 被打垮 | 过期时间集中 / 实例故障 | ① **过期时间加随机值** ② 多级缓存（本地 + Redis）③ 集群高可用 ④ **熔断降级** ⑤ 限流 |

**互斥锁重建代码**：

```java
public String get(String key) {
    String value = redis.get(key);
    if (value != null) return value;

    String lockKey = "lock:" + key;
    // SET NX PX：只有抢到锁的线程去查 DB
    if (redis.set(lockKey, "1", "NX", "PX", 3000)) {
        try {
            value = redis.get(key);              // 双重检查，避免重复查
            if (value == null) {
                value = db.query(key);
                redis.set(key, value, 60 + random(30), TimeUnit.SECONDS);
            }
            return value;
        } finally {
            redis.del(lockKey);
        }
    } else {
        Thread.sleep(50);                         // 没抢到，稍后重试
        return get(key);
    }
}
```

> **逻辑过期 vs 互斥锁**：互斥锁保证强一致但有等待；逻辑过期保证高可用但返回的是旧数据（适合能容忍短暂不一致的场景）。

### 5.7 缓存与数据库一致性 ⭐⭐⭐

**Cache Aside（旁路缓存）**：

- **读**：先读缓存，未命中读 DB 并写回缓存。
- **写**：**先更新 DB，再删除缓存**（而不是更新缓存）。

**为什么是"删除"而不是"更新缓存"？**

1. 更新缓存有并发覆盖问题（A 更新 DB→B 更新 DB→B 更新缓存→A 更新缓存，缓存变旧值）。
2. 缓存可能并不需要（冷数据），更新是浪费。
3. **删除更简单，且下次读时按需加载**。

**为什么"先更新 DB 再删缓存"？** 反过来的话，先删缓存再更新 DB，中间有读请求会把**旧值**写回缓存，导致长期不一致。

**仍有极小概率不一致的窗口**：

```
读请求 A：缓存未命中 → 读 DB 得到旧值
写请求 B：更新 DB → 删除缓存
读请求 A：把旧值写回缓存   ← 不一致（概率极低，要求 A 的读 DB 慢于 B 的整个写流程）
```

**解决**：

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| **延迟双删** | 更新 DB 后删缓存，再延迟 500ms~1s 再删一次 | 延迟时间难估 |
| **订阅 binlog** | Canal 监听 binlog 异步删缓存 | 引入中间件，最终一致 |
| **分布式锁串行化** | 读写都加锁 | 性能下降 |
| **给缓存设置较短 TTL** | 兜底 | 最终一致 |

> **面试话术**："强一致场景不要用缓存，或者用『先更新 DB + 分布式锁 + 延迟双删』；互联网业务通常接受最终一致，用 Canal 订阅 binlog 删除缓存最稳妥。"

### 5.8 分布式锁 ⭐⭐⭐

**基础实现**：

```bash
# 加锁：SET key value NX PX 30000
SET lock:order:123 uuid-xxx NX PX 30000

# 解锁：必须用 Lua 保证"判断 + 删除"原子
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

**三个必须解决的坑**：

| 坑 | 后果 | 解决 |
| --- | --- | --- |
| 业务没执行完锁就过期 | 多个线程同时持锁 | **看门狗续期**（Redisson） |
| 误删别人的锁 | 锁失效 | value 存唯一标识，Lua 比对后删除 |
| 主从切换丢锁 | 锁丢失 | RedLock（有争议）/ 改用 ZooKeeper / DB |

**Redisson 看门狗**：默认锁 30s，后台每 10s（1/3 周期）续期一次，直到 `unlock()` 停止。

**RedLock 的争议**（Martin Kleppmann vs antirez）：

- 向 N 个独立 Redis 节点加锁，超过 N/2+1 成功且总耗时小于锁有效期才算成功。
- 反对者认为：**依赖时钟**、GC 停顿可能导致持锁者不自知，无法提供强一致保证。
- 结论：**RedLock 不是强一致的分布式锁**，高一致场景用 **ZooKeeper/etcd**（基于租约和会话）。

**选型**：

| 方案 | 一致性 | 性能 | 适用 |
| --- | --- | --- | --- |
| Redis 单机 | 一般 | 高 | 大多数业务（防重复提交、任务互斥） |
| Redisson | 较好 | 高 | 生产推荐 |
| ZooKeeper | 强 | 中 | 要求严格互斥 |
| etcd | 强 | 中 | 云原生 |

### 5.9 热 Key / 大 Key / 其他 ⭐

**大 Key 的危害**：网络阻塞、删除阻塞（`DEL` 是同步的）、集群数据倾斜、持久化慢。

| 问题 | 检测 | 处理 |
| --- | --- | --- |
| 大 Key | `redis-cli --bigkeys`、`MEMORY USAGE key` | 拆分（如 Hash 按字段拆多个）、用 `UNLINK` 异步删除 |
| 热 Key | `--hotkeys`、监控、客户端统计 | 本地缓存、多副本分散、限流 |

**其他高频点**：

| 知识点 | 要点 |
| --- | --- |
| Pipeline | 批量发送减少 RTT，但**不保证原子性**，且一次不要发太多（阻塞） |
| Lua 脚本 | 原子执行，但**不能有耗时操作**（阻塞单线程） |
| Redis 事务 | `MULTI/EXEC`，**不支持回滚**（命令错误才整体不执行，运行时错误部分执行） |
| `SCAN` vs `KEYS` | `KEYS` 阻塞且 O(n)，生产禁用；`SCAN` 游标分批 |
| 内存碎片 | `MEMORY DOCTOR`、`activedefrag` |
| 持久化阻塞 | fork 时 COW、AOF 重写 |

## 六、Spring 全家桶

> 4 年经验对 Spring 的要求：**Bean 生命周期、循环依赖、事务失效、自动装配原理** 这四块必须能讲，其余了解即可。

### 6.1 IoC 与 Bean 生命周期 ⭐⭐⭐

**IoC**：对象的创建和依赖关系交给容器管理，实现**控制反转**和**依赖注入**。

**Bean 生命周期（能背）**：

```
① 实例化（构造器 / 工厂方法）
② 属性填充（@Autowired 注入）
③ Aware 回调（BeanNameAware / BeanFactoryAware / ApplicationContextAware）
④ BeanPostProcessor.postProcessBeforeInitialization()
⑤ 初始化（@PostConstruct → InitializingBean.afterPropertiesSet() → init-method）
⑥ BeanPostProcessor.postProcessAfterInitialization()   ← AOP 代理在这里生成
⑦ 使用
⑧ 销毁（@PreDestroy → DisposableBean.destroy() → destroy-method）
```

> **关键**：**AOP 代理是在 ⑥ 生成的**，这解释了为什么循环依赖需要三级缓存（见 6.2）。

### 6.2 循环依赖与三级缓存 ⭐⭐⭐

**三级缓存**：

```java
// 一级：完整的 Bean
Map<String, Object> singletonObjects;
// 二级：早期暴露的 Bean（已实例化，未填充属性 / 未代理）
Map<String, Object> earlySingletonObjects;
// 三级：ObjectFactory，用于生成早期引用（可能是代理）
Map<String, ObjectFactory<?>> singletonFactories;
```

**解决流程（A 依赖 B，B 依赖 A）**：

```
① 创建 A：实例化 A → 把 A 的 ObjectFactory 放入三级缓存
② 填充 A 的属性，发现需要 B
③ 创建 B：实例化 B → 填充 B 的属性，发现需要 A
④ 从三级缓存拿到 A 的 ObjectFactory，调用 getObject() 得到 A 的早期引用
   → 放入二级缓存，从三级缓存移除
⑤ B 创建完成，放入一级缓存
⑥ A 继续填充属性（拿到 B），完成初始化，放入一级缓存
```

**为什么需要三级而不是两级？**

- 如果只有两级（早期引用直接放二级），那么**每次提前引用都会生成代理**，但最终 A 还需要被代理一次 → 可能生成**两个不同的代理对象**。
- 三级缓存存的是 `ObjectFactory`（lambda），**只在真正发生循环依赖时才调用 `getEarlyBeanReference` 生成代理**，否则就返回原始对象。**这是延迟代理**，保证了"最多一个代理"。

**为什么 Spring 无法解决的情况**：

| 场景 | 原因 |
| --- | --- |
| **构造器注入的循环依赖** | 对象还没实例化，无法提前暴露 |
| **prototype 作用域的循环依赖** | 不缓存，直接抛异常 |
| `@Async` 方法导致的循环依赖 | 代理时机不同（需 `@Lazy` 解决） |

**解决方案**：`@Lazy`（注入代理，延迟解析）、改成 setter 注入、重构解耦。

### 6.3 AOP 原理 ⭐⭐

| 代理方式 | 条件 | 说明 |
| --- | --- | --- |
| **JDK 动态代理** | 目标类**实现了接口** | `Proxy.newProxyInstance` + `InvocationHandler` |
| **CGLIB** | 目标类**没有接口**，或强制 `proxyTargetClass=true` | 生成子类，**无法代理 final 类/方法** |

**Spring Boot 2.x 起默认 `proxyTargetClass=true`（全用 CGLIB）**，原因：CGLIB 不再需要额外依赖，且能代理没有接口的类。

**AOP 的切面执行顺序**（多个 advice）：

```
@Around 前 → @Before → 目标方法 → @Around 后 → @After → @AfterReturning / @AfterThrowing
```

**自调用失效**：`this.method()` 不经过代理 → 事务/缓存/AOP 全部失效。解决：注入自身、`AopContext.currentProxy()`、拆分到另一个 Bean。

### 6.4 Spring 事务 ⭐⭐⭐

**七种传播行为**：

| 传播行为 | 说明 | 场景 |
| --- | --- | --- |
| **REQUIRED**（默认） | 有事务则加入，无则新建 | 绝大多数场景 |
| **REQUIRES_NEW** | 总是新建事务，挂起当前 | 记录日志（不能因主事务回滚而丢失） |
| SUPPORTS | 有则加入，无则以非事务运行 | 查询 |
| NOT_SUPPORTED | 以非事务运行，挂起当前 | 耗时操作 |
| MANDATORY | 必须在事务中，否则抛异常 | 强制约束 |
| NEVER | 必须不在事务中，否则抛异常 | — |
| NESTED | 嵌套事务（保存点） | 子事务回滚不影响主事务 |

> **REQUIRES_NEW vs NESTED**：前者是**两个独立事务**（需要新连接）；后者是**同一个事务的保存点**（回滚到保存点，主事务可继续）。

**`@Transactional` 失效的 8 个场景（必背）**：

| 场景 | 原因 |
| --- | --- |
| ① 方法**非 public** | 代理只拦截 public（Spring 6 起 protected/包可见也可，但不要依赖） |
| ② **同类自调用** `this.xxx()` | 不走代理 |
| ③ 异常被 **catch 吞掉** | 容器感知不到异常 |
| ④ 抛出**受检异常** | 默认只回滚 `RuntimeException` 和 `Error`，需 `rollbackFor = Exception.class` |
| ⑤ 类**未被 Spring 管理** | 没有代理 |
| ⑥ **多线程**调用 | 事务绑定在 ThreadLocal，子线程不同事务 |
| ⑦ 数据库引擎**不支持事务** | 如 MyISAM |
| ⑧ 传播行为设置不当 | 如 `NOT_SUPPORTED` |

**事务与锁的坑**：事务内做 RPC / 发 MQ / 大量计算 → **长事务** → 锁持有时间长、连接池耗尽。**原则：事务尽量短，RPC 和 MQ 放到事务外（用事务消息或本地消息表保证一致性）。**

### 6.5 Spring Boot 自动装配 ⭐⭐

```java
@SpringBootApplication
  = @SpringBootConfiguration
  + @EnableAutoConfiguration      // 核心
  + @ComponentScan
```

**装配流程**：

```
① @EnableAutoConfiguration
② → @Import(AutoConfigurationImportSelector.class)
③ → 读取 META-INF/spring.factories（2.7 之前）
     或 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（2.7+）
④ → 得到候选配置类列表（Spring Boot 3 中有上百个）
⑤ → 用 @Conditional 系列注解过滤（@ConditionalOnClass / @ConditionalOnMissingBean / @ConditionalOnProperty）
⑥ → 注册 Bean
```

**为什么要有 `@ConditionalOnMissingBean`？** 让用户自定义的 Bean 覆盖默认配置（**约定优于配置 + 可覆盖**）。

**手写一个 starter**（4 年经验常问）：

```
my-spring-boot-starter/
├── pom.xml
└── src/main/resources/META-INF/spring/
    └── org.springframework.boot.autoconfigure.AutoConfiguration.imports   # 写配置类全限定名
```

配置类上加 `@Configuration` + `@ConditionalOnClass` + `@EnableConfigurationProperties`。

## 七、消息队列

> 面试重点不在"会不会用 API"，而在 **可靠性、幂等、顺序、积压** 这四个工程问题。

### 7.1 为什么用 MQ？⭐

| 作用 | 说明 | 例子 |
| --- | --- | --- |
| **解耦** | 生产者不关心消费者 | 下单后发消息，积分/库存/短信各自消费 |
| **异步** | 非核心链路异步化，降低 RT | 下单主链路只写 DB，发券异步 |
| **削峰** | 把突发流量缓存在队列 | 秒杀请求先入队再消费 |

**引入 MQ 的代价**：系统复杂度上升、**一致性变成最终一致**、消息可能丢失/重复/乱序、需要运维成本。

> **4 年经验的关键**：能说出"什么业务**不该**用 MQ"——强一致、低延迟、需要同步返回结果的场景。

### 7.2 Kafka vs RocketMQ vs RabbitMQ ⭐

| 维度 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 吞吐 | **最高（十万+）** | 高（万级~十万） | 中（万级） |
| 语言 | Scala/Java | Java | Erlang |
| 延迟 | ms 级 | ms 级 | **μs 级** |
| 顺序消息 | 单分区有序 | **支持（MessageQueueSelector）** | 较弱 |
| 事务消息 | 支持（0.11+） | **原生支持（半消息+回查）** | 不支持 |
| 延时消息 | 不支持（需外部实现） | **支持（18 个等级 / 5.0 任意时间）** | 支持（TTL+死信） |
| 消息回溯 | **支持（按 offset）** | 支持 | 不支持 |
| 适用 | 日志、埋点、大数据 | **电商交易（推荐）** | 中小规模、复杂路由 |

**Kafka 为什么吞吐高？**

1. **顺序写磁盘**（追加日志段，接近内存速度）。
2. **页缓存**（不自己管理缓存，交给 OS）。
3. **零拷贝**（`sendfile`，数据不经过用户态）。
4. **批量发送 + 压缩**（`batch.size`、`linger.ms`）。
5. **分区并行**。

### 7.3 消息可靠性（三段式）⭐⭐⭐

**消息可能丢失的三个环节**：

#### ① 生产者 → Broker

| 手段 | 说明 |
| --- | --- |
| **同步发送 + 确认** | Kafka `acks=-1/all`（ISR 全部确认）；RocketMQ 同步发送返回 `SEND_OK` |
| **重试** | 网络抖动重试，配合幂等 |
| **本地消息表** | DB 事务内写消息表，定时任务补发（保证不丢） |

`acks` 取值：

- `0`：不等确认（最快，可能丢）
- `1`：Leader 写入即返回（Leader 挂了可能丢）
- `-1/all`：ISR 全部同步完成（**最安全**）

#### ② Broker 存储

- **副本机制**：`replication.factor >= 3`，`min.insync.replicas >= 2`。
- **刷盘**：Kafka 靠**多副本**而不是刷盘；RocketMQ 有同步刷盘/异步刷盘。
- **禁止 unclean 选举**：`unclean.leader.election.enable=false`（否则可能选到落后副本）。

#### ③ Broker → 消费者

- **关闭自动提交 offset**，业务处理成功后手动 `commit`。
- Kafka：`enable.auto.commit=false` + 手动提交。
- RocketMQ：返回 `CONSUME_SUCCESS` 才 ack。

> **结论**：想做到"不丢"，就必须接受**至少一次（at-least-once）**，于是必然要处理**重复消费**。

### 7.4 幂等与重复消费 ⭐⭐⭐

**为什么一定会有重复？** 因为 ack 可能丢失：消费者处理完了，但提交 ack 时挂了 → Broker 重投。

**幂等的五种实现**：

| 方案 | 说明 | 适用 |
| --- | --- | --- |
| **唯一索引** | DB 唯一约束兜底 | 插入类业务（最可靠） |
| **去重表 / Redis setnx** | 用消息 ID 判重 | 通用 |
| **状态机** | 只有特定状态才能流转（如"待支付→已支付"） | 订单类 |
| **业务唯一键** | 订单号 + 操作类型 | 支付、退款 |
| **乐观锁版本号** | `UPDATE ... WHERE version = ?` | 更新类 |

```java
// 典型实现：Redis 防重 + DB 唯一索引兜底
String key = "msg:dedup:" + msg.getMsgId();
if (!redis.set(key, "1", "NX", "PX", 24 * 3600 * 1000L)) {
    return;                        // 已处理过，直接 ack
}
try {
    // 业务处理（DB 有唯一索引兜底）
    orderService.handle(msg);
} catch (DuplicateKeyException e) {
    log.warn("重复消息 {}", msg.getMsgId());   // 幂等，忽略
}
```

### 7.5 顺序消息 ⭐

**为什么会乱序？** 多分区/多队列并行消费 + 重试。

**保证顺序的三要素**：

1. **生产端**：按业务 key（如 `orderId`）hash 到**同一分区/队列**。
2. **存储端**：单分区内天然有序。
3. **消费端**：**单线程消费该分区**（或多线程但按 key 分发到内存队列，每个队列单线程）。

```java
// RocketMQ 顺序发送
producer.send(msg, new MessageQueueSelector() {
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        int index = Math.abs(arg.hashCode()) % mqs.size();
        return mqs.get(index);
    }
}, orderId);
```

> **注意**：顺序消费会**牺牲吞吐**（并行度下降），只在必要时用（如订单状态流转）。

### 7.6 消息积压怎么办？⭐⭐

**先定位原因**：消费者挂了？消费变慢（慢 SQL/下游超时）？生产突增？

**处理步骤**：

```
① 紧急扩容消费者（不超过分区数，否则多余的消费者空闲）
② 如果分区数不够 → 临时扩分区（Kafka 扩分区会打乱 key 的顺序保证）
③ 消费逻辑降级：先落库/落盘，异步慢慢处理（"临时转存"方案）
④ 新建一个 topic，分区数扩大 10 倍，用临时消费者把积压消息"搬运"过去
⑤ 事后：加监控告警（积压数、消费 TPS）、限流、扩容自动化
```

**面试话术**："积压的本质是**消费速度 < 生产速度**。短期靠扩容消费者/分区，长期靠优化消费逻辑（批量、异步、去掉不必要的同步 RPC）和容量规划。"

### 7.7 事务消息（RocketMQ）⭐

**要解决的问题**：本地事务和发消息的原子性（"下单成功但消息没发出去"或"消息发了但订单回滚"）。

**流程（半消息 + 回查）**：

```
① 生产者发送"半消息"到 Broker（对消费者不可见）
② Broker 返回成功
③ 生产者执行本地事务
④ 根据结果：COMMIT（消息可见）或 ROLLBACK（删除半消息）
⑤ 如果 ④ 没送达（生产者挂了），Broker 定时**回查**生产者的本地事务状态
⑥ 生产者根据 DB 状态返回 COMMIT/ROLLBACK
```

**对比本地消息表**：事务消息不需要额外建表，但依赖 MQ 支持；本地消息表通用但有延迟、需要定时任务。

## 八、分布式与微服务

> 这一章是 4 年经验与 2 年经验的分水岭：**你能否在"没有标准答案"的权衡题上讲出取舍**。

### 8.1 CAP 与 BASE ⭐⭐

**CAP**：一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）**三者不可同时满足**。

- 分布式系统 **P 必须保留**（网络分区必然发生），所以实际是在 **C 和 A 之间取舍**。
- **CP**：ZooKeeper、etcd（选举期间不可用）。
- **AP**：Eureka、Nacos 临时实例（返回可能过期的数据）。

**BASE**：基本可用（Basically Available）、软状态（Soft state）、最终一致（Eventually consistent）——是对 AP 的工程化延伸。

> **常见误区**："CAP 只能三选二" 这句话不严谨。准确说法是：**在网络分区发生时，必须在 C 和 A 之间选一个**；没有分区时 C 和 A 可以同时满足。

### 8.2 分布式事务 ⭐⭐⭐

| 方案 | 一致性 | 性能 | 侵入性 | 适用 |
| --- | --- | --- | --- | --- |
| **2PC/XA** | 强 | 差（同步阻塞、协调者单点） | 低 | 传统金融、跨库 |
| **TCC** | 强（业务层） | 中 | **高**（要写 Try/Confirm/Cancel） | 支付、资金 |
| **SAGA** | 最终 | 好 | 中（要写补偿） | 长流程、跨服务 |
| **本地消息表** | 最终 | 好 | 中 | 通用，最常用 |
| **事务消息** | 最终 | 好 | 低（依赖 MQ） | 有 MQ 的场景 |
| **最大努力通知** | 最终 | 最好 | 低 | 对账、通知类 |

**TCC 的三个坑**（必答）：

1. **空回滚**：Try 没执行，Cancel 却来了（要记录事务状态，Cancel 时判断）。
2. **幂等**：Confirm/Cancel 可能重复调用。
3. **悬挂**：Cancel 先于 Try 到达（Cancel 后要拒绝后续的 Try）。

**Seata AT 模式原理**：

- 一阶段：拦截业务 SQL，解析出**前镜像/后镜像**存入 `undo_log`，直接提交本地事务（**全局锁**保证隔离）。
- 二阶段：成功则异步删 undo_log；失败则用前镜像**反向补偿**。

> **选型建议**：能不用分布式事务就不用（拆成最终一致 + 补偿）；必须强一致用 TCC/XA；大多数互联网业务用**本地消息表 + 定时补偿**足够。

### 8.3 分布式 ID ⭐⭐

| 方案 | 有序性 | 性能 | 缺点 |
| --- | --- | --- | --- |
| UUID | 无序 | 高 | **无序导致 B+ 树频繁分裂**、占空间 |
| 数据库自增 | 有序 | 低（单点） | 扩展难 |
| 数据库多步长 | 有序 | 中 | 扩容麻烦 |
| **雪花算法 Snowflake** | 趋势递增 | **高**（本地生成） | **依赖时钟**（回拨问题） |
| **号段模式（Leaf-segment）** | 有序 | 高 | 依赖 DB 发号 |
| Redis INCR | 有序 | 高 | 依赖 Redis 可用性 |

**雪花算法结构（64 bit）**：

```
1 bit 符号位（恒 0）
41 bit 时间戳（毫秒，可用 69 年）
10 bit 机器 ID（1024 台）
12 bit 序列号（每毫秒 4096 个）
→ 单机每毫秒 4096 个，即 400 万 QPS
```

**时钟回拨怎么解决？**

1. 回拨小（< 5ms）：**等待**时钟追上。
2. 回拨大：**抛异常**拒绝服务 / 报警。
3. 用**备用 workerId** 或切换 ZooKeeper 发号。
4. 改进方案：**Leaf-snowflake**（ZooKeeper 校验时钟）、**百度 UidGenerator**（借用未来时间）。

### 8.4 限流、熔断、降级 ⭐⭐

**限流**（四种限流算法的对比见本章 6.7 节）：

- **单机限流**：Guava `RateLimiter`（令牌桶）、Sentinel。
- **分布式限流**：Redis + Lua（固定窗口/滑动窗口）、网关层限流。
- **集群限流**的难点：需要全局计数，Redis 是单点；可用**令牌桶预分配**（每个实例分一部分配额）。

**熔断 vs 降级**：

| | 熔断 | 降级 |
| --- | --- | --- |
| 触发 | 错误率/慢调用比例超阈值 | 容量不足 / 非核心依赖故障 |
| 行为 | **直接拒绝请求**，快速失败 | **返回兜底数据**（缓存、默认值） |
| 恢复 | 半开试探 | 手动/自动 |

**降级的层次**：

```
页面降级 → 功能降级（关闭非核心）→ 读降级（只读）→ 写降级 → 服务降级（返回兜底）
```

### 8.5 服务注册与发现 ⭐

**Nacos 的 AP/CP**：

- **临时实例**（默认）：心跳上报，15s 未收到标记不健康，30s 剔除 → **AP**（可用性优先）。
- **持久实例**：`ephemeral=false`，服务端主动探测 → **CP**（Raft 保证一致）。

**为什么注册中心更适合 AP？** 因为"服务列表短暂不一致"比"注册中心不可用"的代价小得多。

**服务发现方式**：

- **客户端发现**：客户端拉取列表自己负载均衡（Nacos + LoadBalancer）。
- **服务端发现**：通过负载均衡器/网关转发（K8s Service）。

### 8.6 幂等设计（贯穿所有分布式场景）⭐⭐

| 场景 | 幂等键 | 方案 |
| --- | --- | --- |
| 接口重复提交 | 客户端生成 `requestId` | Redis `setnx` + 过期 |
| MQ 重复消费 | `msgId` / 业务唯一键 | 去重表 / 唯一索引 |
| 支付回调 | 商户订单号 | 状态机 + 唯一索引 |
| 重试的 RPC | 业务 ID | 服务端幂等 |

**通用套路**：**唯一约束兜底 + 状态机校验 + 去重表**，三者结合最稳。

## 九、计算机网络与操作系统

> 占比不高（约 10%），但**一面必问 TCP 和 HTTP**，且答错很掉分。抓重点即可。

### 9.1 TCP 三次握手 / 四次挥手 ⭐⭐⭐

**三次握手**：

```
Client                          Server
  |------- SYN(seq=x) ----------->|   ①
  |<--- SYN+ACK(seq=y,ack=x+1) ---|   ②
  |------- ACK(ack=y+1) --------->|   ③
```

**为什么是三次而不是两次？**

1. **防止历史连接**：旧的 SYN 到达服务端，若两次握手服务端就建立连接，会浪费资源等待；三次让客户端有机会拒绝。
2. **同步双方初始序列号（ISN）**：双方都需要确认对方的接收能力和初始序号。
3. **确认双方的收发能力**：两次只能确认"客户端→服务端"，三次才能确认双向。

**四次挥手**：

```
Client                          Server
  |------- FIN ----------------->|  ① 客户端不再发送
  |<------ ACK ------------------|  ②
  |<------ FIN ------------------|  ③ 服务端数据发完
  |------- ACK ----------------->|  ④
```

**为什么挥手是四次？** 因为 TCP 是**全双工**，收到 FIN 只表示对方不再发送，但自己可能还有数据要发，所以 ACK 和 FIN 不能合并（除非服务端也没有数据了，此时可能变成三次）。

**TIME_WAIT 为什么等 2MSL？**

1. 保证**最后一个 ACK 能到达**（若丢失，对方会重发 FIN，此时还能响应）。
2. 让**旧连接的残留报文**在网络中消散，避免影响新连接。

> TIME_WAIT 过多（`netstat` 大量 `TIME_WAIT`）会影响端口耗尽，但**不要盲目调小**；可用 `tcp_tw_reuse`（谨慎）。

### 9.2 TCP 可靠传输机制 ⭐

| 机制 | 说明 |
| --- | --- |
| 序列号 + 确认 | 保证有序、不丢 |
| **超时重传** | RTO 动态计算（RTT 加权） |
| **快速重传** | 收到 3 个重复 ACK 立即重传，不等超时 |
| **滑动窗口** | 流量控制，防止接收方被打爆 |
| **拥塞控制** | 慢启动、拥塞避免、快重传、快恢复 |
| 校验和 | 检测数据损坏 |

**拥塞控制四阶段**：

```
① 慢启动：cwnd 从 1 指数增长到 ssthresh
② 拥塞避免：超过 ssthresh 后线性增长（+1 MSS/RTT）
③ 快重传：3 个重复 ACK 立即重传
④ 快恢复：ssthresh 减半，cwnd = ssthresh，进入拥塞避免
```

### 9.3 HTTP 演进 ⭐⭐

| 版本 | 关键特性 | 解决的问题 | 遗留问题 |
| --- | --- | --- | --- |
| HTTP/1.0 | 短连接 | — | 每次都要握手 |
| HTTP/1.1 | **长连接 keep-alive**、管线化、分块传输 | 减少握手 | **队头阻塞**（同一连接串行） |
| HTTP/2 | **二进制分帧、多路复用**、HPACK 头压缩、服务端推送 | 应用层队头阻塞 | **TCP 层队头阻塞**（丢包阻塞所有流） |
| HTTP/3 | **QUIC（基于 UDP）**、0-RTT、连接迁移 | TCP 队头阻塞 | 部署/兼容性 |

**HTTPS 握手（TLS 1.2）**：

```
① Client Hello（支持的加密套件 + 随机数）
② Server Hello（选定套件 + 随机数 + 证书）
③ 客户端验证证书链，生成 pre-master secret，用公钥加密发送
④ 双方用三个随机数计算出对称密钥（会话密钥）
⑤ 后续通信用对称加密
```

**为什么用非对称加密协商、对称加密传输？** 非对称安全但慢（大数运算），对称快；结合两者兼顾安全与性能。

**TLS 1.3 的优化**：1-RTT 握手（甚至 0-RTT 恢复），精简套件，**前向安全**强制。

### 9.4 IO 模型与 epoll ⭐⭐

**五种 IO 模型**：

| 模型 | 说明 | 特点 |
| --- | --- | --- |
| 阻塞 BIO | 读写阻塞 | 简单，一线程一连接 |
| 非阻塞 NIO | 轮询 | 空转浪费 CPU |
| **IO 多路复用** | select/poll/epoll | 一线程管多连接（**主流**） |
| 信号驱动 | 内核通知 | 少用 |
| 异步 AIO | 内核完成后再通知 | 真正异步，Linux 支持不完善 |

**select / poll / epoll 对比**：

| | select | poll | epoll |
| --- | --- | --- | --- |
| 最大连接 | 1024（fd_set 限制） | 无上限 | 无上限 |
| 数据结构 | 位图 | 链表 | **红黑树 + 就绪链表** |
| 每次调用 | **全量拷贝 + O(n) 遍历** | 同 select | **只返回就绪的，O(1)** |
| 触发方式 | 水平触发 | 水平触发 | **水平 / 边缘触发** |

**epoll 为什么高效？**

1. `epoll_ctl` 注册一次，`epoll_wait` 不用重复拷贝 fd 集合。
2. 内核用**回调**把就绪 fd 放入就绪链表，`epoll_wait` 直接返回就绪列表，**O(1)**。
3. 支持**边缘触发（ET）**：只在状态变化时通知，配合非阻塞 IO 减少系统调用。

**LT vs ET**：

- **LT（水平触发）**：只要缓冲区还有数据就一直通知，编程简单（可不一次读完）。
- **ET（边缘触发）**：只在变化时通知一次，**必须一次读到 EAGAIN**，否则丢事件；性能更好。

**Netty 为什么快？** 主从 Reactor 多线程模型 + epoll ET + 零拷贝（`ByteBuf` 池化、`CompositeByteBuf`、`FileRegion`）+ 无锁串行化设计。

### 9.5 TCP 粘包 / 拆包 ⭐

**原因**：TCP 是**字节流**，没有消息边界；Nagle 算法合并小包，MSS 分片。

**解决**：

1. **固定长度**（简单但不灵活）。
2. **分隔符**（如 `\r\n`，需转义）。
3. **长度字段**（**最常用**：先读 4 字节长度，再读内容）。

### 9.6 操作系统高频点 ⭐

| 知识点 | 要点 |
| --- | --- |
| 进程 vs 线程 | 进程有独立地址空间；线程共享堆和方法区，独享栈和 PC |
| 协程 | 用户态调度，切换成本低，适合 IO 密集 |
| 用户态/内核态 | 系统调用、中断、异常会切换；切换有开销 |
| 虚拟内存 | 页表映射，缺页中断，页面置换（LRU/Clock） |
| 零拷贝 | `mmap + write`、`sendfile`、`splice`；减少 CPU 拷贝和上下文切换 |
| 死锁四条件 | 互斥、持有等待、不可剥夺、循环等待 |

### 10.2 短链系统（最经典的入门设计题）

**需求**：长 URL → 短 URL（`https://t.cn/AbC123`），访问时 302 跳转。

**核心问题 1：怎么生成短码？**

| 方案 | 做法 | 优缺点 |
| --- | --- | --- |
| **哈希** | MD5 取前 6~8 位 | 简单，但**有冲突**，需处理 |
| **自增 ID + Base62** | 发号器 → 62 进制 | **无冲突**，但 ID 连续可被遍历（加混淆/随机偏移） |
| **雪花 ID + Base62** | 分布式发号 | 趋势递增，长度略长 |
| 随机生成 + 查重 | 随机 6 位 | 冲突率随量上升 |

**Base62**：`[0-9a-zA-Z]` 共 62 个字符，6 位可表示 `62^6 ≈ 568 亿`。

**核心问题 2：存储怎么选？**

- **MySQL**：`short_code`（唯一索引）+ `long_url` + `create_time` + `expire_time`。
- **Redis**：热点短链缓存（`short → long`），TTL 与业务一致。
- 数据量极大时按 `short_code` 哈希分库分表。

**核心问题 3：跳转用 301 还是 302？**

- **301（永久）**：浏览器会缓存，减少服务端压力，但**无法统计点击**。
- **302（临时）**：每次都请求服务端，**可统计、可动态改目标、可做风控**。
- 结论：**业务短链用 302**。

**追问**：

| 追问 | 回答 |
| --- | --- |
| 如何防止短码被遍历？ | 自增 ID 加随机偏移 / 用雪花 ID / 加签名校验 |
| 如何统计 PV/UV？ | 302 时异步写 Kafka → 实时/离线统计；UV 用 HyperLogLog |
| 如何防恶意刷？ | 限流（IP/短码维度）、黑名单、验证码 |
| 缓存穿透怎么办？ | 布隆过滤器 + 空值缓存 |

### 10.3 秒杀系统（高频 Hard）

**核心矛盾**：瞬时高并发 + 库存不能超卖 + 不能拖垮整个系统。

**分层设计**：

```
① 前端
   - 按钮置灰、答题/验证码、静态资源 CDN、倒计时本地化
② 网关层
   - 限流（令牌桶）、黑名单、防重放、请求削峰
③ 服务层
   - 库存预热到 Redis、Lua 原子扣减、用户维度去重
   - 异步下单（MQ），前端轮询结果
④ 存储层
   - DB 扣减用乐观锁 / `UPDATE stock SET num = num - 1 WHERE id = ? AND num > 0`
   - 或最终一致：Redis 扣减 + MQ 异步落库 + 对账补偿
```

**防超卖的三种方案**：

| 方案 | 实现 | 优缺点 |
| --- | --- | --- |
| **DB 乐观锁** | `WHERE num > 0` 条件更新 | 简单可靠，但 DB 压力大 |
| **Redis + Lua** | Lua 中判断 + 扣减（原子） | 高性能，但需保证 Redis 与 DB 最终一致 |
| **分布式锁** | 锁住商品维度 | 串行化，吞吐低，不推荐 |

```lua
-- 库存扣减 Lua（原子）
local stock = tonumber(redis.call('get', KEYS[1]))
if stock == nil or stock <= 0 then
    return -1
end
redis.call('decr', KEYS[1])
return stock - 1
```

**追问**：

| 追问 | 回答 |
| --- | --- |
| 如何防止同一用户重复抢？ | Redis `SETNX user:goods`，或用 `SADD` 去重 |
| 下单失败怎么回滚库存？ | MQ 消费失败 → 补偿接口 + 定时对账 |
| Redis 挂了怎么办？ | 降级为 DB 乐观锁 + 限流；库存预热可重放 |
| 如何保证公平性？ | 队列/抽签制，或按用户 ID 分批放行 |
| 超卖了一台怎么办？ | 兜底：多卖的订单退款 + 告警 + 复盘 |

### 10.4 排行榜（Redis ZSet 的典型应用）

**需求**：实时排行榜（日榜/周榜/总榜），支持 Top N 和我的排名。

```bash
ZINCRBY rank:2024-06-01 10 user:123     # 加分
ZREVRANGE rank:2024-06-01 0 99 WITHSCORES  # Top 100
ZREVRANK rank:2024-06-01 user:123        # 我的排名（从 0 开始）
```

**关键设计**：

- **分页**：`ZREVRANGE` 按区间取，`O(log N + M)`。
- **我的排名**：`ZREVRANK` 是 `O(log N)`，别用 `ZRANGE` 遍历。
- **榜单周期**：key 带日期，定时任务生成/归档；或用**桶**（如按天分桶再合并）。
- **同分排序**：`ZSet` 分数相同时按 member 字典序，需要"先到先得"可用 `score + 时间戳小数`。

**海量用户怎么办？**

- 只维护**活跃用户**的榜单（如 Top 1 万），其余用离线计算。
- 分桶（按用户 ID 哈希分 100 桶，每桶 Top N，再归并）。
- 冷数据落 DB/数仓。

### 10.5 订单超时自动取消（延时任务）

**五种方案对比**：

| 方案 | 精度 | 可靠性 | 适用 |
| --- | --- | --- | --- |
| 定时任务扫表 | 分钟级 | 高（但扫表压力大） | 小规模兜底 |
| **DelayQueue**（JVM） | 高 | 低（重启丢失） | 单机 |
| **Redis ZSet** | 秒级 | 中 | 中小规模 |
| **RabbitMQ 死信/延迟插件** | 秒级 | 高 | 中小规模 |
| **RocketMQ 延时消息** | 固定等级/任意 | 高 | **推荐** |
| **时间轮**（Netty/HashedWheelTimer） | 毫秒级 | 中 | 高性能单机 |
| **定时任务 + 分片扫表** | 分钟级 | 高 | 大规模兜底 |

**Redis ZSet 实现**：

```java
// 下单：score = 到期时间戳
redis.zadd("order:delay", expireAt, orderId);

// 轮询（每秒）：取出到期的
Set<String> due = redis.zrangeByScore("order:delay", 0, now, 0, 100);
for (String orderId : due) {
    // 用 ZREM 返回值做幂等：只有删除成功的那个线程才处理
    if (redis.zrem("order:delay", orderId) == 1) {
        handleTimeout(orderId);
    }
}
```

> **必须配合状态机**：取消前查订单状态，只有"待支付"才能取消；已支付的直接跳过（**幂等**）。

### 10.6 附近的人 / LBS

**方案对比**：

| 方案 | 原理 | 精度 | 性能 |
| --- | --- | --- | --- |
| 数据库经纬度范围查询 | `WHERE lat BETWEEN ... AND lng BETWEEN ...` | 矩形误差 | 差（索引难用） |
| **GeoHash** | 把经纬度编码成字符串，前缀相同的距离近 | 网格误差 | 好（可走索引） |
| **Redis GEO**（底层 ZSet + GeoHash） | `GEOADD` / `GEORADIUS` / `GEOSEARCH` | 好 | **最好** |
| 搜索引擎（ES geo_point） | 倒排 + 距离计算 | 好 | 好，适合复杂过滤 |

```bash

```

**GeoHash 的边界问题**：相邻网格可能前缀不同。解决：查询时取**周围 8 个网格**一起查。

### 10.7 Feed 流 / 朋友圈

**推拉模式**：

| 模式 | 做法 | 优缺点 |
| --- | --- | --- |
| **推（写扩散）** | 发消息时写入所有粉丝的收件箱 | 读快，写慢（大 V 有几千万粉丝时爆炸） |
| **拉（读扩散）** | 读时去关注列表拉取并归并 | 写快，读慢 |
| **推拉结合** | 普通用户推，大 V 拉 | **主流方案** |

**大 V 问题**：明星发一条动态要写 5000 万份 → 用"拉"的模式，读时单独合并大 V 的内容。

**分页**：用**游标（cursor）**而不是 offset（避免新内容插入导致重复）。

### 10.8 点赞 / 计数系统

**方案**：

- **Redis Hash**：`like:{postId}` → `{userId: 1}`，`HLEN` 计数，`SISMEMBER` 判重。
- 大 key 问题：按 `postId` 分片（hash tag 或分桶）。
- 异步落库：Kafka → 批量写 DB。
- **计数不要求强一致**：Redis 计数 + 定时对账。

**点赞列表分页**：用 `ZSet`（score = 时间戳），`ZREVRANGE` 分页。

### 10.9 支付对账

**核心**：**最终一致 + 可追溯**。

```
① 下单：本地消息表记录"待支付"
② 支付回调：验签 → 幂等（订单号唯一）→ 更新状态 → 发消息
③ 定时对账（T+1）：下载渠道账单 → 与本地流水逐笔比对
   - 长款（渠道有、本地无）→ 补单
   - 短款（本地有、渠道无）→ 冲正/挂账
   - 金额不符 → 人工介入
④ 差错池：所有不一致落表，人工/自动处理
```

**追问**：回调丢了怎么办？→ **主动查询**（定时轮询渠道订单状态）+ 对账兜底。

### 11.1 项目介绍的 STAR 结构

```
S（Situation 背景）：一句话说清业务是什么、规模多大
T（Task 任务）：你负责哪部分、目标是什么（带数字）
A（Action 行动）：你做了什么、为什么这么做（**这里占 60% 时间**）
R（Result 结果）：量化收益（QPS/RT/成本/稳定性）
```

**反面例子**（常见错误）：

> "我负责订单模块，用 Spring Boot + MyBatis + MySQL 做了增删改查。"

**正面例子**：

> "订单中心每天 200 万单，原来下单链路同步调用 5 个下游，P99 是 800ms。我做了三件事：①把积分、优惠券、消息通知改为 MQ 异步（一致性用本地消息表保证）；②热点商品库存预热到 Redis，用 Lua 原子扣减；③下单接口做垂直拆分，主链路只保留库存和订单落库。最终 P99 从 800ms 降到 120ms，大促峰值 1.2 万 TPS 无超卖。"

**数字要具体**：QPS、RT（P99）、数据量、机器数、成本节省、故障次数下降。

### 11.2 项目深挖的 12 个必问

面试官通常会沿着这条链追问，每一个都要准备：

| # | 追问 | 你要准备什么 |
| --- | --- | --- |
| 1 | 这个项目最复杂的地方在哪？ | 一个具体的技术难点，不是"业务复杂" |
| 2 | 为什么用 A 不用 B？ | 选型对比表（能说出 B 的缺点） |
| 3 | 遇到过什么线上问题？怎么定位的？ | 完整的排查链路（现象→工具→根因→修复→预防） |
| 4 | 这个方案有什么缺陷？ | **主动说缺点**，展示你的判断力 |
| 5 | 如果流量涨 10 倍，哪里先崩？ | 瓶颈分析 + 扩容方案 |
| 6 | 数据一致性怎么保证的？ | 具体机制（本地消息表/对账/重试） |
| 7 | 接口超时/失败怎么处理？ | 超时、重试、熔断、降级、幂等 |
| 8 | 你的代码有没有做过性能优化？ | 具体数字：从多少到多少，怎么做的 |
| 9 | 怎么保证上线不出问题？ | 灰度、回滚、开关、压测、监控 |
| 10 | 团队怎么协作？你推动过什么？ | 跨团队推动的具体案例 |
| 11 | 如果重做一次，你会怎么改？ | 反思能力（**加分项**） |
| 12 | 你在项目中的不可替代性？ | 你独有的贡献 |

### 11.3 讲"线上问题"的标准模板（高频）

面试官非常喜欢问"你遇到过什么线上问题"。准备 **2~3 个**，按这个结构讲：

```
① 现象：监控告警 / 用户反馈，具体表现（接口 5xx 上升、RT 从 50ms 涨到 3s）
② 影响：影响多少用户/订单，持续多久
③ 定位：
   - 看监控（哪个指标异常）
   - 看日志（异常栈、慢 SQL）
   - 看链路（traceId 定位慢在哪）
   - 看现场（jstack / jstat / arthas）
④ 根因：一句话说清（不是"代码有 bug"，而是"XX 场景下 YY 条件触发 ZZ"）
⑤ 修复：临时止血 + 根本修复
⑥ 预防：监控、告警、压测、代码 review、预案
```

**三个经典案例库**（可套用）：

| 案例 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 线程池打满 | 接口大量超时，CPU 不高 | 下游变慢导致线程阻塞，队列堆积 | 加超时 + 隔离线程池 + 熔断 |
| 频繁 Full GC | RT 周期性飙升 | 大对象/缓存无界增长 | 修缓存淘汰 + 调堆 + 加监控 |
| 慢 SQL | 某接口 P99 突增 | 数据量涨后索引失效/深分页 | 加联合索引 + 延迟关联 |
| 消息积压 | 下游数据延迟 | 消费逻辑有同步 RPC，变慢 | 批量 + 异步 + 扩容消费者 |
| 缓存雪崩 | DB CPU 100% | 大批 key 同时过期 | 过期时间加随机 + 熔断 |

### 13.2 高频"一句话结论"卡片

> 面试时先甩结论，再展开。以下每一条都能扩展成 2 分钟。

| 问题 | 一句话结论 |
| --- | --- |
| HashMap 线程安全吗 | 不安全，JDK8 后不死循环但会丢数据，用 ConcurrentHashMap |
| volatile 保证原子性吗 | 不保证，只保证可见性和有序性 |
| 线程池为什么不用 Executors | 无界队列或无界线程数，都会 OOM |
| ThreadLocal 为什么泄漏 | key 弱引用被回收，value 强引用留在 Entry 里 |
| AQS 的核心 | volatile state + CLH 双向队列 + CAS |
| JVM 为什么分代 | 对象朝生夕死，分代后可以针对性用不同算法 |
| G1 和 CMS 的区别 | G1 可预测停顿、Region 化、无碎片；CMS 有碎片会 Full GC |
| 为什么用 B+ 树 | 非叶子只存键 → 树矮 → IO 少；叶子链表 → 范围查询快 |
| 为什么 RR 能防幻读 | 快照读靠 MVCC，当前读靠间隙锁（不完全） |
| redo 和 binlog 区别 | redo 是 InnoDB 物理日志做崩溃恢复；binlog 是 Server 层逻辑日志做主从复制 |
| Redis 为什么快 | 内存 + 单线程无锁 + epoll + 高效结构 |
| 缓存一致性怎么做 | 先更新 DB 再删缓存 + 延迟双删 / binlog 订阅 |
| 分布式锁怎么实现 | SET NX PX + Lua 释放 + 看门狗续期 |
| 循环依赖怎么解决 | 三级缓存，第三级存 ObjectFactory 延迟生成代理 |
| @Transactional 为什么失效 | 非 public、自调用、异常被吞、受检异常、多线程等 8 种 |
| MQ 怎么保证不丢 | 生产确认 + 副本刷盘 + 消费手动 ack，代价是重复 |
| 幂等怎么做 | 唯一索引兜底 + 去重表 + 状态机 |
| 三次握手为什么三次 | 防止历史连接 + 同步双方 ISN |
| epoll 为什么快 | 红黑树注册一次 + 就绪链表回调，O(1) 取就绪 |

### 13.3 高频易错点（面试官最爱抓）

| 易错说法 | 正确表述 |
| --- | --- |
| "volatile 保证原子性" | ❌ 只保证可见性 + 有序性 |
| "synchronized 是重量级锁" | ❌ 有锁升级，低竞争时很轻 |
| "偏向锁一直存在" | ❌ JDK15 起默认关闭并废弃，后续已移除 |
| "HashMap 扩容要 rehash" | ❌ JDK8 只需判断 `hash & oldCap` |
| "CMS 没有 STW" | ❌ 初始标记和重新标记要 STW |
| "G1 没有分代" | ❌ 逻辑上仍有分代（Eden/Survivor/Old Region） |
| "MySQL 用 RR 就完全没有幻读" | ❌ 快照读和当前读混用时仍可能幻读 |
| "索引一定走 B+ 树" | ❌ 还有哈希索引（Memory 引擎）、全文索引 |
| "Redis 是单线程" | ❌ 命令执行单线程，网络 IO 6.0 起多线程 |
| "AOF 比 RDB 更安全所以只用 AOF" | ❌ 恢复慢，生产多用混合持久化 |
| "分布式锁用 SETNX 就够了" | ❌ 要考虑过期、误删、续期、主从切换 |
| "MQ 能保证 exactly-once" | ❌ 工程上是 at-least-once + 幂等 |
| "CAP 是三选二" | ⚠️ 准确说是分区发生时在 C 和 A 之间取舍 |
| "索引越多越好" | ❌ 写放大、空间占用、优化器选错 |

### 13.6 最后的话

4 年经验的面试，**拼的不是知识广度，而是"深度 + 表达 + 真实经验"**。

- 知识的深度：每个重点都能被追问三层（是什么 → 为什么 → 怎么用/有什么坑）。
- 表达的结构：先结论、再原理、后取舍、补案例。
- 真实经验：有数字、有踩坑、有反思。

如果时间有限，**优先把项目讲透 + 把 MySQL/Redis/并发 这三块打穿**，收益远高于背冷门八股。
