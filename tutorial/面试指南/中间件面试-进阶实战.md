| 维度 | 中间件/基础架构研发 | 业务后端（需精通中间件） |
| --- | --- | --- |

| 源码要求 | 必须读过（能改代码/提 PR） | 读过关键路径即可 |

### 0.3 中间件面试的四段结构

```
第一段·原理（15 min）
  "说说 Kafka 的存储结构" → 期待你讲到 segment/index/稀疏索引/零拷贝
  追问："为什么不用 B+ 树？" → 考的是"读写比决定存储结构"

第二段·场景（15 min）
  "线上 MQ 积压 2 亿条，怎么办？"
  → 期待：先定位原因，再分级处理，最后防复发

第三段·故障（15 min）
  "Redis 集群 CPU 100%，你的排查路径？"
  → 期待：工具 + 指标 + 根因 + 止血

第四段·设计（15 min）
  "设计一个百万实例的注册中心"
  → 期待：架构 + 一致性 + 容量 + 失败模式
```

**每一段的评分点不同**：原理看深度，场景看**判断力**，故障看**经验**，设计看**取舍**。

## 一、中间件通用底座：IO、Netty、协议

> 所有中间件的性能差异，最终都收敛到三件事：**IO 模型、线程模型、内存管理**。

### 1.1 五种 IO 模型与 Reactor 三种模式 ⭐⭐⭐

| 模型 | 阻塞点 | 典型代表 |
| --- | --- | --- |
| 阻塞 BIO | read/write 阻塞 | Tomcat（传统） |
| 非阻塞 NIO | 轮询 | 自己写循环（浪费 CPU） |
| **IO 多路复用** | `select/poll/epoll` | Netty、Redis、Nginx |
| 信号驱动 | 内核通知 | 少用 |
| 异步 AIO | 内核完成后回调 | Linux io_uring（新） |

**Reactor 三种模式**：

```
① 单 Reactor 单线程
   accept + read + 业务 都在一个线程 → Redis 就是这种

② 单 Reactor 多线程
   IO 线程只做读写，业务丢线程池
   → 问题：一个 Reactor 处理所有连接的 IO，高并发下仍是瓶颈

③ 主从 Reactor 多线程（Netty 默认）
   bossGroup 负责 accept → workerGroup 负责 read/write
   → 每个 EventLoop 绑定一个线程，处理多个 Channel
```

**追问**："为什么 EventLoop 要绑定固定线程？"
→ 为了避免锁。一个 Channel 的所有事件都由同一个 EventLoop 处理，**天然串行，无需同步**（Netty 的"无锁串行化设计"）。

**追问**："一个 EventLoop 处理多个 Channel，会不会互相影响？"
→ 会。**一个耗时的业务逻辑会阻塞该 EventLoop 上所有 Channel**，所以 Netty 的 handler 里不能做阻塞操作，必须丢业务线程池。

### 1.2 Netty 核心机制 ⭐⭐⭐

#### （1）组件关系

```
ServerBootstrap
  ├── bossGroup (EventLoopGroup, 通常 1 个线程)
  └── workerGroup (EventLoopGroup, 默认 2 * CPU)
        └── EventLoop (1 线程 + 1 Selector + 1 任务队列)
              └── Channel (SocketChannel)
                    └── ChannelPipeline
                          ├── ChannelInboundHandler
                          └── ChannelOutboundHandler
```

#### （2）ByteBuf 与内存池

| 维度 | 说明 |
| --- | --- |
| 读写指针 | `readerIndex` / `writerIndex`，不需要 flip（对比 NIO ByteBuffer） |
| 池化 | `PooledByteBufAllocator`（默认），基于 jemalloc 思想做 arena/chunk/page 分级 |
| 堆内 vs 堆外 | 堆外（Direct）避免一次拷贝，但分配/回收成本高 → 所以必须池化 |
| 引用计数 | `retain()` / `release()`，泄漏检测 `ResourceLeakDetector` |

**追问**："Netty 为什么快？" 四个原因：

1. **主从 Reactor + 无锁串行化**。
2. **内存池**（减少 GC 和分配开销）。
3. **零拷贝**（`CompositeByteBuf`、`slice`、`FileRegion`/`sendfile`）。
4. **FastThreadLocal**（数组下标寻址，比 `ThreadLocal` 的哈希表快）。

#### （3）Pipeline 与事件传播

```
Inbound 事件：head → handler1 → handler2 → ... → tail
Outbound 事件：tail → ... → handler2 → handler1 → head
```

**追问**："`ctx.write()` 和 `channel.write()` 的区别？"
→ `ctx.write()` 从**当前 handler 的前一个 outbound handler** 开始传播；`channel.write()` 从 **tail** 开始（走完整条链）。这是自定义编码器时最容易搞错的地方。

### 1.3 零拷贝的三种实现 ⭐⭐

| 实现 | 避免的拷贝 | 适用 |
| --- | --- | --- |
| **`sendfile`** | 用户态拷贝（2 次 → 0 次） | 文件 → Socket（Kafka、Nginx 静态文件） |
| **`mmap`** | 用户态拷贝（读） | 大文件随机读（RocketMQ 的 CommitLog） |
| **`splice`** | 内核态管道传输 | 代理转发（需要中间处理时） |
| Netty `CompositeByteBuf` | 合并多个 buffer 时的拷贝 | 协议头 + body 拼接 |
| Netty `slice`/`duplicate` | 共享底层内存 | 拆包时避免复制 |

**面试追问**："Kafka 为什么能用 sendfile，而 RocketMQ 用 mmap？"

| | Kafka | RocketMQ |
| --- | --- | --- |
| 存储 | 每 partition 一个文件，顺序写 | 所有 topic 写一个 CommitLog |
| 读 | 直接把文件段发给消费者 | 需要按 ConsumeQueue 随机定位 |
| 方案 | `sendfile`（零拷贝） | `mmap`（内存映射，随机读快） |
| 代价 | 只能顺序读 | 页缓存压力大、大文件 mmap 有风险 |

### 1.4 协议设计与序列化 ⭐⭐

**一个可扩展的二进制协议**：

```
+--------+--------+--------+--------+
| magic  | ver    | type   | flags  |   4B 头
+--------+--------+--------+--------+
|            requestId (8B)          |   用于异步 RPC 匹配
+------------------------------------+
|            bodyLength (4B)         |
+------------------------------------+
|              body (N B)            |
+------------------------------------+
```

**关键设计点**：

| 设计点 | 说明 |
| --- | --- |
| **魔数** | 快速识别非法连接（如 `0xCAFEBABE`） |
| **版本号** | 支持协议演进，服务端按版本解析 |
| **长度字段** | 解决 TCP 粘包（**最重要**） |
| **requestId** | 异步 RPC 的请求响应匹配 |
| **序列化标识** | 支持多协议（JSON/Protobuf/Hessian） |
| **扩展字段** | 用 `map<string,string>` 承载未来字段，避免改协议 |

**序列化对比**：

| 序列化 | 体积 | 速度 | 可读性 | 兼容性 | 场景 |
| --- | --- | --- | --- | --- | --- |
| JSON | 大 | 中 | 好 | 好 | 对外 API |
| Protobuf | **小** | **快** | 差 | 好（字段编号） | 内部 RPC |
| Hessian | 中 | 中 | 差 | 一般 | Dubbo 传统 |
| Avro | 小 | 快 | 差 | **最好**（schema 演进） | 大数据 |
| Kryo | 小 | 很快 | 差 | 差（需要注册类） | 内部高性能 |

**追问**："Protobuf 为什么兼容性好？"
→ 用**字段编号**而不是字段名，新增字段用新编号，旧端忽略未知字段；删除字段要保留编号（`reserved`）防止复用。

### 1.5 连接管理：中间件最容易被忽略的细节 ⭐⭐

| 问题 | 方案 | 坑 |
| --- | --- | --- |
| 连接假死 | 心跳（应用层 PING/PONG） | 只依赖 TCP keepalive 太慢（默认 2 小时） |
| 大量 TIME_WAIT | 连接池复用、`SO_REUSEADDR` | 短连接 + 高 QPS = 端口耗尽 |
| 断线重连 | 指数退避 + 抖动 | 同时重连会打垮服务端（**重连风暴**） |
| 慢客户端 | 背压（写缓冲水位） | 不设上限 → 内存被撑爆 |
| 连接数过多 | 连接多路复用（单连接多请求） | 头部阻塞（需 requestId 异步） |

**"重连风暴"案例**：

```
现象：中间件重启后，10 万客户端同时重连 → 服务端 accept 队列打满 → 更多超时 → 更多重连
解决：① 客户端随机延迟（0~30s）② 服务端限流 accept ③ 分批重启
```

### 1.6 主流中间件的线程模型对比（能背下来很加分）

| 中间件 | 网络模型 | 业务/命令执行 | 存储线程 |
| --- | --- | --- | --- |
| **Redis** | 单线程 epoll（6.0 起 IO 多线程） | 单线程 | 后台线程（bio：close/aof fsync/lazyfree） |
| **Kafka** | 多线程（acceptor + processor + request handler） | 线程池 | 后台刷盘线程 |
| **RocketMQ** | 主从 Reactor（Netty） | 业务线程池 | 刷盘线程 + 主从同步线程 |
| **Nginx** | 多进程 + epoll | worker 单线程 | — |
| **Netty 应用** | 主从 Reactor | 业务线程池 | — |

**面试话术**："Redis 单线程是为了简单和原子性，Kafka 多线程是因为它的瓶颈在磁盘和网络而不是 CPU；线程模型的选择本质是**看瓶颈在哪**。"

## 二、存储引擎：中间件的下半身

> 中间件的性能上限由存储决定。面试官问"为什么快"，本质是在问**"你的数据怎么落到磁盘、怎么读回来"**。

### 2.1 B+ 树 vs LSM 树 vs 列存 ⭐⭐⭐

| 维度 | B+ 树 | LSM 树 | 列存 |
| --- | --- | --- | --- |
| 写 | 随机写（页分裂） | **顺序写**（追加） | 批量写 |
| 读 | **点查快**（O(log n)） | 需查多层（内存表 + 多个文件） | 点查慢、扫描快 |
| 写放大 | 中 | **高**（compaction） | 低 |
| 读放大 | 低 | **高**（多层查找） | 高（需解压多列） |
| 空间放大 | 低 | 中（旧版本未清理） | **最低**（压缩率高） |
| 代表 | MySQL、PostgreSQL | RocksDB、HBase、Cassandra、TiKV | ClickHouse、Doris |

**选型口诀**：

```
读多写少 + 点查 → B+ 树
写多读少 + 顺序写 → LSM
分析聚合 + 大扫描 → 列存
```

**追问**："LSM 的写放大有多严重？"
→ 最坏情况一条记录在每层都被重写一次，`写放大 ≈ 层数 × 每层合并次数`；RocksDB 通过 **leveled / tiered / universal** 三种 compaction 策略在写放大和读放大之间权衡。

### 2.2 WAL 与崩溃恢复 ⭐⭐⭐

**所有可靠存储都有 WAL**（Write-Ahead Log）：

```
① 修改先写日志（顺序写 + fsync）
② 再改内存结构
③ 后台异步刷盘（checkpoint）
④ 崩溃后用日志重放
```

**为什么快**：顺序写 + 批量 fsync（组提交）把随机 IO 变成顺序 IO。

**对比三种 WAL**：

| 系统 | 日志内容 | 恢复方式 |
| --- | --- | --- |
| InnoDB redo | 物理逻辑（页的修改） | 从 checkpoint 重放 |
| RocksDB WAL | 写批次（key-value） | 重放到 memtable |
| Kafka | 本身就是日志（不需要额外 WAL） | 依赖副本而不是本地恢复 |

**追问**："WAL 会不会成为瓶颈？"
→ 会，所以有**组提交**（多个事务合并一次 fsync）、**异步刷盘**（牺牲部分可靠性）、**多日志文件并行**（不同磁盘）。

### 2.3 Compaction：LSM 的心脏 ⭐⭐⭐

```
写入 → memtable（内存，跳表）
     → 满了变 immutable memtable → 刷成 L0 文件
     → L0 文件多了 → 合并到 L1（key 有序、不重叠）
     → L1 满了 → 合并到 L2 … 直到 Ln
```

**三种策略**：

| 策略 | 写放大 | 读放大 | 空间放大 | 适用 |
| --- | --- | --- | --- | --- |
| **Leveled**（RocksDB 默认） | 高（~10x） | 低 | 低 | 读多写少 |
| **Tiered** | 低 | 高 | 高 | 写密集（HBase 曾用） |
| **Universal/FIFO** | 最低 | 中 | 中 | 时序数据、TTL 场景 |

**追问**："compaction 造成的毛刺怎么解决？"
→ ① 限速（`rate_limiter`）；② 分离 compaction 线程与写线程；③ 用 **Tiered 存储**（Kafka 分层存储）；④ 预分配 + 独立磁盘。

### 2.4 mmap、Page Cache 与 Direct IO ⭐⭐

| 方式 | 机制 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Page Cache**（read/write） | 内核缓存，第二次读命中内存 | 简单、通用 | 多一次拷贝 |
| **mmap** | 文件映射到虚拟内存 | 无拷贝、随机读快 | 缺页中断、大文件难管理、不可控 |
| **Direct IO** | 绕过 Page Cache | 内存可控 | 需要自己对齐、自己缓存 |

**RocketMQ 为什么用 mmap**：CommitLog 是顺序写 + 随机读（按 ConsumeQueue 定位），mmap 让随机读也走内存，且避免用户态拷贝。

**mmap 的坑**：

```
① 缺页中断（首次访问）→ 毛刺
② 文件被截断/删除 → SIGBUS 崩溃
③ 脏页回写不可控 → 突然的 IO 抖动
④ 大文件（> 数 GB）映射在 32 位系统不可行
```

**面试话术**："我们线上一个基于 mmap 的存储出过 `SIGBUS`，原因是磁盘满了导致文件被截断；后来加了『磁盘水位告警 + 写前检查剩余空间』。"

### 2.5 索引：不只是 B+ 树 ⭐⭐

| 索引 | 原理 | 适用 |
| --- | --- | --- |
| **B+ 树** | 有序，范围查询 | 通用 |
| **哈希索引** | O(1) 点查 | 等值查询（Memory 引擎） |
| **布隆过滤器** | 位数组 + 多哈希，判断"一定不存在" | 减少无效磁盘查（LSM、HBase） |
| **倒排索引** | term → doc list | 全文检索（ES） |
| **跳表** | 多层链表 | Redis ZSet |
| **稀疏索引** | 每 N 条建一个 | Kafka、ClickHouse |
| **位图索引** | 每列一个 bit 数组 | 低基数（性别、状态） |

**布隆过滤器的误判**：

```
false positive（说不存在 → 一定不存在；说存在 → 可能不存在）
参数：m 位、k 个哈希、n 个元素
最优 k = (m/n) * ln2
误判率 ≈ (1 - e^(-kn/m))^k
```

### 2.6 压缩：省的不只是磁盘 ⭐

| 算法 | 压缩率 | 速度 | 场景 |
| --- | --- | --- | --- |
| gzip | 高 | 慢 | 冷数据、日志归档 |
| snappy/lz4 | 中 | **很快** | Kafka、RocksDB（默认） |
| zstd | **高** | 快 | 新一代默认（Kafka 2.1+、RocksDB） |
| zlib | 中高 | 中 | 通用 |

**关键认知**：压缩不仅省磁盘，还**省网络带宽和 IO**；但消耗 CPU。**判断标准是"CPU 是否是瓶颈"**——如果 CPU 空闲而 IO 打满，上压缩；反之不要。

### 2.7 存储选型决策树

```
需要事务 + 点查 + 强一致？
  └─ 是 → B+ 树（MySQL/PG）
  └─ 否 → 写吞吐是否是瓶颈？
        ├─ 是 → LSM（RocksDB/HBase/TiKV）
        └─ 否 → 是否需要大范围聚合？
              ├─ 是 → 列存（ClickHouse/Doris）
              └─ 否 → 是否需要全文检索？
                    ├─ 是 → 倒排（ES）
                    └─ 否 → 内存（Redis）或对象存储
```

## 三、Redis 深水区

> 业务后端问 Redis 停留在"缓存三问题"；中间件面试问的是：
> **集群规模、扩缩容、内存分布、阻塞点、二次开发。**

### 3.1 集群与容量：面试官会追问到具体数字 ⭐⭐⭐

#### （1）分片规模怎么定

| 约束 | 经验值 | 原因 |
| --- | --- | --- |
| 单分片内存 | **10~16GB** | fork/COW 代价、全量同步耗时、故障恢复时间 |
| 单集群分片数 | 几十~几百 | 超过后 gossip 开销、运维复杂度上升 |
| 单机 QPS | 8~10 万 | 单线程 + 网络 RTT |
| 集群总 QPS | 分片数 × 单机 | 但受限于客户端连接与网络 |

**容量估算公式**：

```
分片数 = ceil(总数据量 / 单分片容量) × (1 + 冗余)
例：200GB 数据，单分片 16GB → 13 个分片 → 取 16（主从各 16 台）
QPS 校验：200 万 QPS / 10 万 = 20 个分片 → 取 max(容量, QPS) = 20
```

#### （2）扩缩容：槽迁移的真实代价

```bash
# 迁移槽位
redis-cli --cluster reshard 10.0.0.1:6379
# 或手动：CLUSTER SETSLOT / MIGRATE
```

**迁移过程中会发生什么**：

```
① 目标节点 CLUSTER SETSLOT IMPORTING
② 源节点 CLUSTER SETSLOT MIGRATING
③ 逐个 key MIGRATE（同步复制，阻塞源节点）
④ 迁移完成后广播新拓扑
```

**坑**：

- `MIGRATE` 是**同步阻塞**的，大 key 会导致明显卡顿 → 要**先拆大 key**，或限速（`--cluster-pipeline`）。
- 迁移期间客户端会收到 `ASK` 重定向，**RT 上升**。
- 跨机房迁移带宽成本高。

#### （3）数据倾斜

| 原因 | 表现 | 解决 |
| --- | --- | --- |
| 大 key | 单分片内存/CPU 高 | 拆分 |
| 热 key | 单分片 QPS 高 | 本地缓存、key 打散 |
| 槽分配不均 | 节点间不均衡 | `redis-cli --cluster rebalance` |
| hash tag 使用不当 | 大量 key 落同一槽 | 检查 `{}` 用法 |

### 3.2 持久化与 fork：面试必问的"代价" ⭐⭐⭐

#### （1）fork 到底有多贵

```
fork 耗时 ≈ 页表大小 / 内存带宽
经验值：10GB 实例约 20~50ms；30GB 实例 100ms+
```

**这段停顿对 Redis 是致命的**（单线程），所以：

- 大实例的 RDB/AOF rewrite 要**错峰**。
- 用 `fork` 的频率要控制（`save` 配置不要过密）。
- 可以用 **RDB 关闭 + AOF everysec** 减少 fork。

#### （2）COW 的内存放大

```
fork 后，父进程每写一个页，就复制一份（4KB）
写入比例 30% → 额外内存 ≈ 30% 堆大小
最坏情况（全量写）→ 内存翻倍
```

**这就是"Redis 内存要留 50% 余量"的原因**——不是给数据，是给 COW 和碎片。

#### （3）AOF 的三种刷盘与真实吞吐

| 策略 | fsync 频率 | 吞吐 | 丢失窗口 |
| --- | --- | --- | --- |
| always | 每命令 | 差（几千 QPS） | 0 |
| **everysec** | 每秒 | 好（接近内存） | ≤ 1s |
| no | OS 决定 | 最好 | 不可控（可能几十秒） |

**追问**："everysec 真的只丢 1 秒吗？"
→ 不一定。如果上一秒的 fsync 还没完成，主线程会**阻塞等待**（`aof_buf` 写入延迟），此时性能会抖动；极端情况下（磁盘慢）会退化成 always 的体验。

#### （4）磁盘选型

| 介质 | 建议 |
| --- | --- |
| SSD（NVMe） | 生产标配，AOF fsync 延迟 < 1ms |
| 机械盘 | 只能接受 RDB + 低写入，AOF always 基本不可用 |
| 网络盘（云盘） | 注意 IOPS 上限和抖动 |

### 3.3 内存管理与碎片 ⭐⭐

#### （1）内存分布

```
used_memory           Redis 分配器统计的使用量
used_memory_rss       操作系统看到的物理内存
mem_fragmentation_ratio = rss / used
```

| 比值 | 含义 | 处理 |
| --- | --- | --- |
| < 1 | 用了 swap（**危险**） | 加内存 / 关 swap |
| 1.0~1.5 | 正常 | — |
| > 1.5 | 碎片严重 | `activedefrag yes` 或重启 |

#### （2）碎片产生的原因

```
① 频繁增删不同大小的 key
② 大 key 删除后留下空洞
③ jemalloc 的 size class 不匹配
```

**治理**：

```bash
config set activedefrag yes
config set active-defrag-ignore-bytes 100mb
config set active-defrag-threshold-lower 10
# 或：主从切换（重启从节点）来整理碎片
```

#### （3）内存告警的正确姿势

不要只看 `used_memory`，要看：

```
① maxmemory 使用率（> 80% 告警）
② 碎片率（> 1.5 告警）
③ 淘汰速率（evicted_keys 突增 → 容量不足）
④ 大 key 数量与总大小
```

### 3.4 阻塞点全清单（面试高频）⭐⭐⭐

> "Redis 是单线程的，任何慢操作都会阻塞所有人。"——这句话要能展开成一张表。

| 阻塞源 | 典型命令/场景 | 影响 | 规避 |
| --- | --- | --- | --- |
| **O(N) 命令** | `KEYS *`、`HGETALL` 大 hash、`SMEMBERS` 大集合、`LRANGE 0 -1` | 阻塞数十 ms~秒 | `SCAN` 分批、限制集合大小 |
| **大 key 删除** | `DEL` 一个百万元素的 hash | 同步释放，阻塞 | `UNLINK`（异步）、拆分 |
| **fork** | RDB / AOF rewrite | 20~100ms+ | 大实例错峰、减少 fork |
| **AOF 重写** | 磁盘慢时 | 主线程等 IO | SSD、限速 |
| **全量同步** | 新从节点接入 | 主库 fork + 传输 | 控制从节点数量、用磁盘less 复制 |
| **Lua 脚本** | 死循环 / 大循环 | 阻塞直到超时 | 限制 `lua-time-limit`、脚本要短 |
| **swap** | 内存不足 | 灾难性变慢 | 关 swap / 监控 |
| **持久化阻塞** | `SAVE`（同步） | 全量阻塞 | 禁用 `SAVE`，只用 `BGSAVE` |
| **集群迁移** | `MIGRATE` 大 key | 阻塞 | 拆 key、限速 |

**追问**："怎么发现是哪个命令阻塞的？"
→ ① `SLOWLOG GET`（慢查询日志，阈值 `slowlog-log-slower-than`）；② `LATENCY DOCTOR` / `LATENCY HISTORY`；③ `INFO commandstats` 看调用次数与耗时；④ `MONITOR`（仅短时排障，影响性能）。

### 3.5 二次开发与替代方案 ⭐

| 方案 | 特点 | 适用 |
| --- | --- | --- |
| **Redis Stack** | 官方模块：Search/JSON/TimeSeries/Bloom | 需要搜索/JSON 能力 |
| **Tair**（阿里） | 持久化内存、多线程、数据结构扩展 | 超大规模、降本 |
| **KeyDB** | 多线程 IO/命令，兼容 Redis 协议 | 单机多核利用 |
| **Dragonfly** | 多线程 + 新架构，宣称更高吞吐 | 新项目探索 |
| **Redis Modules** | 自定义命令（C API） | 定制能力 |

**面试话术**："我们评估过 KeyDB，它的多线程能把单机 QPS 提升 2~3 倍，但生态和稳定性不如 Redis，最终选择了**分片 + 客户端多连接**的横向扩展路线。"

## 四、消息中间件

> 消息中间件是中间件面试的"主战场"，因为它同时涉及**存储、网络、一致性、运维**。

### 4.1 三家架构对比 ⭐⭐⭐

| 维度 | Kafka | RocketMQ | Pulsar |
| --- | --- | --- | --- |
| 存储模型 | partition → segment 文件 | 所有 topic → 单一 CommitLog | **存算分离**（Broker + BookKeeper） |
| 元数据 | ZK → **KRaft**（4.0 移除 ZK） | NameServer（无状态） | ZK/etcd + Broker |
| 副本 | ISR（Leader + Follower） | 主从（同步/异步复制） | Bookie 多副本（Quorum） |
| 顺序 | 分区内有序 | 队列内有序 | 分区内有序 |
| 延时消息 | 不支持（需外部） | 原生（18 级 / 5.0 任意时间） | 支持（Delayed Delivery） |
| 事务消息 | 支持（0.11+） | **原生**（半消息 + 回查） | 支持（事务） |
| 多租户 | 弱（靠 topic 前缀） | 中 | **强（tenant/namespace/topic）** |
| 吞吐 | **最高** | 高 | 高 |
| 运维复杂度 | 中 | 中 | **高**（两个集群） |
| 适用 | 日志/埋点/大数据 | 电商交易 | 多租户平台、云原生 |

**RocketMQ 为什么用单一 CommitLog？**

```
Kafka：每 partition 一个文件 → topic/partition 多时（几千个）→ 磁盘随机写严重
RocketMQ：所有消息写同一个 CommitLog（顺序写）→ 适合 topic 数量多的电商场景
代价：读消息要先查 ConsumeQueue（逻辑索引）再回 CommitLog → 读放大
```

**Pulsar 存算分离的代价**：

- 优点：Broker 无状态、扩容快、存储独立扩、支持 Tiered Storage。
- 代价：多一跳网络（Broker → Bookie）、延迟略高、运维两套集群。

### 4.2 副本与一致性 ⭐⭐⭐

#### （1）Kafka 的 ISR / HW / LEO

```
LEO（Log End Offset）：每个副本最后一条消息的位置
HW（High Watermark）：ISR 中最小 LEO，消费者只能读到 HW 之前
ISR：与 Leader 保持同步的副本集合（replica.lag.time.max.ms 内）
```

**追问**："为什么消费者只能读到 HW？"
→ 保证**已提交**语义：HW 之前的消息在多数副本上存在，Leader 挂了也不会丢。

**追问**："`acks=all` 就一定不丢吗？"
→ 不一定。如果 `min.insync.replicas=1`，ISR 只剩 Leader 时也能写入，此时挂了就丢。**必须 `acks=all` + `min.insync.replicas>=2` + `unclean.leader.election=false` 三者配合。**

#### （2）RocketMQ 的主从与 DLedger

| 模式 | 一致性 | 可用性 | 说明 |
| --- | --- | --- | --- |
| 异步复制 | 可能丢 | 高 | 默认 |
| 同步双写 | 不丢（主从都写成功） | 中 | RT 增加 |
| **DLedger（Raft）** | 强 | 中 | 自动选主，无需人工切换 |

**追问**："RocketMQ 主挂了怎么办？"
→ 传统主从**不支持自动切换**（4.x），需要人工或外部组件；5.x + DLedger 支持自动选主。

### 4.3 事务消息与幂等 ⭐⭐

**RocketMQ 事务消息流程**：

```
① 发半消息（对消费者不可见）
② 执行本地事务
③ 返回 COMMIT / ROLLBACK
④ 若 ③ 丢失 → Broker 回查（默认 60s 后，最多 15 次）
⑤ 生产者 checkLocalTransaction 查 DB 返回状态
```

**三个实现细节**：

| 细节 | 说明 |
| --- | --- |
| 回查必须幂等、只读 | 可能被多次调用 |
| 中间态返回 UNKNOW | 本地事务还在执行，让 Broker 稍后再查 |
| 回查次数有上限 | 超过后进死信/告警，需要人工介入 |

**幂等的工程实现**（消费端）：

```java
// 唯一索引兜底 + 去重表 + 状态机
@Transactional
public void consume(OrderMsg msg) {
    // ① 去重表（msgId 唯一索引）
    if (!dedupMapper.insertIgnore(msg.getMsgId())) return;
    // ② 状态机：只有待支付才能改为已支付
    int affected = orderMapper.updateStatus(msg.getOrderId(), PENDING, PAID);
    if (affected == 0) { log.warn("状态已变更，幂等忽略"); return; }
    // ③ 业务
    accountService.credit(msg);
}
```

### 4.4 延时消息的四种实现 ⭐⭐

| 方案 | 精度 | 可靠性 | 说明 |
| --- | --- | --- | --- |
| **RocketMQ 延时等级** | 固定 18 级（1s~2h） | 高 | 5.0 支持任意时间（时间轮 + 定时文件） |
| **RocketMQ 5.0 定时消息** | 秒级任意 | 高 | 推荐 |
| Kafka + 外部调度 | 取决于调度 | 中 | 定时任务扫表 / 时间轮服务 |
| RabbitMQ TTL + 死信 | 秒级 | 高 | 队列头阻塞（TTL 短的会阻塞长的） |
| Redis ZSet | 秒级 | 中 | 简单但有轮询成本 |

**面试追问**："为什么 RabbitMQ 的 TTL + 死信有坑？"
→ 队列是 FIFO，如果队头消息 TTL 很长，后面的短 TTL 消息要等它过期才能出队（**队头阻塞**）。解决：每个延时等级一个队列。

### 4.5 顺序消息：代价与实现 ⭐⭐

```
生产端：按业务 key（orderId）hash 到同一分区/队列
存储端：单分区内天然有序
消费端：单线程消费该分区（或按 key 分发到内存队列，每队列单线程）
```

**代价**：

- 并行度下降（分区数 = 最大并行度）。
- 一个消息卡住会阻塞整个分区（**必须设超时和跳过策略**）。
- 扩分区会打乱 key 的映射（Kafka 扩分区后 key → partition 可能变化）。

**追问**："顺序消费卡住一条怎么办？"
→ ① 设置消费超时，超时后**跳过并记录**（牺牲严格顺序保可用）；② 或用"重试队列 + 人工处理"；③ 关键业务用**状态机 + 幂等**，允许乱序但不允许状态错乱。

### 4.6 积压：面试最爱问的场景题 ⭐⭐⭐

**场景**：Kafka 积压 2 亿条，消费者组 10 个实例，单条处理 20ms，怎么在一晚上追平？

**第一步：算账（面试官最想看到的）**

```
当前消费能力：10 实例 × (1000/20ms) = 500 条/s
2 亿条 / 500 = 40 万秒 ≈ 4.6 天   → 单靠现状不可能

目标：8 小时追平 → 需要 2亿 / (8*3600) ≈ 7000 条/s
→ 需要 14 倍吞吐
```

**第二步：找出瓶颈**

| 可能瓶颈 | 判断方法 |
| --- | --- |
| 消费者实例数 < 分区数 | 加实例立刻见效 |
| 单条处理慢（同步 RPC/DB） | 看火焰图/RT |
| 分区数不足 | 实例加了但部分空闲 |
| 下游限流 | 下游 RT 上升 |

**第三步：组合拳**

```
① 扩消费者到分区数（若分区足够）
② 批量消费（batch 500 条 + 批量写库）→ 吞吐提升 5~10 倍
③ 把同步 RPC 改成异步/批量
④ 临时降级：只做核心逻辑（跳过非必要的校验/通知），先把积压排空
⑤ 扩分区（注意顺序性）或新建高并行 topic 做"搬运"
⑥ 消费端加并发（内存队列 + 多线程，按 key 保序）
```

**第四步：防复发**

```
- 消费延迟监控（lag）告警
- 自动扩容（按 lag 触发）
- 压测消费能力，写入容量基线
- 大促前预扩容
```

**面试话术**："我不会一上来就扩容。**先算清缺口倍数**，再定位是并行度不够还是单条太慢，最后用『批量 + 降级 + 扩容』组合。如果 8 小时也追不平，就要评估**丢弃非核心消息**或**离线补数**。"

### 4.7 选型决策树

```
需要事务消息 / 延时消息 / 顺序消息？
  └─ 是 → RocketMQ

需要极高吞吐 + 日志/埋点 + 与大数据生态集成？
  └─ 是 → Kafka

需要多租户 + 存算分离 + 云原生？
  └─ 是 → Pulsar

规模很小（< 1000 QPS）且团队不熟 MQ？
  └─ 是 → RabbitMQ 或 直接用 DB 队列（别过度设计）
```

### 4.8 新特性（面试加分）⭐

| 特性 | 说明 | 价值 |
| --- | --- | --- |
| **KRaft** | Kafka 用 Raft 替代 ZooKeeper（3.3 预览，4.0 移除 ZK） | 运维简化、元数据扩展性 |
| **Tiered Storage** | 冷数据下沉到对象存储 | 存储成本降 80%+ |
| **Share Group**（KIP-932） | 队列语义（一条消息一个消费者） | 替代"消费组"模型，适合任务队列 |
| **RocketMQ 5.0 Proxy** | gRPC 协议、多语言、无状态 Proxy | 云原生、弹性 |
| **Pulsar Tiered Storage** | 自动分层 | 无限保留 |

**面试话术**："Kafka 4.0 移除 ZK 后，元数据规模不再是瓶颈（ZK 的 10 万分区限制消失），但运维要从『管两套』变成『管一套』，升级路径要提前规划。"

## 五、数据访问中间件

> 这一块是业务后端的"必考区"，也是中间件团队"最容易踩坑"的地方。

### 5.1 连接池：HikariCP 为什么快 ⭐⭐

| 优化 | 说明 |
| --- | --- |
| **FastList** | 替代 `ArrayList`，去掉范围检查（get/remove 更快） |
| **ConcurrentBag** | 无锁的连接获取（ThreadLocal 缓存 + 共享队列） |
| 字节码精简 | 减少方法调用层级 |
| 代理优化 | 用 Javassist 生成代理，避免反射 |
| 延迟初始化 | 启动时不建连接，首次用时才建 |

**关键参数**：

```properties
maximumPoolSize=10          # 经验：CPU 核数 * 2 + 磁盘数，不要太大
minimumIdle=10              # 与 maximumPoolSize 相等，避免频繁创建
connectionTimeout=3000      # 获取连接超时（不是查询超时！）
idleTimeout=600000
maxLifetime=1800000         # 小于 DB 的 wait_timeout
```

**追问**："连接池越大越好吗？"
→ **不是**。连接数超过 DB 的处理能力后，只会增加上下文切换和锁竞争。经验公式：`连接数 ≈ CPU 核数 × 2 + 磁盘数`；实际要压测。

**追问**："`connectionTimeout` 和 `socketTimeout` 的区别？"
→ 前者是**从池里拿连接**的超时；后者是**网络读**的超时。很多"接口超时"其实是拿不到连接（池耗尽）。

### 5.2 读写分离与延迟 ⭐⭐

```
写 → 主库
读 → 从库（可能有延迟）

延迟来源：
① 主库 binlog 落盘慢
② 从库 SQL 线程重放慢（大事务、无主键表、DDL）
③ 网络延迟
④ 从库压力大（读流量本身）
```

**业务兜底手段**：

| 手段 | 说明 | 代价 |
| --- | --- | --- |
| 强制走主库 | 关键读（支付后查订单） | 主库压力 |
| 半同步复制 | 减少丢数据窗口 | RT 增加 |
| 缓存补偿 | 写后删缓存，读不到再查主 | 复杂 |
| 延迟监控 | `Seconds_Behind_Master` + 心跳表 | 需要告警 |

**面试话术**："我们用的是**心跳表**方案——主库每秒写一条时间戳，从库读出来算差值，比 `Seconds_Behind_Master` 更准（后者会被大事务卡住而不更新）。"

### 5.3 ShardingSphere 内核五步 ⭐⭐⭐

```
SQL → ① 解析（Parser）→ AST
    → ② 路由（Router）→ 目标库表
    → ③ 改写（Rewriter）→ 分页/聚合/自增主键改写
    → ④ 执行（Executor）→ 多线程并发
    → ⑤ 归并（Merger）→ 结果集合并
```

**每一步的难点**：

| 步骤 | 难点 |
| --- | --- |
| 解析 | SQL 方言（MySQL/PG/Oracle），复杂 SQL（子查询、窗口函数） |
| 路由 | 分片键缺失 → **广播路由**（全部分片执行，性能差） |
| 改写 | 分页 `LIMIT offset, size` 要改成 `LIMIT 0, offset+size` 再归并截取 |
| 执行 | 连接池管理、并发度控制、超时 |
| 归并 | 排序归并、聚合归并（`AVG` 要改成 `SUM/COUNT`）、分页归并 |

**追问**："跨分片分页为什么慢？"
→ 每个分片都要取 `offset + size` 条 → 内存归并 → 再截取。**offset 越大越慢**，所以要用**游标分页**或**二次查询**。

**追问**："分片键怎么选？"
→ ① 覆盖 80% 的查询；② 分布均匀；③ 不跨片（如按 `user_id` 分片，则所有查询带 `user_id`）；④ 避免热点（如按 `merchant_id` 可能大商家倾斜）。

### 5.4 分片算法与扩容 ⭐⭐

| 算法 | 优点 | 缺点 |
| --- | --- | --- |
| `hash(分片键) % N` | 简单、均匀 | **扩容要 rehash 全部数据** |
| `range`（按 ID 区间） | 扩容简单（加新区间） | 热点（新数据集中） |
| **一致性哈希** | 扩容只迁移部分 | 实现复杂、可能倾斜（需虚拟节点） |
| **双倍扩容**（如 2→4→8） | 只迁移一半 | 需要成倍扩容 |

**扩容的工程做法**：

```
① 停机迁移（最简单，但不可接受）
② 双写 + 数据同步 + 灰度切读（推荐）
③ 影子表 + binlog 同步 + 原子切换
```

**面试话术**："我们用的是一致性哈希 + 虚拟节点，一次扩容只迁移 1/N 的数据；但业务上更推荐**预分片**（一开始就分 1024 片，映射到少量物理库），这样扩容只需改映射，不用搬数据。"

### 5.5 CDC 与数据同步 ⭐⭐

```
MySQL binlog → Canal/Debezium → Kafka → 下游（ES/缓存/数仓）
```

| 环节 | 关键点 |
| --- | --- |
| binlog 格式 | 必须 **ROW**（STATEMENT 无法还原行变更） |
| 位点管理 | 记录 `binlog file + position` 或 GTID |
| 幂等 | 下游按主键 upsert |
| 顺序 | 同一主键的变更要保序（按主键 hash 到同一分区） |
| 全量 + 增量 | 先全量快照，再切增量（注意快照期间的一致性） |
| DDL | 要同步表结构变更（否则解析失败） |

**追问**："Canal 挂了重启，怎么保证不丢不重？"
→ 位点持久化 + 下游幂等；**不丢靠位点，不重靠幂等**。

### 5.6 分布式事务中间件 ⭐

| 方案 | 代表 | 特点 |
| --- | --- | --- |
| XA | MySQL XA、Atomikos | 强一致，性能差 |
| **AT** | Seata | 自动补偿（undo_log），业务无侵入 |
| TCC | Seata TCC | 业务侵入，灵活 |
| SAGA | Seata SAGA | 长流程，补偿 |
| 消息最终一致 | RocketMQ 事务消息 | 最常用 |

**Seata AT 的核心**：

```
一阶段：拦截 SQL → 生成前镜像/后镜像 → 写 undo_log → 提交本地事务
        （同时申请全局锁，保证写隔离）
二阶段：成功 → 异步删 undo_log
        失败 → 用前镜像反向补偿
```

**追问**："AT 的全局锁会不会成为瓶颈？"
→ 会。所有写操作都要抢全局锁，高并发下退化成串行。**所以高并发写场景不用 AT，用消息最终一致。**

## 六、注册中心与配置中心

> 这类中间件的面试特点是：**规模一放大，所有简单方案都会失效**。
> 「10 个服务」和「10 万个实例」需要的是完全不同的设计。

### 6.1 四家对比：CAP 的工程实践 ⭐⭐⭐

| 维度 | Nacos | Eureka | ZooKeeper | etcd |
| --- | --- | --- | --- | --- |
| 一致性 | AP（临时实例）/ CP（持久实例） | **AP** | **CP**（ZAB） | **CP**（Raft） |
| 健康检查 | 心跳（客户端上报）+ 服务端探测 | 客户端心跳 | Session + 临时节点 | Lease + 心跳 |
| 配置中心 | ✅ 内置 | ❌ | 可用（watch） | 可用（watch） |
| 推送模型 | 1.x 长轮询；**2.x gRPC 长连接** | 客户端拉取（30s） | Watch（一次性） | Watch（长连接） |
| 规模 | 十万级 | 万级 | 万级（ZK 不适合超大注册） | 万级（受 Raft 写限制） |
| 运维 | 中 | 低 | 中 | 中 |
| 典型问题 | 2.x 连接数暴涨 | 自我保护导致读到旧实例 | 脑裂、Session 超时 | 写性能受 Raft 限制 |

**为什么注册中心更适合 AP？**

```
服务列表短暂不一致（多了一个已下线的实例）→ 客户端重试后自愈
注册中心不可用 → 所有服务无法发现 → 全站故障

→ 可用性远比一致性重要
```

**但注意**：Nacos 的**持久实例**（`ephemeral=false`）走 CP，用于 DNS 场景或需要强一致的注册。

### 6.2 健康检查与摘除：细节决定事故 ⭐⭐⭐

| 机制 | 说明 | 参数（Nacos 默认） |
| --- | --- | --- |
| 客户端心跳 | 临时实例每 5s 上报 | `heartbeat-interval=5s` |
| 不健康标记 | 15s 未收到心跳 | 标记不健康（仍可被发现） |
| 实例剔除 | 30s 未收到心跳 | 从列表移除 |
| 保护阈值 | 健康实例比例低于阈值时，**不剔除**（返回全部） | `protect-threshold` |

**"保护阈值"的设计哲学**：

```
如果健康实例 < 阈值 → 说明可能是注册中心/网络问题，而不是实例真的挂了
→ 宁可返回不健康的实例（客户端可能还能连通），也不要返回空列表（直接 100% 失败）
```

**追问**："实例被摘除后，客户端多久感知？"
→ 取决于：① 注册中心推送延迟；② 客户端本地缓存刷新；③ 负载均衡器的连接池。**端到端可能几秒到几十秒**，所以**优雅下线**必须"先从注册中心摘除 → 等待 → 再停进程"。

### 6.3 配置推送：长轮询 vs 长连接 ⭐⭐

#### （1）Nacos 1.x 的长轮询

```
客户端：POST /listener {dataId, group, md5}  → 服务端 hold 住（默认 30s）
服务端：期间有变更 → 立即返回；无变更 → 29.5s 后返回空（客户端重新发起）
```

**优点**：实现简单、兼容性好。
**缺点**：每次都要建 HTTP 连接，10 万实例 = 10 万连接 + 大量请求。

#### （2）Nacos 2.x 的 gRPC 长连接

```
客户端启动时建立 gRPC 长连接（双向流）
→ 服务端主动推送变更
→ 连接复用，心跳由 gRPC 维护
```

**优点**：连接数大幅下降、推送实时。
**缺点**：长连接管理复杂（断线重连、连接迁移）、服务端内存压力。

**追问**："配置变更怎么保证所有实例都收到？"
→ ① 推送 + 客户端 ACK/重试；② 客户端定时**全量比对**（兜底）；③ 版本号/MD5 校验。

### 6.4 脑裂与一致性 ⭐⭐

| 系统 | 脑裂风险 | 机制 |
| --- | --- | --- |
| ZooKeeper | **有**（旧主可能继续服务） | 过半机制 + epoch（zxid），旧主无法提交 |
| etcd | 有 | Raft term + 过半，少数派无法写入 |
| Eureka | 无（AP） | 自我保护：网络分区时**保留所有实例**，宁可读到旧数据 |
| Nacos | 临时实例 AP（Distro 协议） | 各节点异步复制，可能短暂不一致 |

**Eureka 的自我保护**：

```
如果在 15 分钟内，心跳续约失败比例 > 85%
→ 认为网络故障，不再剔除任何实例
→ 代价：可能把已下线的实例继续返回给客户端
```

**面试话术**："Eureka 的自我保护是**用一致性换可用性**的典型：网络抖动时，它宁愿让你读到可能已下线的实例（客户端重试可自愈），也不愿把整个列表清空。"

### 6.5 百万实例的挑战（中间件研发必考）⭐⭐⭐

**问题拆解**：

| 挑战 | 量级 | 方案 |
| --- | --- | --- |
| 连接数 | 100 万长连接 | 单机 10 万 → 10 台接入层；用 gRPC/自定义协议减少内存 |
| 内存 | 每实例元数据 ~1KB → 1GB | 分片存储（按 service 哈希） |
| 推送风暴 | 一次发布通知 10 万实例 | 分级推送（按变更范围）、批量合并、限速 |
| 心跳风暴 | 100 万 × 每 5s = 20 万 QPS | 服务端批量处理、随机化心跳周期 |
| 全量拉取 | 客户端启动拉全量 | 分页拉取 + 增量推送 |
| 多机房 | 跨机房延迟 | 单元化部署 + 跨机房异步同步 |

**架构设计**：

```
接入层（无状态，长连接）→ 会话层（记录 clientId → 连接）
                        → 元数据层（分片存储，按 service 哈希）
                        → 一致性层（Distro/Raft）
                        → 控制面（推送编排、限流）
```

**关键决策**：

- **推还是拉**：**推 + 拉兜底**。推送实时，拉取保证最终一致。
- **心跳谁来发**：客户端发（简单、可控）vs 服务端探测（准，但成本高）。
- **数据分片**：按 `serviceName` 哈希，避免单节点存全部。
- **变更合并**：1 秒内的多次变更合并成一次推送。

## 七、网关与服务治理

> 网关是"流量的第一道门"，面试重点：**动态能力、性能、稳定性**。

### 7.1 网关选型 ⭐⭐

| 网关 | 语言/模型 | 动态配置 | 性能 | 适用 |
| --- | --- | --- | --- | --- |
| **Nginx/OpenResty** | C + Lua | `lua-resty` + 共享内存 | **极高** | 流量入口、静态资源 |
| **APISIX** | OpenResty + etcd | **etcd watch，秒级** | 高 | 云原生 API 网关 |
| **Envoy** | C++ + xDS | xDS 协议 | 极高 | Service Mesh Sidecar |
| **Spring Cloud Gateway** | Java + WebFlux | 配置中心刷新 | 中 | Java 体系内部网关 |
| **Kong** | OpenResty + PostgreSQL | Admin API | 高 | 传统 API 管理 |

**选型判据**：

```
纯流量入口 + 高性能 → Nginx/APISIX
Service Mesh → Envoy
Java 团队 + 需要业务定制 → Spring Cloud Gateway
需要插件生态 + 可视化 → Kong/APISIX
```

**追问**："Spring Cloud Gateway 为什么性能不如 APISIX？"
→ ① JVM 的 GC 和内存开销；② WebFlux 的 Reactor 抽象有成本；③ 每请求要经过多个 Filter。但它的优势是**用 Java 写业务逻辑方便**。

### 7.2 动态路由与热更新 ⭐⭐

| 方案 | 原理 | 生效速度 |
| --- | --- | --- |
| Nginx reload | 重新加载配置（worker 优雅退出） | 秒级，但会短暂占用资源 |
| OpenResty + shared dict | Lua 读共享内存 | 毫秒级 |
| APISIX + etcd | watch 变更，增量更新 | 毫秒~秒 |
| Envoy + xDS | 控制面推送 | 毫秒~秒 |
| SCG + Nacos | 事件刷新 RouteDefinition | 秒级 |

**追问**："reload 有什么风险？"
→ ① 老 worker 要等连接处理完（长连接可能很久）；② 频繁 reload 会导致内存碎片和 CPU 抖动；③ 配置写错会全量失败。**所以生产用增量更新而不是 reload。**

### 7.3 限流：算法与 Sentinel 内核 ⭐⭐⭐

| 算法 | 原理 | 突发流量 | 代表 |
| --- | --- | --- | --- |
| 固定窗口 | 每秒计数清零 | 临界双倍 | 简单实现 |
| **滑动窗口** | 把 1s 拆成 N 个桶 | 平滑 | **Sentinel** |
| 漏桶 | 固定速率流出 | 不允许突发 | Nginx `limit_req` |
| **令牌桶** | 固定速率放令牌，可攒 | **允许突发** | Guava `RateLimiter` |

**Sentinel 的 LeapArray 滑动窗口**：

```java
// 简化逻辑
long timeId = timeMillis / windowLengthInMs;
int idx = (int) (timeId % array.length());
WindowWrap<Window> window = array[idx];

if (window.windowStart() == timeMillis - timeMillis % windowLengthInMs) {
    // 当前窗口，直接累加
    window.value().add(count);
} else {
    // 过期窗口，重置（CAS 保证只有一个线程重置）
    window.resetTo(startTime);
}
```

**追问**："Sentinel 和 Guava RateLimiter 的区别？"
→ Sentinel 是**统计驱动**（统计 QPS/RT/异常数，超过阈值才限流），支持**热点参数限流、系统自适应限流、熔断**；Guava 是**纯令牌桶**，只做速率控制。

**集群限流怎么做**：

```
① Redis + Lua（全局计数）→ 每次请求一次网络往返，性能差
② 令牌桶预分配（每个实例分一部分配额）→ 简单但不精确
③ Sentinel 集群流控（Token Server 统一分配）→ 精确，但 Token Server 是单点
```

### 7.4 熔断与隔离 ⭐⭐

**熔断状态机**：

```
CLOSED（正常）
  → 错误率/慢调用比例超阈值 → OPEN（拒绝，快速失败）
  → 等待窗口 → HALF_OPEN（放少量请求试探）
  → 成功 → CLOSED；失败 → OPEN
```

**隔离的两种方式**：

| 方式 | 原理 | 开销 | 适用 |
| --- | --- | --- | --- |
| **线程池隔离** | 每个依赖一个线程池 | 大（线程切换） | 强隔离、可超时中断 |
| **信号量隔离** | 计数信号量限制并发 | 小 | 高频调用、无需中断 |

**追问**："为什么 Hystrix 后来被 Sentinel 替代？"
→ Hystrix 的线程池隔离开销大、不再维护；Sentinel 用信号量 + 统计窗口，轻量且功能更全（热点、系统规则）。

### 7.5 认证鉴权 ⭐

| 方案 | 说明 | 坑 |
| --- | --- | --- |
| **JWT** | 无状态，网关本地验签 | 无法立即吊销（要配黑名单/短 TTL） |
| OAuth2 | 授权码/客户端凭证 | token 交换有延迟 |
| Session | 有状态，网关查 Redis | 每次请求一次 Redis 查询 |
| **mTLS** | 双向证书 | 证书管理复杂（Service Mesh 常用） |

**网关统一鉴权 vs 服务内鉴权**：

```
网关统一：一次校验，服务内免鉴权；但网关成为信任边界，内网被攻破就全裸
服务内：更安全，但重复实现

推荐：网关做"粗粒度认证"（是否登录、租户是否有效）+ 服务做"细粒度授权"（能不能操作这个资源）
```

### 7.6 网关性能优化 ⭐⭐

| 手段 | 收益 |
| --- | --- |
| 连接复用（upstream keepalive） | 减少 TCP/TLS 握手 |
| HTTP/2 或 gRPC | 多路复用 |
| 零拷贝（静态文件） | 减少内存拷贝 |
| 本地缓存（路由/鉴权结果） | 减少远程调用 |
| 异步日志 | 避免同步写盘 |
| 动静分离（CDN） | 网关只处理动态请求 |
| 内核参数调优 | `somaxconn`、`tcp_tw_reuse`、文件描述符 |

**追问**："网关的 P99 怎么优化？"
→ ① 找出长尾来源（GC/JIT/锁/日志/下游）；② 连接池预热；③ 关闭不必要的 Filter；④ 用 `SO_REUSEPORT` 多进程；⑤ 压测定基线。

## 八、搜索与 OLAP

### 8.1 Lucene 倒排与段合并 ⭐⭐⭐

```
文档 → 分词（analyzer）→ 倒排表（term → posting list）
     → 写入内存 buffer → refresh 生成 segment → 可搜索
     → 后台 merge 合并小段 → 物理删除
```

| 概念 | 说明 |
| --- | --- |
| **segment** | 不可变的索引单元，每次 refresh 生成新段 |
| **refresh** | 内存 buffer → 文件系统缓存（1s，近实时的来源） |
| **flush** | fsync + 清 translog（持久化） |
| **merge** | 合并段，回收被标记删除的文档 |

**追问**："为什么删除是标记删除？"
→ segment 不可变，删除只是打标记（`.del` 文件），真正回收在 merge 时。

**追问**："merge 会有什么影响？"
→ 磁盘 IO 和 CPU 飙升，查询变慢（**merge 风暴**）。控制 `index.merge.policy`、用 SSD、错峰。

### 8.2 ES 集群与分片 ⭐⭐

**写入流程**：

```
协调节点 → 按 routing（默认 _id）hash → 主分片
        → 主分片写 index buffer + translog
        → 并行复制到副本
        → 返回
```

**关键参数**：

| 参数 | 说明 |
| --- | --- |
| `number_of_shards` | 建索引时固定，后期只能 reindex |
| `number_of_replicas` | 可动态改 |
| `refresh_interval` | 默认 1s，批量导入时可设 -1 |
| `translog.durability` | `request`（每次 fsync）/ `async`（默认 5s） |

**脑裂**：

```
discovery.seed_hosts + cluster.initial_master_nodes 配置错误
→ 两个 master 各自维护集群
→ 数据分裂

7.x 起用 cluster.initial_master_nodes 引导，且需要多数派投票
```

**追问**："分片数怎么定？"
→ 单分片 30~50GB，按 3 年数据量算；**宁少勿多**（分片过多导致元数据和查询 fan-out 成本高）。

### 8.3 ES 性能与稳定性 ⭐⭐

| 问题 | 方案 |
| --- | --- |
| 深分页 | `search_after` + PIT，或 `scroll`（导出） |
| 聚合慢 | 预聚合（物化视图/宽表）、`doc_values`、减少桶数量 |
| 写入慢 | 批量 `bulk`、`refresh_interval=-1`、副本数临时设 0 |
| 内存压力 | 堆不超过 32GB（指针压缩）、留一半给 page cache |
| 熔断 | `indices.breaker` 防止 OOM |
| 慢查询 | `slowlog`、profile API |

### 8.4 ClickHouse vs Doris vs StarRocks ⭐⭐

| 维度 | ClickHouse | Doris | StarRocks |
| --- | --- | --- | --- |
| 架构 | Shared-nothing | MPP（FE + BE） | MPP（FE + BE/CN） |
| 点查 | 弱（不适合） | 中 | 中 |
| 大宽表聚合 | **极强** | 强 | 强 |
| Join | 弱（需大表在右） | 强 | **强（CBO）** |
| 更新/删除 | 弱（Mutation 异步） | 支持 | 支持 |
| 高并发点查 | 弱 | 中 | **强** |
| 运维 | 简单 | 中 | 中 |

**选型**：

```
日志/埋点/大宽表聚合 → ClickHouse
需要 Join + 更新的实时数仓 → Doris / StarRocks
高并发点查 + 实时分析 → StarRocks
```

### 8.5 实时数仓链路

```
业务库 → CDC（Canal/Flink CDC）→ Kafka → Flink（清洗/聚合/维表 join）
       → 存储（ClickHouse/Doris/ES/HBase）→ 查询服务
```

**关键点**：

| 点 | 说明 |
| --- | --- |
| 数据质量 | 空值、脏数据过滤、schema 演进 |
| 一致性 | 幂等写（主键 upsert）、exactly-once（两阶段提交） |
| 时效 | 分钟级 vs 秒级（取决于链路） |
| 维表 join | 广播状态、Lookup join（注意缓存） |
| 回溯 | 保留 Kafka 原始数据，支持重放 |

## 九、分布式协调、锁与调度

### 9.1 ZooKeeper vs etcd ⭐⭐

| 维度 | ZooKeeper | etcd |
| --- | --- | --- |
| 协议 | ZAB（类 Paxos） | **Raft** |
| 数据模型 | 树（ZNode） | 扁平 key + 前缀 |
| Watch | **一次性**（要重新注册） | **长连接 + revision**（不丢事件） |
| 租约 | Session（临时节点） | **Lease（显式 TTL）** |
| 读一致性 | 读可能读到旧值（需 `sync()`） | 默认线性一致读（ReadIndex） |
| 规模 | 万级节点 | 万级（受 Raft 写限制） |
| 典型用途 | Kafka（旧）、HBase、Dubbo | K8s、APISIX、Nacos（部分） |

**追问**："ZK 的 Watch 为什么要一次性？"
→ 简化服务端实现（不用维护长期订阅和推送状态）；代价是客户端要重新注册，且**可能丢事件**（在重新注册前发生的变化）。

**追问**："etcd 的 Watch 为什么不会丢？"
→ Watch 带 `revision`，服务端从该 revision 开始推送所有变更；如果历史被压缩（`--auto-compaction`），客户端会收到 `compacted` 错误，需要全量重新拉取。

### 9.2 分布式锁服务化

**业务直接用 Redis 锁的问题**：

```
① 每个业务自己实现，逻辑不一致
② 锁的粒度、超时、续期没有统一规范
③ 无法观测（谁在等锁、等了多久）
④ 无法审计
```

**锁服务的设计**：

| 能力 | 说明 |
| --- | --- |
| 统一 API | `tryLock(key, ttl, timeout)` |
| 自动续期 | 看门狗 / 租约 |
| 可重入 | 同一线程/请求 ID |
| 公平性 | 排队（可选） |
| 可观测 | 等待时长、持有时间、超时次数 |
| **安全性** | **fencing token**（最关键） |

**基于 etcd 的实现（更可靠）**：

```
① 创建 lease（TTL）
② 在 /locks/{key} 下创建临时顺序节点（Put with lease）
③ 检查自己是不是最小序号 → 是则获得锁
④ 否则 watch 前一个节点
⑤ 释放：删除 key（lease 过期也会自动删）
```

**为什么 etcd/ZK 比 Redis 更可靠**：基于**租约 + 会话**，且是 CP 的；Redis 主从切换可能丢锁。

**但要注意**：即使 etcd，也不能完全避免"持有者 GC 后不知道锁丢了"。**严格场景必须加 fencing token**。

### 9.3 分布式任务调度平台

**核心组件**：

```
调度中心（选主）→ 触发（cron/延时/依赖）
              → 分片 → 下发 Executor
              → 执行 → 回调 → 日志/告警
```

**关键设计**：

| 问题 | 方案 | 坑 |
| --- | --- | --- |
| 调度中心高可用 | 选主（ZK/etcd/DB） | 主备切换期间的漏触发 |
| 任务分片 | `hash(id) % shardTotal` | 扩容要 rebalance |
| 重复执行 | 执行状态表 + 唯一键 | 超时重派导致双跑 |
| 失败重试 | 指数退避 + 最大次数 | 无限重试打垮下游 |
| 阻塞调度 | 上一次没跑完就跳过（`blocking=false`） | 长任务会堆积 |
| 日志 | 执行日志分片存储 | 大量小文件 |
| 弹性 | Executor 动态上下线 | 分片重分配导致重复 |

**"防重复执行"的正确做法**：

```sql
-- 执行记录表：唯一键 (job_id, scheduled_time, shard_index)
INSERT INTO job_execution (job_id, scheduled_time, shard_index, status)
VALUES (?, ?, ?, 'RUNNING');
-- 唯一索引冲突 → 说明已执行，直接返回
```

### 9.4 选主与 Lease ⭐

| 方案 | 实现 | 问题 |
| --- | --- | --- |
| ZK 临时节点 | 抢 `/leader` | Session 超时误判 |
| etcd Lease | 租约续期 | 时钟/网络抖动 |
| DB 乐观锁 | `UPDATE ... WHERE leader = ?` | 性能差、单点 |
| Redis SETNX | TTL | 主从丢锁 |

**"选主"的本质问题是同一个**：**如何确认持有者还活着**。所有方案都只能做到"尽力"，区别在于**误判的概率和后果**。

## 十、中间件可观测与运维

> 这一章是"中间件研发"和"只会用"的最大区别：
> **你能不能对一个集群的生命周期负责。**

### 10.1 每个中间件该看什么指标 ⭐⭐⭐

| 中间件 | 核心指标 | 告警建议 |
| --- | --- | --- |
| **Redis** | 内存使用率、碎片率、命中率、`evicted_keys`、`blocked_clients`、慢查询数、fork 耗时 | 内存 > 80%、碎片 > 1.5、命中率骤降 |
| **Kafka** | 消费 lag、ISR 数量、`UnderReplicatedPartitions`、磁盘使用率、请求 RT | lag 持续增长、ISR < 副本数 |
| **RocketMQ** | 堆积量、消费 TPS、发送失败率、DLQ 数量 | 堆积 > 阈值、DLQ 增长 |
| **MySQL** | QPS/TPS、慢 SQL、连接数、`Innodb_row_lock_waits`、复制延迟、Buffer Pool 命中率 | 连接数 > 80%、延迟 > 5s |
| **ES** | 集群状态（green/yellow/red）、分片数、JVM 老年代、merge 耗时、查询 RT | 状态非 green、堆 > 75% |
| **注册中心** | 实例数、心跳 QPS、推送延迟、连接数 | 实例数突变、推送延迟 > 5s |
| **网关** | QPS、RT、5xx、限流次数、上游健康 | 5xx 突增、限流比例高 |

**指标之外的三样东西**：

```
① 日志：错误日志、慢日志、GC 日志
② 链路：请求在中间件里的耗时（span）
③ 事件：发布、扩缩容、故障、变更（和指标对齐，才能解释"为什么变了"）
```

### 10.2 故障演练：中间件团队的必修课 ⭐⭐

| 演练 | 验证什么 | 常见失败 |
| --- | --- | --- |
| 杀主节点 | 自动切换、客户端重连 | 切换期间大量超时，客户端无重试 |
| 网络分区 | 脑裂保护、一致性 | 双主写入 |
| 磁盘满 | 降级、告警 | 写入失败但无告警，应用直接报错 |
| 慢盘 | 超时、熔断 | 线程池被拖死 |
| 流量突增 10 倍 | 限流、扩容 | 扩容跟不上，雪崩 |
| 消费者全挂 | 堆积告警、自动重启 | 没人发现，直到业务反馈 |

**演练报告要写什么**：

```
① 假设（我们以为会发生什么）
② 实际操作
③ 实际现象（和假设的差异）
④ 暴露的问题（按严重程度）
⑤ 改进项（owner + deadline）
⑥ 下次演练计划
```

### 10.3 扩缩容与升级 ⭐⭐

**扩容的三种场景**：

| 场景 | 做法 | 风险 |
| --- | --- | --- |
| 加副本（读扩展） | 直接加从节点 | 全量同步压力 |
| 加分片（写扩展） | 迁移槽/重平衡 | 迁移期间 RT 上升 |
| 加集群（水平拆） | 业务路由到新集群 | 数据迁移、双写 |

**升级的正确姿势**：

```
① 先在预发/灰度集群验证
② 滚动升级（一次一个节点，等同步追上）
③ 观察核心指标（RT、错误率、副本同步）
④ 准备好回滚（镜像/包保留）
⑤ 避开业务高峰
```

**版本升级的坑**：

- **协议不兼容**（客户端旧版本连不上新服务端）
- **数据格式变更**（需要迁移工具）
- **默认参数变化**（新版本默认值不同，行为变了）
- **废弃特性**（如 Kafka 4.0 移除 ZK）

### 10.4 多租户隔离 ⭐⭐

| 隔离级别 | 说明 | 成本 |
| --- | --- | --- |
| **逻辑隔离** | namespace + 配额 + 限流 | 低（一个集群） |
| **物理隔离** | 独立集群/独立节点 | 高 |
| **混合** | 大租户独立，小租户共享 | 中 |

**必须做的四件事**：

```
① 配额（namespace 级别的存储/连接/QPS 上限）
② 限流（防止单租户打满）
③ 计量（按租户统计用量，用于计费/成本分摊）
④ 隔离故障（一个租户的慢查询不影响别人 → 可能需要独立线程池/队列）
```

### 10.5 成本优化：中间件团队的 KPI ⭐

| 手段 | 收益 | 风险 |
| --- | --- | --- |
| 集群合并（小集群 → 大集群） | 资源利用率提升 30~60% | 故障爆炸半径变大 |
| 冷热分离（Tiered Storage） | 存储成本降 50~80% | 冷数据读延迟 |
| 压缩（zstd） | 存储降 40%，带宽降 | CPU 上升 |
| 弹性伸缩 | 闲时缩容 | 冷启动、抖动 |
| 容量水位提升（60% → 75%） | 省机器 | 故障时缓冲变小 |

**面试话术**："降本不能只砍资源，要同时**重新算容量基线**和**调整限流**，否则就是把稳定性换成成本。"

## 十一、自研中间件设计题（7 道）

> 这是中间件研发岗的"压轴题"。回答框架统一：
> **需求 → 核心设计 → 难点 → 失败模式 → 演进**

### 11.1 设计一个 RPC 框架

**需求**：服务间调用，高性能、可扩展、支持多种序列化与负载均衡。

**核心设计**：

```
客户端：动态代理 → 序列化 → 编码 → 连接池 → 发送 → 等待响应（requestId 匹配）
服务端：解码 → 反序列化 → 线程池执行 → 编码响应
治理：注册中心、负载均衡、超时、重试、熔断、链路追踪
```

**关键决策**：

| 决策 | 选项 | 结论 |
| --- | --- | --- |
| 协议 | HTTP / 自定义二进制 | **自定义**（省 header、支持多路复用） |
| 序列化 | JSON / Protobuf / Hessian | **可插拔**，默认 Protobuf |
| 连接 | 短连接 / 长连接 / 多路复用 | **长连接 + requestId 多路复用** |
| 线程模型 | 每请求一线程 / Reactor | **主从 Reactor + 业务线程池** |
| 超时 | 客户端 / 服务端 | **都要有，客户端略大** |

**难点**：

- **粘包**（长度字段）
- **请求响应匹配**（requestId + Future）
- **超时后迟到的响应**（要丢弃，避免内存泄漏）
- **优雅上下线**（先摘除 → 等在途请求 → 关闭）

**失败模式**：服务端 OOM（请求队列无界）、客户端线程泄漏（Future 未清理）、序列化漏洞。

### 11.2 设计一个消息队列

**需求**：高吞吐、持久化、多消费组、顺序、至少一次。

**核心设计**：

```
存储：CommitLog（顺序写）+ 索引（ConsumeQueue）
副本：主从同步 / Raft
消费：拉模式 + 位点管理
```

**难点**：

| 难点 | 方案 |
| --- | --- |
| 顺序写 + 随机读 | mmap / page cache 预热 |
| 消费位点 | 服务端存 / 客户端存（可重放） |
| 消息堆积 | 磁盘容量规划、TTL、降级 |
| 重复消费 | 业务幂等 |
| 事务消息 | 半消息 + 回查 |
| 多消费组 | 每个组独立位点 |

**失败模式**：磁盘满、副本同步落后、消费位点丢失、Rebalance 风暴。

### 11.3 设计一个注册中心

### 12.2 详细复盘一：Redis 集群 CPU 打满

```
现象：Redis 集群某分片 CPU 100%，客户端大量超时，P99 从 1ms 涨到 2s
影响：依赖该分片的订单查询接口 30% 超时，持续 12 分钟

定位：
① 看监控：该分片 QPS 不高（2 万），但 CPU 满 → 不是流量问题
② SLOWLOG：大量 HGETALL（单个 hash 80 万字段，耗时 800ms）
③ 业务排查：某活动的购物车 hash 没有设上限，一个用户加了 80 万个商品

根因：大 key + O(N) 命令，单线程被阻塞

修复：
① 紧急：删除该 key（用 UNLINK 异步），并对该用户做限流
② 短期：购物车加数量上限（200），HGETALL 改为 HMGET 分批
③ 长期：
   - 大 key 巡检（每日 `--bigkeys`）
   - 代码规范禁止对无上限集合用 O(N) 命令
   - 加"单命令耗时"告警

预防：把"大 key"纳入上线 checklist；压测时构造大 key 场景
```

### 12.3 详细复盘二：Kafka Rebalance 风暴

```
现象：消费 lag 从 0 涨到 500 万，消费者日志大量 "Rebalance"
影响：下游数仓数据延迟 40 分钟

定位：
① 消费者实例数 20，分区数 40 → 资源够
② 日志显示每 2~3 分钟一次 Rebalance
③ 看 GC 日志：单次 Full GC 12s > session.timeout.ms(10s)
   → 心跳线程也停了 → 被踢出组 → 触发 Rebalance

根因：消费者堆内存不足 + 单条消息处理可能产生大对象 → Full GC 超时

修复：
① 紧急：扩容消费者堆内存，临时调大 session.timeout.ms
② 中期：优化消费逻辑（批量、减少对象创建）
③ 长期：静态成员（group.instance.id）避免重启触发 rebalance；
        监控 GC 与 rebalance 次数

预防：消费端堆内存基线 + GC 告警；压测时观察 rebalance
```

### 12.4 详细复盘三：分库分表后列表页变慢

```
现象：订单列表接口 P99 从 80ms 涨到 900ms
影响：全部用户

定位：
① 慢查询日志显示 SQL 被广播到 32 个分片
② 原因：新需求"按状态查订单列表"，SQL 里没有 user_id
③ 分片键是 user_id → 无分片键 → 广播路由 → 32 个分片各查 1 万行 → 归并

根因：查询模式与分片键不匹配

修复：
① 短期：强制前端传 user_id（C 端页面本来就有）
② 中期：状态维度建**异构索引表**（status → order_id），异步同步
③ 长期：列表页改走 ES（已同步订单数据）

预防：新 SQL 上线前必须 EXPLAIN + 确认分片键；建立"广播路由"告警
```

### 12.5 讲故障的模板（背下来）

```
① 一句话现象 + 影响面（多少用户/订单，持续多久）
② 定位过程（用了什么工具，看到了什么异常，排除了什么）
③ 根因（一句话，要具体到"什么条件下触发什么"）
④ 止血 + 修复（临时 vs 根本）
⑤ 预防（监控/流程/代码规范，最好有机制）
⑥ 反思（如果重来，哪里可以更早发现）
```

## 十五、面试话术模板

### 15.1 讲原理：三段式

```
① 一句话定位："Kafka 的存储本质是『分区 + 分段 + 稀疏索引』。"
② 展开关键设计："这样做的收益是……代价是……"
③ 落到实践："所以我们在 X 场景下选了 Y。"
```

### 15.2 讲选型：决策矩阵

```
"我列了四个维度（性能/成本/运维/团队熟悉度），权重分别是……，
两个方案得分接近，所以最终是**组合使用**：A 做主，B 兜底。"
```

### 15.3 讲故障：六段式

```
现象 → 影响 → 定位 → 根因 → 修复 → 预防
（每条都要有工具/数字，不要只说"我们排查了一下"）
```

### 15.4 讲设计：五步

```
需要澄清的 → 量级估算 → 架构草图 → 关键决策与代价 → 失败模式
```

### 15.5 不会的时候怎么说

```
"这块我没有在生产环境深度实践过，我的理解是……（讲原理）。
 如果是我做，我会先验证 X，因为它是最大的不确定性。"
```

**不要编**。中间件的细节很容易被追问穿，承认边界 + 给出思路，比胡说得分高。

## 写在最后

中间件面试的核心不是"记住多少组件"，而是：

1. **能不能把一个组件的设计动机讲清楚**（为什么这么设计）。
2. **能不能算清容量与代价**（多少机器、多少延迟、多少成本）。
3. **能不能在故障时不慌**（工具、路径、止损）。
4. **能不能设计一个新的**（RPC/MQ/注册中心/网关）。

如果你只有 1 周：把 [第十三章 100 问](#十三高频-100-问) 的 ★★★ 过一遍 + 准备 2 个故障复盘 + 吃透 Kafka 和 Redis 的存储与集群。

如果你有 6 周：按 [14.1](#141-六周学习路线) 走，并至少完成"手写 RPC + 手写 MQ"两个项目——它们能覆盖 70% 的面试考点。
