## 零、及格线与优秀线：同一道题的三档答案

> **这一章是整份文档的核心。** 如果你只读一章，读这章。
> 社招面试的残酷之处：**"答对"不加分，"答出别人不知道的"才加分。**

### 0.1 面试官如何打分

面试官心里通常有四个格子，每个格子 1~5 分：

| 维度 | 及格（3 分） | 优秀（4~5 分） | 面试官的动作 |
| --- | --- | --- | --- |
| **准确性** | 结论正确 | 结论 + 边界条件都对 | 记录，继续 |
| **深度** | 知道是什么 | 知道实现/源码/为什么 | **追问第二层** |
| **判断力** | 会用 | 知道什么时候**不用**、代价是什么 | **给场景题** |
| **经验密度** | 教科书答案 | 有数字、有事故、有取舍 | 给高分 |

**关键洞察**：面试官判断"深度"，靠的不是你说了多少，而是**你能不能在他的追问下不崩**。所以准备策略是：**每个重点知识点，预先想好第二层、第三层追问的答案。**

### 0.2 三档答案对比（背这个感觉）

#### 例 1：Redis 为什么快？

**及格（60 分，所有人都会）**

> 因为 Redis 是基于内存的，而且单线程没有锁竞争，还用了 IO 多路复用。

**良好（75 分，准备过的人）**

> 四个原因：① 纯内存，避免磁盘 IO；② 单线程执行命令，无锁、无上下文切换；③ epoll 多路复用处理海量连接；④ 高效数据结构，比如 SDS、跳表、listpack。
> 另外 6.0 引入了多线程，但只用于网络 IO，命令执行仍是单线程。

**优秀（90 分，能拿到 offer 的答案）**

> 我会分三层讲，因为这三层瓶颈不一样。
>
> **第一层：单次命令的延迟。** 纯内存访问约 100ns 量级，SDS 取长度 O(1)、listpack 把小集合放在连续内存里减少指针跳转（省 cache miss）、跳表范围查询 O(log N) 且实现比红黑树简单——这些让单次操作稳定在微秒级。
>
> **第二层：并发模型。** 单线程事件循环（`ae.c` 的 epoll + 定时事件）避免了锁和上下文切换。但要注意：**单线程的优势建立在"命令都很短"这个前提上**，所以 Redis 才有 `lazyfree`、`SCAN`、大 key 治理这些机制，因为 O(N) 命令会阻塞整个事件循环。6.0 的多线程只把 **read/write/协议解析** 放到 IO 线程，命令执行仍在主线程——因为真正的瓶颈是网络带宽而不是 CPU 计算。
>
> **第三层：瓶颈在哪。** 单机大概 10 万 QPS，此时瓶颈通常在**网络 RTT 和 syscall 次数**，所以要用 pipeline / Lua 把 N 次 RTT 压成 1 次。再往上就受限于单核和内存带宽，只能分片（Cluster）——但分片会带来跨槽事务和批量操作的复杂度。
>
> **反过来说，什么时候 Redis 不快？** ① value 很大（>10KB）时网络和序列化成瓶颈；② 有 `KEYS`、`SMEMBERS` 大集合这类 O(N) 命令；③ 触发 fork（RDB/AOF 重写）时主线程会短暂阻塞，大堆下可能几百毫秒；④ 持久化策略激进（`always`）时每次写都要 fsync。

**差距在哪？** 优秀答案多了：具体模块名（`ae.c`）、前提条件、反向结论（什么时候不快）、以及真实数字。**面试官记住的是"这个人读过/想过"，而不是"这个人背过"。**

#### 例 2：MySQL 为什么用 B+ 树做索引？

**及格**：因为 B+ 树查询快，而且范围查询方便。

**良好**：非叶子节点只存键，一页能放更多索引，树更矮；叶子节点用链表连接，范围查询快；对比 B 树非叶子也存数据，扇出小。

**优秀**

> 我想从**磁盘 IO 的代价**来推这个设计，因为这是根因。
>
> InnoDB 的一页是 16KB，一次随机 IO 大概是 0.1ms（SSD）到 10ms（机械盘）。假设一行 1KB、主键加指针 14B：非叶子页能放约 1170 个键，叶子页放 16 行。三层树可以存 `1170 × 1170 × 16 ≈ 2190 万`行，而**查询只需 3 次 IO**——这就是 B+ 树的全部意义：**用扇出换层高，用层高换 IO 次数**。
>
> 为什么非叶子不存数据？因为存了数据扇出会掉一个数量级，层高从 3 变 4、5，每多一层就多一次 IO。
>
> 为什么叶子要链表？因为 B 树的范围查询要中序遍历、跨层回溯，而 B+ 树叶子是双向链表，`BETWEEN` 只需定位起点再顺序扫，还能配合 `ORDER BY` 免排序。
>
> 更深一层：**B+ 树是"读优化"结构**，写入是随机 IO + 页分裂。所以当写远大于读（比如日志、时序数据），就会选 **LSM-Tree**（RocksDB/TiDB/HBase），把随机写变成顺序写，用 compaction 换读放大。这也是为什么选型要看读写比：**读多写少用 B+ 树，写多读少用 LSM**。
>
> 另外还有个实践点：B+ 树索引的效果强依赖 Buffer Pool 命中率。热数据能全放内存时，三层树几乎都是内存访问；一旦 Buffer Pool 不足，每次回表都是真 IO，这时候"索引"反而可能是负优化——这也是为什么大表要控制单行大小、把大字段拆出去。

**加分点**：把"数据结构选择"上升到"读写比决定存储引擎"，这是架构视角。

#### 例 3：如何保证缓存与数据库一致？

**及格**：先更新数据库，再删除缓存。

**良好**：Cache Aside 模式；先更新 DB 再删缓存；如果删除失败要重试；可以用延迟双删。

**优秀**

> 先明确一点：**缓存和 DB 做不到强一致**，只能做到"足够快的最终一致"。所以要先把业务的一致性要求问清楚——是允许几百毫秒的旧值，还是必须读到最新（比如支付后查订单）。
>
> 在这个前提下，我会分四层来设计：
>
> **① 更新策略：为什么是删而不是改。** 更新缓存有两个问题：并发写会互相覆盖（A 写 DB、B 写 DB、B 写缓存、A 写缓存 → 缓存是旧值）；而且很多缓存写完根本不会被读，纯浪费。所以用删除 + 懒加载。
>
> **② 顺序：为什么先 DB 后删。** 如果先删缓存再改 DB，中间任何一次读都会把旧值回填，而且这个旧值会一直留到下次淘汰。先改 DB 再删，最坏情况只在一个很窄的窗口里出问题：读请求在 DB 更新前读到旧值，却在该值被删之后才回填。
>
> **③ 那个窗口怎么处理。** 三个手段：延迟双删（删 → 改 DB → 延迟再删，延迟要 > 一次读的耗时，通常取主从同步延迟 + 业务 RT，500ms~1s）；Canal 订阅 binlog 异步删（最稳，能覆盖所有写路径，包括别人直接改库）；以及给缓存带版本号/逻辑过期，读时校验。
>
> **④ 兜底与观测。** 任何方案都会漏，所以要有对账：定时任务抽样比对缓存与 DB 的关键字段，发现不一致就删缓存并告警。另外如果是多级缓存（本地 Caffeine + Redis），失效要广播，否则本地缓存会长期脏。
>
> **什么时候我不用缓存？** 强一致场景（账户余额、库存扣减的关键路径）直接读 DB + 行锁/乐观锁，缓存只做展示层；或者用"DB 为准 + 缓存只做旁路加速 + 短 TTL"。

#### 例 4：线程池参数怎么配？

**及格**：CPU 密集 N+1，IO 密集 2N。

**优秀**

> 公式只是起点，我实际是按 **Little's Law + 压测** 来定的：并发数 = QPS × 平均 RT。比如单机目标 2000 QPS、下游 RT 50ms，那需要的并发是 100，再留 30% 余量配 130 个线程。但线程不是越多越好，要同时约束三件事：
>
> ① **队列必须有界**，且长度要对应可接受的排队时间（队列长度 / QPS = 排队延迟）。无界队列本质是把过载变成 OOM。
> ② **拒绝策略要能降级**，我一般用自定义策略：打点 + 降级返回兜底值，而不是直接抛异常给用户。
> ③ **必须隔离**：核心链路和非核心链路用不同池，避免一个慢下游把整个池拖死（这是最常见的线上事故）。
>
> 另外我会做动态调参（基于配置中心），因为大促和日常的合理值不一样；监控看四个指标：活跃线程数、队列长度、拒绝次数、任务 RT。如果队列持续增长，说明是**下游变慢**，加线程只会更糟——这时应该限流或熔断。

- 数字模糊（"提升了很多"、"大概快了一倍"）。

## 一、源码级 Java：从"知道"到"读到过"

> 目标不是背源码，而是**能在被追问时说出"这块我看过，关键在 X 方法里"**。
> 下面每个点都标注了**该看哪个类/方法**，方便你按图索骥。

### 1.1 HashMap：那些"知道结论但说不清"的细节 ⭐⭐⭐

#### （1）resize 的 loHead / hiHead 拆分

```java
// java.util.HashMap#resize
Node<K,V> loHead = null, loTail = null;   // 留在原位置 i
Node<K,V> hiHead = null, hiTail = null;   // 移到 i + oldCap
do {
    next = e.next;
    if ((e.hash & oldCap) == 0) {         // 关键判断
        if (loTail == null) loHead = e; else loTail.next = e;
        loTail = e;
    } else {
        if (hiTail == null) hiHead = e; else hiTail.next = e;
        hiTail = e;
    }
} while ((e = next) != null);
if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
```

**能讲出的深度**：

- 为什么用 `hash & oldCap` 而不是重新算 `(newCap-1) & hash`？因为容量是 2 的幂，扩容后多出的那一位恰好是 `oldCap`，所以只需看这一位是 0 还是 1。
- **尾插 + 拆成两条链**，所以不会像 JDK7 头插那样在并发扩容时成环（JDK7 的 `transfer` 会反转链表顺序）。
- JDK8 仍然线程不安全：`++size`、`tab[i] = newNode(...)` 都是无保护的。

#### （2）树化的两个门槛与退化

```java
// treeifyBin 里
if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)  // 64
    resize();                       // 优先扩容而不是树化
else if ((e = tab[index]) != null)
    ... TreeNode ...
```

**追问**："为什么链表长度到 8 要树化，但又要求容量 ≥ 64？"
→ 小容量下长链表说明**哈希分布差是因为桶太少**，扩容成本比树化低；容量 ≥ 64 后仍然冲突，才认为是真的哈希碰撞，用红黑树保证 `O(log n)` 而不是 `O(n)`。

**追问**："为什么退化阈值是 6 而不是 8？" → 留缓冲区，避免在 7 附近反复树化/退化（抖动）。

#### （3）为什么 HashMap 的容量方法叫 `tableSizeFor` 且要减 1

```java
static final int tableSizeFor(int cap) {
    int n = cap - 1;             // 处理 cap 本身就是 2 的幂的情况
    n |= n >>> 1; n |= n >>> 2; n |= n >>> 4; n |= n >>> 8; n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

**能讲的深度**：这是"把最高位之后全部填 1 再 +1"的经典位技巧；减 1 是为了让 `cap=16` 时返回 16 而不是 32。

#### （4）源码级追问清单

| 追问 | 该答到哪一层 |
| --- | --- |
| `put` 时为什么先判断 `table == null` | 懒初始化，构造时不分配数组 |
| 为什么 `key` 的 hash 要异或高 16 位 | 桶定位只用低位，让高位参与降低碰撞 |
| `TreeNode` 继承 `LinkedHashMap.Entry` 有什么好处 | 复用双向链表结构，便于树化/退化与 LRU 场景 |
| `HashMap` 和 `Hashtable` 的区别 | Hashtable 全表 synchronized、不允许 null、迭代器非 fail-fast 语义不同 |
| 为什么遍历顺序不保证 | 桶顺序 + 链表/树内部顺序，且扩容会打乱 |

### 1.2 ConcurrentHashMap：并发扩容是重点 ⭐⭐⭐

#### （1）`sizeCtl` 的四种语义（能背出来是加分项）

| 取值 | 含义 |
| --- | --- |
| `0` | 未初始化 |
| `-1` | 正在初始化（`casTabAt` 抢到初始化权） |
| `-(1 + resizeStamp(n) << RESIZE_STAMP_SHIFT)` | 正在扩容，低位记录参与扩容的线程数 |
| `> 0` | 下次扩容阈值（`0.75 * capacity`） |

#### （2）多线程协助扩容（`helpTransfer` / `transfer`）

```java
// transfer 里每个线程负责一段桶（stride，默认 16）
if ((stride = (NCPU > 1) ? (n >>> 3) / NCPU : n) < MIN_TRANSFER_STRIDE)
    stride = MIN_TRANSFER_STRIDE;     // 16
```

**能讲的深度**：

- 扩容不是单线程做，**发现 `sizeCtl < 0` 的线程会来帮忙**（`helpTransfer`），每个线程按 stride 领取一段桶。
- 搬迁时用 `ForwardingNode` 标记已处理的桶，其他线程看到它就跳过。
- 这是"**协作式扩容**"，避免大表扩容时的长停顿（对比 HashMap 单线程 resize 可能几百 ms）。

#### （3）计数：`CounterCell` 与伪共享

```java
// ConcurrentHashMap#sumCount
final long sumCount() {
    CounterCell[] as = counterCells;
    CounterCell a;
    long sum = baseCount;
    if (as != null) {
        for (int i = 0; i < as.length; ++i) {
            if ((a = as[i]) != null) sum += a.value;
        }
    }
    return sum;
}

@sun.misc.Contended static final class CounterCell { volatile long value; }
```

**追问**："`size()` 为什么不准确？" → 分段计数，`sumCount()` 遍历时其他线程还在写；且返回是 `int`，官方推荐用 `mappingCount()`（返回 long）。

**追问**："`@Contended` 是干什么的？" → **伪共享**：多个 `CounterCell` 落在同一个 64B 缓存行，一个核写会让其他核的缓存行失效。`@Contended` 填充到独立缓存行。（用户类使用需 `-XX:-RestrictContended`）

#### （4）为什么不允许 null

`get(key)` 返回 null 无法区分"不存在"和"值是 null"，而并发下**没法像 HashMap 那样用 `containsKey` 二次确认**（两次调用之间值可能变了）。这是设计上的取舍，不是遗漏。

#### （5）`put` 的主干逻辑（能手写伪代码）

```java
for (Node<K,V>[] tab = table;;) {
    if (tab == null || (n = tab.length) == 0) tab = initTable();
    else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
        if (casTabAt(tab, i, null, new Node(hash, key, val))) break;  // 空桶：CAS
    }
    else if ((fh = f.hash) == MOVED) tab = helpTransfer(tab, f);      // 扩容中：帮忙
    else {
        synchronized (f) { ... }                                      // 非空桶：锁头结点
    }
}
```

**一句话总结**：*ConcurrentHashMap 的演进是「锁粒度」的演进——JDK7 锁 Segment（1/16），JDK8 锁桶头结点 + CAS + 协作扩容。*

### 1.3 AQS 的三个"说不清"细节 ⭐⭐⭐

#### （1）`PROPAGATE` 状态是干什么的

```java
// doReleaseShared
if (h != null && h != tail) {
    int ws = h.waitStatus;
    if (ws == Node.SIGNAL) { ... unparkSuccessor(h); }
    else if (ws == 0 && !compareAndSetWaitStatus(h, 0, Node.PROPAGATE))
        continue;
}
```

**回答**：共享模式下，释放资源后需要**把唤醒传播下去**（比如 `CountDownLatch` 释放后所有等待线程都该被唤醒）。`PROPAGATE` 防止在"释放 → 唤醒 → 又有人 acquire"的竞态中丢失传播，导致部分线程永远挂起。

#### （2）中断与取消

```java
if (Thread.interrupted()) {          // 检测中断
    cancelAcquire(node);             // 标记 CANCELLED(1)，并从队列摘除
    throw new InterruptedException();
}
```

**追问**："AQS 的队列里节点状态有哪几种？" → `CANCELLED(1)`、`SIGNAL(-1)`、`CONDITION(-2)`、`PROPAGATE(-3)`、`0`（初始）。

#### （3）Condition 的双队列

```
sync queue（同步队列）  ⇄  condition queue（条件队列）
await(): 加锁态 → 加入 condition queue → 释放锁 → park
signal(): 从 condition queue 移到 sync queue → 等待重新竞争锁
```

**追问**："为什么 `await()` 必须持有锁？" → 因为要操作条件队列，且要保证 `signal` 与状态检查的原子性（否则会丢失信号）。这也是"必须用 `while` 而不是 `if` 检查条件"的原因——被唤醒后条件可能又变了。

#### （4）ReentrantLock 的公平性实现

```java
// NonfairSync.lock
if (compareAndSetState(0, 1)) setExclusiveOwnerThread(Thread.currentThread());
else acquire(1);

// FairSync.tryAcquire
if (!hasQueuedPredecessors() && compareAndSetState(0, acquires)) { ... }
```

**能讲的深度**：非公平锁**允许插队**（刚释放的锁可能被新来的线程抢走），吞吐更高，但可能饥饿；公平锁每次都要检查队列前驱。

### 1.4 伪共享、内存屏障与硬件 ⭐⭐

| 概念 | 说明 | 在 JDK 里的体现 |
| --- | --- | --- |
| **缓存行** | x86 通常 64B，一次读入整行 | `@Contended`、`LongAdder`、Disruptor 的 padding |
| **伪共享** | 两个变量在同一行，被不同核写 → 行来回失效 | 用 padding 隔离 |
| **内存屏障** | LoadLoad / StoreStore / LoadStore / StoreLoad | `volatile` 读写插入屏障 |
| **x86 的 lock 前缀** | 保证缓存一致性（MESI） | `Unsafe` 的 CAS 实现 |
| **ARM 的 dmb** | 弱内存模型，需要显式屏障 | 同一套 Java 代码在 ARM 上依赖屏障正确性 |

**面试话术**："Java 的内存模型是语言级约定，屏蔽了 x86 的 TSO 和 ARM 的弱内存模型差异；`volatile` 在 x86 上通常只加 StoreLoad 屏障（`lock addl`），在 ARM 上要加 `dmb ish`，所以同一段代码在不同架构上的开销不同。"

### 1.5 ThreadLocal 进阶：TTL 与虚拟线程 ⭐⭐

#### （1）为什么 `InheritableThreadLocal` 在线程池里失效

它只在**创建线程时**复制父线程的 map。线程池的线程是复用的，创建一次后不再复制。

#### （2）TransmittableThreadLocal（TTL）怎么做到的

- 不是靠继承，而是**在任务提交时快照、执行时回放、结束后恢复**。
- 通过增强 `Runnable`/`Callable`（`TtlRunnable`）或 Java Agent 字节码增强，把 `ThreadLocal` 的值包装进任务。
- 关键类：`Transmitter.capture()` / `replay()` / `restore()`。

#### （3）虚拟线程下的问题（JDK21+）

| 问题 | 说明 |
| --- | --- |
| ThreadLocal 数量爆炸 | 每个虚拟线程一份 ThreadLocalMap，百万级虚拟线程 → 内存压力 |
| **pinning** | 在 `synchronized` 块里阻塞会**钉住载体线程**，导致调度器饿死；JDK24（JEP 491）已缓解 |
| native 方法 | 仍会 pin |
| 替代方案 | **ScopedValue**（预览）更适合传递不可变上下文 |

**面试话术**："虚拟线程适合 IO 密集、线程数巨大的场景，但它不是银弹：`synchronized` 阻塞、native 调用、CPU 密集都会让它退化；而且它改变了我们对『线程数 = 并发度』的直觉。"

## 二、并发深水区

> 上一层的考点是"线程池有 7 个参数"，深水区的考点是：**你踩过哪些并发 bug，怎么定位的。**

### 2.1 线程池：5 个生产环境才会暴露的坑 ⭐⭐⭐

#### 坑 1：`submit` 会吞掉异常

```java
// ❌ 异常被包装进 Future，没人 get 就永远不会暴露
executor.submit(() -> { throw new RuntimeException("boom"); });

// ✅ 要么用 execute（异常直接走 UncaughtExceptionHandler）
executor.execute(() -> { throw new RuntimeException("boom"); });

// ✅ 要么保留 Future 并检查
Future<?> f = executor.submit(task);
try { f.get(); } catch (ExecutionException e) { log.error("task failed", e.getCause()); }
```

**追问**："为什么会吞？" → `submit` 返回 `FutureTask`，异常被 `setException` 捕获存在 `outcome` 字段里，只有 `get()` 时才重抛。

#### 坑 2：`Future.get()` 没有超时

一个下游卡住 → 线程被永久占用 → 池被耗尽。**必须 `get(timeout, unit)`**，或统一用 `CompletableFuture.orTimeout()`。

#### 坑 3：线程池没有隔离

```
订单主链路和"发短信"共用同一个池
→ 短信服务抖动，池被占满
→ 下单接口全部超时（雪崩）
```

**正确做法**：按**依赖**隔离（每个下游一个池），或按**重要性**隔离（核心/非核心）。这也是 Hystrix/Sentinel 线程池隔离的由来。

#### 坑 4：队列选错导致 `maximumPoolSize` 失效

```java
// ❌ LinkedBlockingQueue 默认容量 Integer.MAX_VALUE
new ThreadPoolExecutor(8, 200, 60, SECONDS, new LinkedBlockingQueue<>());
// 实际最大线程数永远是 8，队列无界 → 任务堆积 → OOM

// ✅ 有界队列
new ThreadPoolExecutor(8, 200, 60, SECONDS, new ArrayBlockingQueue<>(1000), ...);
```

**排查技巧**：`jstack` 里看到线程名都是 `pool-1-thread-8` 且不再增长，同时 `jmap -histo` 里 `LinkedBlockingQueue$Node` 数量巨大 → 就是这个问题。

#### 坑 5：优雅关闭缺失

```java
// 应用关闭时，先停止接收，再等在途任务
executor.shutdown();
if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
    executor.shutdownNow();          // 中断
}
```

**追问**："`shutdownNow()` 之后任务一定停吗？" → 不一定，只有响应中断的任务会停；阻塞在 `synchronized` 或非中断 IO 上的任务不会。

#### 源码级：`ctl` 与 `addWorker`

```java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
private static final int COUNT_BITS = Integer.SIZE - 3;        // 29
private static final int CAPACITY   = (1 << COUNT_BITS) - 1;   // 约 5.36 亿

private static int runStateOf(int c)     { return c & ~CAPACITY; }
private static int workerCountOf(int c)  { return c & CAPACITY; }
```

**能讲的深度**：用一个 int 同时存状态和数量，是为了**用一次 CAS 同时改两个值**（避免两个字段的不一致）；`addWorker` 先 CAS 增加计数再创建线程，失败则回滚——这是"先占位后执行"的典型并发模式。

### 2.2 无锁编程：Disruptor 为什么快 ⭐⭐

很多人只知道"Disruptor 是无锁队列"，但说不清**快在哪**。四个原因：

| 优化 | 说明 |
| --- | --- |
| **消除伪共享** | `Sequence` 前后填充 56B padding，避免缓存行互相失效 |
| **CAS 代替锁** | 生产者用 CAS 抢槽位，无阻塞 |
| **批量 + 序号屏障** | 消费者按 `SequenceBarrier` 批量消费，减少同步次数 |
| **预分配数组** | 环形数组，对象复用，无 GC 压力 |

```java
// 环形数组定位（必须是 2 的幂，用位与代替取模）
long sequence = ringBuffer.next();
try {
    Event e = ringBuffer.get(sequence);   // 取的是预分配对象，不是 new
    e.setValue(...);
} finally {
    ringBuffer.publish(sequence);          // 发布后消费者才可见
}
```

**追问**："和 `BlockingQueue` 比，代价是什么？" → ① 只支持固定大小的环形缓冲；② 消费者必须自己处理"追不上"的情况；③ 实现复杂，容易出错。**适合超高频、可批量、可丢/可等待的场景（如行情、日志），不适合通用业务。**

### 2.3 并发 bug 的定位方法论 ⭐⭐⭐

#### （1）先读懂线程状态

| 状态 | 含义 | 排查方向 |
| --- | --- | --- |
| `RUNNABLE` | **在 JVM 眼里可运行**（可能正在等 IO/锁） | 结合 `top -Hp` 看是否真耗 CPU |
| `BLOCKED` | 等 `synchronized` 锁 | **锁竞争**，看 `waiting to lock` 的持有者 |
| `WAITING` | `wait()` / `join()` / `park()` 无超时 | **可能是死等**，看谁该 notify |
| `TIMED_WAITING` | `sleep` / `parkNanos` / `get(timeout)` | 通常是正常等待，注意超时值是否合理 |

> **高频误区**：`RUNNABLE` 不等于"在跑"。`jstack` 里大量 `RUNNABLE` 且都在 `socketRead0`，说明是 **IO 阻塞**，不是 CPU 忙。

#### （2）线程 dump 的三步分析

```bash
# ① 抓 3 次，间隔 5 秒（单次快照会误判）
jstack -l <pid> > /tmp/1.txt; sleep 5; jstack -l <pid> > /tmp/2.txt

# ② 统计线程状态分布
grep "java.lang.Thread.State" /tmp/1.txt | sort | uniq -c

# ③ 找同一把锁上的等待链
grep -A 3 "waiting to lock" /tmp/1.txt
```

**三类典型结论**：

- 大量 `BLOCKED` 在同一把锁 → **锁粒度太大**（如同步整个方法）。
- 大量 `WAITING` 在 `poll()`/`take()` → **消费端处理慢**（队列积压）。
- 大量 `RUNNABLE` 在同一个业务方法 → **CPU 密集 or 死循环**，上 `async-profiler`。

#### （3）锁竞争量化

```bash
# async-profiler 的 lock 模式，直接给出竞争最激烈的锁
./profiler.sh -e lock -d 30 -f /tmp/lock.html <pid>

# 或用 JFR
jcmd <pid> JFR.start duration=60s filename=/tmp/rec.jfr
```

#### （4）上下文切换

```bash
vmstat 1 5
# cs 列 = 上下文切换次数；如果每秒几十万，说明锁竞争或线程过多
pidstat -w -p <pid> 1
```

### 2.4 并发设计模式（面试常考"你了解哪些并发模式"）

| 模式 | 解决什么 | Java 实现 |
| --- | --- | --- |
| **生产者-消费者** | 解耦速率 | `BlockingQueue` |
| **Future / Promise** | 异步结果 | `CompletableFuture` |
| **Guarded Suspension** | 条件不满足就等 | `wait/notify`、`Condition` |
| **Balking** | 条件不满足就放弃 | `if (state != OK) return;` |
| **两阶段终止** | 安全停止线程 | `volatile flag` + 中断 |
| **Worker Thread** | 任务与执行分离 | 线程池 |
| **Pipeline** | 分阶段并行处理 | 多级队列 |
| **背压（Backpressure）** | 生产快于消费 | 有界队列 + 拒绝策略 |

**"背压"是深水区关键词**：一个系统没有背压，就等于把过载转成雪崩。回答任何"高并发"问题时，主动提"**我们怎么感知压力并反压**"（队列满、RT 上升、CPU 水位、Sentinel 系统规则）。

### 2.5 可见性 bug 的真实案例

```java
// 案例：线程 A 修改 flag，线程 B 循环检查 —— B 可能永远看不到
class Worker {
    private boolean stopped = false;      // ❌ 没有 volatile

    public void run() {
        while (!stopped) {                // JIT 可能把 stopped 提到循环外（hoisting）
            doWork();
        }
    }
    public void stop() { stopped = true; }
}
```

**深层原因**：不是"缓存没刷新"这么简单，而是 **JIT 允许把循环不变量提出循环**（hoisting），加上 CPU 缓存，导致读到的永远是旧值。

**追问**："加 `volatile` 就一定对吗？" → 可见性对了，但 `while` 循环里如果还有复合操作（`i++`），仍需要原子类或锁。

### 2.6 `CompletableFuture` 的编排陷阱

```java
// ❌ 陷阱 1：默认用 commonPool，IO 任务会拖垮全局
CompletableFuture.supplyAsync(() -> rpc.call());

// ✅ 指定线程池
CompletableFuture.supplyAsync(() -> rpc.call(), bizPool);

// ❌ 陷阱 2：异常被吞（没有 exceptionally/whenComplete）
// ✅ 必须显式处理
future.exceptionally(ex -> { log.error("fail", ex); return fallback; });

// ❌ 陷阱 3：thenApply 里做阻塞操作（占着线程等）
// ✅ 用 thenApplyAsync + 独立池，或改用响应式
```

**`thenApply` vs `thenCompose`**：前者是 `map`（`T -> R`），后者是 `flatMap`（`T -> CompletableFuture<R>`）。用错会导致嵌套 `CompletableFuture<CompletableFuture<R>>`。

### 3.1 GC 日志实战解读 ⭐⭐⭐

#### （1）先看一段真实的 G1 日志

```
[2024-05-01T10:00:00.123+0800][info][gc,start] GC(123) Pause Young (Normal) (G1 Evacuation Pause)
[2024-05-01T10:00:00.124+0800][info][gc,heap] GC(123) Eden regions: 120->0(120)
[2024-05-01T10:00:00.124+0800][info][gc,heap] GC(123) Survivor regions: 5->6(15)
[2024-05-01T10:00:00.124+0800][info][gc,heap] GC(123) Old regions: 300->310(500)
[2024-05-01T10:00:00.124+0800][info][gc,heap] GC(123) Humongous regions: 2->2(10)
[2024-05-01T10:00:00.124+0800][info][gc,metaspace] GC(123) Metaspace: 120M->120M(1024M)
[2024-05-01T10:00:00.148+0800][info][gc] GC(123) Pause Young (Normal) (G1 Evacuation Pause) 425M->318M(2048M) 25.123ms
```

**逐行能读出什么**：

| 字段 | 含义 | 异常信号 |
| --- | --- | --- |
| `GC(123)` | 第 123 次 GC | — |
| `Pause Young (Normal)` | 普通 Young GC | 若是 `(Concurrent Start)` 则触发了并发标记周期 |
| `Eden 120->0(120)` | Eden 120 个 Region 全部清空 | 正常 |
| `Survivor 5->6(15)` | 存活对象进入 Survivor | 持续增长说明对象活得太久 |
| `Old 300->310(500)` | **老年代增长 10 个 Region** | ⚠️ 晋升过快 → 可能有内存泄漏或 Survivor 太小 |
| `Humongous 2->2(10)` | 大对象区 | ⚠️ 数量多说明有超大对象（如大数组、大缓存） |
| `425M->318M(2048M)` | 回收前→后（堆总容量） | 回收后仍接近容量 → 危险 |
| `25.123ms` | 停顿时间 | 若频繁 > `MaxGCPauseMillis`，说明预测失效 |

#### （2）三种"要命"的日志特征

| 日志关键字 | 含义 | 处理 |
| --- | --- | --- |
| `to-space exhausted` |  survivor/old 都放不下，**晋升失败** | 加堆/调大 Survivor/降低晋升速度 |
| `Evacuation Failure` | 转移失败，触发 Full GC | 同上，且检查是否有大对象洪峰 |
| `Full GC` 频繁 | 并发标记跟不上分配速度 | 调 `IHOP`、加堆、查内存泄漏 |
| `Concurrent Mark Cycle` 频繁 | 老年代占用反复超过阈值 | 调 `InitiatingHeapOccupancyPercent` |

**面试话术**："看到 `to-space exhausted` 基本可以判定是**晋升失败**，常见于『突发大流量 + Survivor 太小 + 对象存活时间长』三者叠加。"

#### （3）开启正确的日志参数

```bash
# JDK9+ 统一日志
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=10,filesize=50m

# JDK8
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/data/logs/gc.log \
-XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=10 -XX:GCLogFileSize=50M
```

> **生产建议**：GC 日志一定要**异步落盘 + 滚动**，否则日志 IO 本身会影响 GC 停顿。

### 3.2 G1 深水区：RSet、SATB 与 IHOP ⭐⭐

#### （1）RSet（Remembered Set）解决什么

G1 把堆分成 Region，回收某个 Region 时需要知道**谁引用了它**。RSet 就是"**其他 Region 指向我的引用**"的记录。

- 底层用 **Card Table**（每个 Region 一张卡表，512B 一张卡）。
- **PRT（Per-Region Table）** 是 RSet 的实现，稀疏时用卡表、稠密时用位图。
- **写屏障**在赋值时更新 RSet（`g1_write_barrier_post`）。

**代价**：RSet 占内存（约 5%~10% heap），维护有开销。这也是 G1 在小堆上不如 Parallel 的原因。

#### （2）SATB（Snapshot-At-The-Beginning）

并发标记期间对象引用会变，G1 用 SATB 保证不漏标：

- 标记开始时**逻辑上**给堆拍快照。
- **写屏障**在引用被覆盖前，把**旧值**记录下来（`pre-write barrier` → SATB 队列）。
- 标记结束前处理完 SATB 队列，保证"快照时活着的对象都被标记"。

**对比 CMS 的增量更新（incremental update）**：CMS 记录**新增**的引用，G1 记录**删除**的引用。两者都会产生浮动垃圾，但 SATB 只需在标记阶段处理一次。

#### （3）IHOP 与自适应

```bash
-XX:InitiatingHeapOccupancyPercent=45      # 老年代占比超过 45% 启动并发标记
-XX:+G1UseAdaptiveIHOP                     # JDK10+ 默认开启，动态调整
```

**为什么需要 IHOP**：并发标记要花时间，如果等到老年代快满了才开始，标记期间可能就晋升失败 → Full GC。IHOP 是**提前量**。

**调优顺序**（别乱调）：

```
① 先定 MaxGCPauseMillis（如 200ms）——这是目标不是保证
② 加堆，直到 Young GC 频率可接受
③ 若频繁 Full GC → 查泄漏 / 调 IHOP / 调 RegionSize
④ 最后才考虑换收集器（ZGC）
```

### 3.3 ZGC：为什么能做到亚毫秒 ⭐⭐

| 机制 | 说明 |
| --- | --- |
| **染色指针（Colored Pointers）** | 把标记位存在**指针的高位**（不是对象头），避免读对象头 |
| **多重映射（Multi-Mapping）** | 同一块物理内存映射到 3 个虚拟地址（marked0/marked1/remapped），用地址区分状态 |
| **读屏障（Load Barrier）** | 每次读引用时检查指针颜色，必要时修正（这是 ZGC 的核心开销） |
| **并发转移** | 对象移动与用户线程并发，用转发指针/读屏障保证正确性 |

**能讲的深度**：

- ZGC 的停顿与**堆大小、存活对象数无关**，只与 GC Roots 数量有关 → 所以能支持 TB 级堆。
- 代价是**吞吐量下降**（读屏障 + 并发转移占用 CPU），一般比 G1 低 5%~15%。
- **分代 ZGC（JDK21）** 通过分代减少每次扫描的对象量，把吞吐又拉回来一些。

**选型**：

| 场景 | 推荐 |
| --- | --- |
| 堆 < 8G、追求吞吐 | G1 / Parallel |
| 堆大（>16G）、P99 敏感 | G1（调优后） |
| 堆超大（>64G）、停顿必须 < 1ms | **ZGC** |
| 容器内、内存受限 | G1 + `-XX:MaxRAMPercentage` |

### 3.4 JIT：为什么"跑一会儿才快" ⭐⭐

#### （1）分层编译

| 层级 | 编译器 | 说明 |
| --- | --- | --- |
| 0 | 解释执行 | 启动最快 |
| 1~3 | C1 | 快速编译 + 采集 profiling 信息 |
| 4 | C2 | 深度优化（内联、逃逸分析、向量化） |

**这就是"预热"的由来**：接口刚启动时走解释/C1，QPS 上不去；跑几万次后 C2 编译，性能才稳定。

#### （2）三个关键优化

| 优化 | 说明 | 失效场景 |
| --- | --- | --- |
| **方法内联** | 把小方法展开，消除调用开销 | 方法太大（`MaxInlineSize=35`、`FreqInlineSize=325` 字节码） |
| **逃逸分析** | 对象没逃出方法 → 栈上分配 / 标量替换 | 对象被返回、被存入全局集合 |
| **锁消除** | 证明锁对象不会被共享 → 去掉锁 | 对象被发布出去 |

**追问**："为什么我的代码有时候快有时候慢？" → 可能是**去优化（deoptimization）**：C2 基于 profiling 做了乐观假设（比如"这个类型永远不会变"），一旦假设被打破就退回解释执行，出现性能抖动。

```bash
# 看编译与去优化事件
-XX:+PrintCompilation -XX:+UnlockDiagnosticVMOptions -XX:+TraceDeoptimization
```

#### （3）CodeCache 满

```bash
# 警告：CodeCache is full. Compiler has been disabled.
-XX:ReservedCodeCacheSize=256m
```

**现象**：运行一段时间后 QPS 突然下降、CPU 升高（退回解释执行）。**排查**：`jconsole` 看 CodeCache 使用率，或 `jcmd <pid> Compiler.codecache`。

### 3.5 性能分析工具链（会一个就够，但要精通）⭐⭐⭐

#### async-profiler（强烈推荐）

```bash
# CPU 火焰图（基于 perf_events，不依赖 safepoint，采样更准）
./profiler.sh -e cpu -d 30 -f /tmp/cpu.html <pid>

# 内存分配火焰图（找"谁在疯狂 new"）

# 锁竞争

./profiler.sh -e wall -t -d 30 -f /tmp/wall.html <pid>
```

**为什么比 `jstack` 采样好**：`jstack` 只能采到 **safepoint** 的栈，会漏掉正在执行 native/编译代码的线程；async-profiler 用 `perf_events`，能采到任意位置。

#### 火焰图怎么读

```
横轴：采样占比（越宽 = 占用越多）
纵轴：调用栈深度（越深 = 调用链越长）
自下而上：main → service → dao → socketRead

看三个东西：
① 最宽的"平顶" → 热点函数
② 很深的栈 → 调用链问题（如层层包装、递归）
③ 出现意外的栈 → 比如大量时间在 GC、在锁、在日志序列化
```

**经典发现**：

- 火焰图里 `java.lang.Thread.run` 下面全是 `ObjectMapper.writeValue` → **日志/序列化是瓶颈**。
- 大量 `G1 Young RemSet` → RSet 维护开销大（引用多、写屏障频繁）。
- 大量 `Unsafe.park` + `wall` 模式 → **线程在等待**（锁/IO），不是 CPU 问题。

### 3.6 内存问题：堆外与 Metaspace ⭐⭐

#### （1）堆外内存

```
DirectByteBuffer（NIO/Netty）→ 不受 -Xmx 限制，受 -XX:MaxDirectMemorySize 限制
默认值 = 堆最大值
```

**现象**：容器 RSS 远超 `-Xmx`，但堆 dump 正常 → 就是堆外。

**排查**：

```bash
# 看 NMT（Native Memory Tracking）
-XX:NativeMemoryTracking=summary
jcmd <pid> VM.native_memory summary

# Netty 泄漏检测
-Dio.netty.leakDetection.level=paranoid
```

**Netty 泄漏的根因**：`ByteBuf` 是池化的，必须 `release()`；忘记释放 → 池耗尽 → 内存暴涨。

#### （2）Metaspace 泄漏

**常见根因**：

| 根因 | 说明 |
| --- | --- |
| 动态生成类 | CGLIB、`Proxy.newProxyInstance`、Groovy、脚本引擎、`LambdaMetafactory` 在循环里创建 |
| 类加载器泄漏 | Tomcat 热部署、OSGi，旧 ClassLoader 被引用无法回收 |
| 反射/字节码框架 | 每次生成新类而不是复用 |

**排查**：`jcmd <pid> GC.class_stats`（需 `-XX:+UnlockDiagnosticVMOptions`）、MAT 看 `ClassLoader` 的引用链。

### 3.7 容量规划与压测方法论 ⭐⭐⭐

#### （1）先算，再测

```
单机 QPS 上限 ≈ (1000 / 平均 RT_ms) × 并发线程数        （Little's Law）
例：RT 50ms，200 线程 → 4000 QPS（理论），实际打 6~7 折取 2500

存储：单条大小 × 日增条数 × 保留天数 × 副本数 × 1.5（索引/碎片）
带宽：QPS × 平均响应大小 × 8
连接数：QPS × RT / 1000（并发连接）
```

#### （2）压测的四个层次

| 层次 | 目的 | 注意 |
| --- | --- | --- |
| **单接口压测** | 找单机极限、拐点 | 关注 P99 而不是平均 |
| **链路压测** | 找瓶颈环节 | 逐级加压，看哪一层先饱和 |
| **全链路压测** | 验证整体容量 | **影子表/影子库 + 流量染色** |
| **破坏性演练** | 验证降级与容灾 | 混沌工程 |

**拐点怎么找**：阶梯加压（100→200→400→800 QPS），画出 **QPS-RT 曲线**；RT 开始非线性上升的点就是拐点，**容量水位取拐点的 60%~70%**。

#### （3）全链路压测的三个关键

1. **流量染色**：压测请求带特殊 header（如 `x-shadow: true`），全链路透传。
2. **数据隔离**：影子库/影子表，避免污染生产数据；或做数据打标 + 逻辑隔离。
3. **风险控制**：压测开关、限流、随时可停；**绝不打到真实的下游第三方**（用挡板）。

### 3.8 完整案例：一次 P99 毛刺的排查

> **这是最值得背的案例类型**：面试官问"你做过最难的排查"，用这个结构讲。

**现象**：接口 P99 从 50ms 涨到 800ms，但平均 RT 只涨了 10ms，CPU、内存、DB 都正常。

**排查过程**：

```
① 看监控：P99 周期性毛刺（每 30s 一次），平均正常 → 不是普遍变慢
② 看 GC 日志：每次毛刺都对应一次 Young GC（停顿 200ms+）→ 高度相关
③ 看 GC 细节：Eden 每次回收前都接近满，Survivor 晋升量大
④ 看对象分配：async-profiler alloc 模式 → 发现一个"批量查询"接口每次 new 大 List（几十 MB）
⑤ 根因：该接口每 30s 被定时任务调用，一次性查 10 万条记录装进内存 → 大对象直接进老年代/触发 Humongous 分配 → 频繁 Young GC
⑥ 修复：分页查询 + 流式处理（游标），单批 1000 条
⑦ 结果：P99 回到 60ms，Young GC 频率下降 80%
⑧ 预防：加"单次结果集大小"告警；代码规范里禁止无分页的全表查询
```

**为什么这个案例值钱**：它展示了 **"P99 毛刺 → GC → 分配模式 → 代码问题"** 的完整因果链，而且有量化结果。

## 四、MySQL / InnoDB 内核级认知

> 深水区的问题长这样：
> 「你的表 5000 万行，为什么加个索引要 40 分钟？」「Buffer Pool 命中率 99%，为什么查询还是慢？」「主从延迟 3 秒，业务怎么兜底？」

### 4.1 Buffer Pool：MySQL 的性能心脏 ⭐⭐⭐

#### （1）LRU 的冷热分离（为什么不是普通 LRU）

```
普通 LRU 的问题：全表扫描会把所有热数据挤出 Buffer Pool（缓存污染）

InnoDB 的解法：把 LRU 分成两段
  young（热区，约 63%）  |  old（冷区，约 37%，innodb_old_blocks_pct=37）
                         ↑
                    新页插入点（midpoint）

新读入的页先进 old 区头部；
如果在 innodb_old_blocks_time（默认 1000ms）内被再次访问，才晋升到 young 区。
→ 全表扫描的页只会在 old 区快速淘汰，不会污染热数据。
```

**追问**："为什么要 1 秒的延迟？" → 防止"扫描时同一页被连续访问多次"就误判为热数据（顺序扫描会反复访问同一页里的多行）。

#### （2）Change Buffer（写缓冲）

**作用**：对**非唯一二级索引**的写操作，如果索引页不在 Buffer Pool，先记到 change buffer，等页被读入时再 merge。

**为什么只能是"非唯一"**：唯一索引插入必须**立即读页判断唯一性**，无法延迟。

**追问**："change buffer 什么时候 merge？" → ① 页被读取时；② checkpoint；③ 后台线程定期；④ 数据库关闭。

**代价**：增加了 crash recovery 的复杂度（change buffer 也要持久化到系统表空间）。

#### （3）自适应哈希索引（AHI）

InnoDB 会监控索引页的访问模式，如果某个索引被**等值查询**频繁访问，自动建哈希索引。

```bash
innodb_adaptive_hash_index=ON       # 默认开
# 高并发下 AHI 的 latch 可能成为瓶颈，可以关掉
```

**能讲的深度**：AHI 是在 **Buffer Pool 页级别**建的，不是表级别；它用 `btr_search_latch` 保护，**高并发场景反而可能成为争用点**——这是"看起来是优化，实际可能变慢"的典型。

#### （4）预读（Read-Ahead）

| 类型 | 触发 | 说明 |
| --- | --- | --- |
| **线性预读** | 顺序访问一个 extent 的 56 个页 | 预读下一个 extent |
| **随机预读** | 同一 extent 内 13 个页在 Buffer Pool | 预读整个 extent |

**风险**：SSD 上顺序读很快，预读收益下降；预读太多会挤占 Buffer Pool。

#### （5）Buffer Pool 的关键指标

```sql
SHOW ENGINE INNODB STATUS\G
-- 关注：
-- Buffer pool hit rate 1000 / 1000     （命中率）
-- Free buffers                         （空闲页，长期为 0 说明不够）
-- Database pages                       （数据页数）
-- Modified db pages                    （脏页数，不能太多也不能太少）
-- Pages made young / not young         （冷热转换）
-- young/s 很大 → 热数据在被反复晋升，可能 old 区太小
```

**命中率不是越高越好**：如果命中率 99% 但 `young/s` 异常高，说明在频繁换入换出。

### 4.2 redo log：组提交与 checkpoint ⭐⭐⭐

#### （1）为什么要 redo log（而不是直接写数据页）

- 数据页是**随机写**（16KB 页，散落在磁盘），redo 是**顺序写**。
- 修改先在内存页做，写 redo（顺序、快），脏页异步刷盘 → **把随机写变成顺序写**。
- 崩溃时用 redo 重放 → **crash-safe**。

#### （2）组提交（Group Commit）

```
多个事务同时提交时，fsync 可以合并成一次：
  事务 A、B、C 同时 commit
  → 它们的 redo 一起 fsync（一次 IO）
  → 三个事务都返回成功

收益：并发越高，单次提交的 fsync 成本被摊薄
```

**这就是为什么 `innodb_flush_log_at_trx_commit=1` 在高并发下也能接受**。

#### （3）checkpoint 与脏页

```
LSN（Log Sequence Number）：redo 的逻辑序号
checkpoint：把"已经刷盘的页"对应的 LSN 记下来，之前的 redo 可以覆盖

两种 checkpoint：
  sharp checkpoint：关库时，所有脏页刷盘
  fuzzy checkpoint：运行时，分批刷，避免长时间停顿
```

**关键指标**：`Modified db pages`（脏页数）。脏页太多 → 刷盘跟不上 → **刷脏风暴** → RT 抖动。调 `innodb_io_capacity`（SSD 建议 2000+）。

#### （4）Doublewrite Buffer

**解决"页断裂"（partial page write）**：16KB 的页写到一半断电，页损坏，redo 也无法恢复（redo 是基于页的物理逻辑日志，要求页本身一致）。

```
写数据页时：
① 先顺序写到 doublewrite buffer（2MB，共享表空间）
② 再写到真实位置
崩溃恢复：从 doublewrite 找到完好的副本
```

**代价**：多一次写（顺序写，开销可控）。`innodb_doublewrite=OFF` 可以提速但有风险。

### 4.3 binlog：组提交、GTID 与并行复制 ⭐⭐

#### （1）binlog 组提交三阶段

```
① Flush  ：把 binlog 从内存刷到文件（不 fsync）
② Sync   ：fsync 到磁盘（sync_binlog=1 时）
③ Commit ：引擎层提交（redo commit）

每个阶段都有一组事务，所以叫"三阶段组提交"。
```

**能讲的深度**：两阶段提交 + 组提交结合，`sync_binlog=1` 时也能靠"攒一批再 fsync"降低开销。

#### （2）GTID

```
GTID = server_uuid:transaction_id
例：3E11FA47-71CA-11E1-9E33-C80AA9429562:23
```

**价值**：主从切换时不必计算 binlog offset，只需"从库执行过的 GTID 集合"，自动跳过已执行事务（`gtid_mode=ON` + `enforce_gtid_consistency=ON`）。

#### （3）半同步复制（semi-sync）

| 模式 | 行为 | 风险 |
| --- | --- | --- |
| `AFTER_COMMIT` | 主库提交后等从库 ACK | 主库已提交 → 切换后可能丢（旧版本默认） |
| **`AFTER_SYNC`** | **等从库 ACK 后再提交** | 更安全（MySQL 5.7+ 默认） |

**追问**："半同步退化成异步怎么办？" → `rpl_semi_sync_master_timeout`（默认 10s）超时后退化为异步，要监控 `Rpl_semi_sync_master_status`。

#### （4）并行复制

```
MySQL 5.6：按库并行（schema 级别）→ 单库无收益
MySQL 5.7：LOGICAL_CLOCK（基于组提交的事务组）→ 同组事务可并行
MySQL 8.0：WRITESET（基于行级冲突检测）→ 几乎无冲突的事务都能并行
```

**为什么主从延迟？** 从库 SQL 线程串行重放（即使并行复制，也可能因为大事务、无主键表、DDL 而退化）。

### 4.4 MVCC 源码级：ReadView 与 purge ⭐⭐⭐

#### （1）ReadView 的创建时机（源码：`ReadView::prepare`）

```cpp
// RC：每次 SELECT 都调用
// RR：只在事务第一次 SELECT 时创建，之后复用
```

**能讲的深度**：RR 的"可重复读"不是靠锁，而是靠**第一次读时的快照**；这也是为什么 RR 下"事务开始后别人插入的数据看不到"。

#### （2）可见性判断的源码逻辑

```cpp
bool changes_visible(trx_id_t id, const table_name_t& name) const {
    if (id < m_up_limit_id || id == m_creator_trx_id) return true;   // ① 早于最小活跃 或 自己
    if (id >= m_low_limit_id) return false;                          // ② 晚于最大
    if (m_ids.empty()) return true;
    // ③ 在活跃列表中 → 不可见
    return std::find(m_ids.begin(), m_ids.end(), id) == m_ids.end();
}
```

**四句话总结**：**自己改的可见；比我早且已提交的可见；比我晚的不可见；和我并发的（活跃事务）不可见。**

#### （3）purge 与长事务

```
undo log 版本链由 purge 线程清理。
purge 的边界 = 最老的 ReadView。
→ 一个长事务（或未提交事务）会阻止 purge
→ undo log 无限增长（history list length 飙升）
→ 磁盘暴涨 + 查询变慢（要遍历更长的版本链）
```

**监控**：

```sql
SHOW ENGINE INNODB STATUS\G
-- History list length  （> 100 万就要警惕）

SELECT * FROM information_schema.innodb_trx
ORDER BY trx_started LIMIT 5;      -- 找长事务
```

**面试话术**："长事务的危害不只是锁，更是**阻止 purge 导致 undo 膨胀**，这是很多『磁盘突然满了』事故的根因。"

### 4.5 锁：MDL 与 Online DDL ⭐⭐

#### （1）MDL（元数据锁）

- 访问表时自动加 MDL 读锁；DDL 需要 MDL 写锁。
- **经典事故**：一个长事务持有 MDL 读锁 → DDL 等待 → 后续所有查询排在 DDL 后面 → **连接池打满，整库不可用**。

**防范**：

```sql
-- DDL 前先看有没有长事务
SELECT * FROM information_schema.innodb_trx WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

-- 设置 DDL 等待超时，避免无限排队
SET SESSION lock_wait_timeout = 5;
```

#### （2）Online DDL 三种算法

| 算法 | 是否重建表 | 是否允许并发 DML | 典型操作 |
| --- | --- | --- | --- |
| **INSTANT** | 否（只改元数据） | 是 | 8.0.12+ 加列（末尾）、改默认值、重命名 |
| **INPLACE** | 可能重建（但不停写） | 是 | 加索引、加列（5.7）、改列顺序 |
| **COPY** | 重建 + 锁写 | 否 | 改列类型、改字符集（部分） |

**追问**："为什么加索引能用 INPLACE，而改列类型不行？" → 加索引可以**边建边记录增量**（online DDL 的 log 表）；改列类型会改变行的物理布局，必须重写全表。

#### （3）gh-ost / pt-osc 原理

```
① 建影子表（结构一致）
② 在影子表上做 DDL
③ 触发器（pt-osc）或 binlog 订阅（gh-ost）同步增量
④ 分批拷贝存量数据（chunk）
⑤ 原子 rename 切换
```

> **gh-ost 相比 pt-osc 的优势**：不用触发器（对主库压力小）、可暂停、可限流（`--max-load`）。

### 4.6 优化器：为什么"有索引但不用" ⭐⭐

#### （1）成本模型

```
cost = IO 成本 + CPU 成本
IO：读一个页的代价（innodb_page_cleaners 相关配置）
CPU：比较行、评估条件的代价

全表扫描成本 ≈ 页数 × IO_COST
走索引成本 ≈ 扫描行数 × (IO_COST + CPU_COST) + 回表成本
```

**关键结论**：**当预估走索引要回表很多行时，优化器会选全表扫描**（顺序 IO 比随机 IO 便宜）。

**这就是为什么 `WHERE status = 1`（区分度低）可能不走索引**——因为 90% 的行都满足，回表不如全表扫。

#### （2）统计信息与索引下钻（index dive）

```sql
ANALYZE TABLE t;                     -- 更新统计信息
SHOW INDEX FROM t;                   -- 看 Cardinality
```

**`index dive`**：对 `WHERE col = ?`，优化器会**实际读取索引**估算行数（`eq_range_index_dive_limit` 默认 200，超过则用统计信息估算，可能不准）。

**直方图（MySQL 8.0）**：

```sql
ANALYZE TABLE t UPDATE HISTOGRAM ON status WITH 100 BUCKETS;
-- 解决"数据倾斜导致估算错误"的问题
```

#### （3）Index Merge

```sql
-- 两个单列索引，优化器可能合并
SELECT * FROM t WHERE a = 1 AND b = 2;
-- 执行计划：Using intersect(idx_a, idx_b)
```

**但通常不如联合索引**（`(a,b)`），因为 Index Merge 要回表两次 + 求交集。

#### （4）EXPLAIN 的进阶读法

| 字段 | 深水区读法 |
| --- | --- |
| `rows` | 是**预估**，可能错几个数量级；用 `EXPLAIN ANALYZE`（8.0.18+）看真实值 |
| `filtered` | 结合 `rows` 估算实际参与 join 的行数 |
| `Extra: Using index` | 覆盖索引；但注意 `key_len` 是否用满了联合索引 |
| `Extra: Using index condition` | ICP 生效 |
| `Extra: Using filesort` | 不一定慢（小结果集用内存排序）；看 `Sort_merge_passes` |
| `type: index` | 全索引扫描，通常比 `ALL` 好但仍是 O(n) |

**`EXPLAIN ANALYZE`**（8.0.18+）会真正执行并给出每步的实际行数/耗时——**这是排查"估算错误"的利器**。

### 4.7 复制与高可用 ⭐

| 方案 | 说明 | RPO/RTO | 适用 |
| --- | --- | --- | --- |
| 主从 + 哨兵（MHA/orchestrator） | 传统方案 | RPO 可能 > 0 | 中小规模 |
| **MGR（组复制）** | Paxos 变体，多数派提交 | RPO=0（单主模式） | 金融级 |
| 云 RDS 高可用 | 厂商封装 | 通常 RPO≈0 | 大多数业务 |
| **单元化** | 分片 + 多副本 | 取决于同步方式 | 超大规模 |

**MGR 的三种模式**：

- **单主模式**：一个主写，其余只读（推荐）。
- **多主模式**：任意节点写，**冲突检测严格**，性能差，易死锁。
- **流控**：`group_replication_flow_control_mode`，防止某个节点落后太多。

### 4.8 大表治理：不只是分库分表 ⭐⭐

**四个阶段**（按成本从低到高）：

```
① 索引优化 + SQL 优化（成本最低，收益最直接）
② 冷热分离（历史数据归档到归档表/对象存储/ClickHouse）
③ 分区表（按时间分区，DROP PARTITION 代替 DELETE）
④ 分库分表（最后手段，引入分布式事务与跨分片查询）
```

**为什么分库分表是最后手段？**

- 跨分片 join、跨分片分页、分布式事务、全局 ID、扩容（rehash）全都是成本。
- 分片键选错，后期迁移代价极高。

**"5000 万行"不是分表的标准**，真正的标准是：**单表容量是否导致 Buffer Pool 命中率下降、DDL 是否不可接受、索引维护成本是否过高**。

### 4.9 案例：一条慢 SQL 的完整优化

```
现象：订单列表接口 P99 从 80ms 涨到 1.2s，DB CPU 60%（不高）

排查：
① 慢查询日志 → 找到 SQL
   SELECT * FROM orders WHERE user_id = ? AND status = 3 ORDER BY create_time DESC LIMIT 20;
② EXPLAIN → type=ref, key=idx_user, rows=83000, Extra=Using filesort
③ 分析：
   - idx_user(user_id) 只能定位到用户，该用户有 8.3 万单
   - status 和 create_time 都在回表后过滤/排序 → 扫描 8.3 万行 + filesort
④ 优化：建联合索引 (user_id, status, create_time)
   - 等值 + 等值 + 排序 → 索引天然有序，消除 filesort
   - 但 SELECT * 仍需回表 → 结合覆盖索引或延迟关联
⑤ 进一步：改为 (user_id, status, create_time, id) 覆盖排序+分页键
⑥ 结果：rows 从 83000 降到 20，P99 从 1.2s 降到 35ms

复盘：
- 根因不是"DB 慢"，而是"索引设计没考虑查询模式"
- 预防：建立"慢 SQL 周报 + 索引 review"机制；新接口上线前必须 EXPLAIN
```

## 五、Redis 与缓存体系进阶

> 深水区的问题：
> 「Redis 主从切换时丢了 1 秒的数据，业务上怎么兜底？」「你们 10 万 QPS 的缓存，热 key 怎么发现和处理？」「本地缓存和 Redis 不一致怎么办？」

### 5.1 事件循环：单线程的真相 ⭐⭐

```
main thread:
  aeMain()
    └── while (!stop) {
            aeProcessEvents()
              ├── epoll_wait()          // IO 多路复用
              ├── 处理读事件 → 解析命令 → 执行命令 → 写回
              └── 处理时间事件（serverCron：过期删除、持久化检查、集群心跳）
        }
```

**能讲的深度**：

- **所有命令在一个循环里串行执行**，所以"单线程"意味着**任何 O(N) 命令都会阻塞所有人**（`KEYS`、`SMEMBERS`、`FLUSHALL`、大 key 的 `DEL`）。
- `serverCron` 也在这个循环里 → 过期删除、AOF 刷盘、集群心跳都可能造成延迟毛刺。
- **6.0 的 IO 线程**：只把 `read`/`write`/协议解析分发到 IO 线程，命令执行仍在主线程（因为命令执行不是瓶颈，**网络 syscall 才是**）。

```bash
io-threads 4                    # IO 线程数（建议 <= CPU 核数）
io-threads-do-reads yes         # 读也走 IO 线程
```

**追问**："为什么不用多线程执行命令？" → 需要加锁，且 Redis 的操作大多是内存级（几十 ns），锁开销会吃掉收益；更重要的是**语义简单**（所有命令原子），这是 Redis 的核心卖点。

### 5.2 数据结构：编码转换的阈值 ⭐⭐

| 类型 | 小对象编码 | 大对象编码 | 阈值 |
| --- | --- | --- | --- |
| String | int / embstr | raw | ≤ 44 字节用 embstr（一次分配） |
| Hash | **listpack** | hashtable | 元素 ≤ 128 且值 ≤ 64B |
| List | **listpack**（7.0+） | quicklist | 元素 ≤ 128 且值 ≤ 64B |
| Set | intset / listpack | hashtable | 全整数用 intset；≤128 且 ≤64B 用 listpack |
| ZSet | listpack | **skiplist + dict** | ≤128 且 ≤64B |

**追问**："为什么 ZSet 要同时用跳表和字典？"

- **字典**：`ZSCORE` 用，`O(1)` 查分数。
- **跳表**：`ZRANGE`/`ZRANK` 用，按分数有序遍历。
- 两者共享同一份 member 字符串（指针），内存开销可控。

**追问**："跳表的层数怎么定？" → 随机，`p=0.25`，最大 32 层；期望 `O(log N)`，实现比红黑树简单且**范围查询天然有序**。

**追问**："listpack 和 ziplist 的区别？" → ziplist 每个节点存 `prevlen`，**修改中间元素会连锁更新**（cascade update）；listpack 只存 `entry-len` 和 `backlen`，不依赖前驱，避免连锁更新。Redis 7.0 用 listpack 全面替代 ziplist。

### 5.3 持久化：fork 的真实代价 ⭐⭐⭐

```
RDB / AOF rewrite 都要 fork 子进程：
① fork 本身：复制页表，堆越大越慢（10G 堆约几十 ms）
② COW：父进程写一个页，就复制一份 → 写多时内存翻倍
③ 子进程写盘：磁盘 IO 与主线程竞争
```

**面试话术**："Redis 单实例建议不超过 10~16G，不是因为单线程处理不了，而是 **fork 和 COW 的代价随堆线性增长**；超大实例建议分片。"

**AOF 重写缓冲**：

```
重写期间的新写命令同时写入：
  - AOF 缓冲区（原有）
  - AOF 重写缓冲区（新增）
子进程完成后，把重写缓冲区追加到新 AOF 文件 → 原子替换
```

**追问**："AOF 重写期间 Redis 挂了会怎样？" → 旧 AOF 文件仍完整（重写是写新文件），重启用旧文件 + 少量丢失，**不会损坏**。

### 5.4 Cluster：故障转移与槽迁移 ⭐⭐

#### （1）Gossip 与故障判定

```
每个节点定期 PING 其他节点（cluster-node-timeout 默认 15s）
→ 主观下线（PFAIL）
→ 超过半数主节点认同 → 客观下线（FAIL）
→ 从节点发起选举（Raft-like，需要多数主节点投票）
→ 晋升为主，接管槽位
```

#### （2）MOVED vs ASK

| 重定向 | 含义 | 客户端动作 |
| --- | --- | --- |
| **MOVED** | 槽已永久迁移到别的节点 | **更新本地槽映射**并重试 |
| **ASK** | 槽正在迁移中，这个 key 暂时在目标节点 | **只本次重定向**，不更新映射 |

**追问**："槽迁移过程中客户端会怎样？" → 大量 `ASK` 重定向 → RT 升高；迁移要限速（`cluster-migration-barrier`、`redis-cli --cluster reshard` 的 pipeline）。

#### （3）脑裂与数据丢失

```
网络分区：主节点 A 与集群失联，但客户端还能写 A
→ 集群选举 B 为新主
→ A 恢复后被降级，A 上的写入丢失

缓解：
min-replicas-to-write 1        # 至少 1 个从节点同步才允许写
min-replicas-max-lag 10        # 从节点延迟不超过 10s
```

**这就是"Redis 丢数据"的经典场景**，面试时能讲出来是加分项。

### 5.5 多级缓存与热点治理 ⭐⭐⭐

#### （1）多级缓存的架构

```
请求 → 本地缓存（Caffeine，纳秒级，容量小）
      → Redis（微秒级，容量大）
      → DB
```

**收益**：本地缓存能挡掉 80%~95% 的热点请求，把 Redis 的压力降一个数量级。

**代价**：**一致性变难**。Redis 更新后，各机器的本地缓存怎么失效？

| 方案 | 说明 |
| --- | --- |
| **短 TTL** | 本地缓存 TTL 1~5s，接受短暂不一致（最常用） |
| **广播失效** | Redis Pub/Sub 或 MQ 广播，各机清本地缓存（有延迟、可能丢消息） |
| **版本号** | 缓存里带版本，读时比对（多一次查询，收益下降） |

#### （2）热 key 的发现与处理

**发现**：

```bash
redis-cli --hotkeys                    # 需要 maxmemory-policy 是 lfu*
# 或客户端埋点统计（更准确）
# 或 proxy 层统计（如 Twemproxy/Codis）
```

**处理**（从轻到重）：

| 手段 | 说明 |
| --- | --- |
| **本地缓存** | 最有效，直接挡在应用层 |
| **key 打散** | `hotkey:{1..N}` 多副本，随机读一个（写时要写 N 份） |
| **读写分离** | 热 key 走多个从节点 |
| **限流** | 保护 DB，牺牲部分请求 |

#### （3）大 key 的治理

```bash
redis-cli --bigkeys                     # 扫描各类型最大的 key
redis-cli MEMORY USAGE key              # 单个 key 的内存
```

**危害**：① 网络阻塞（一次传输几十 MB）；② 删除阻塞（`DEL` 同步释放，用 `UNLINK`）；③ 集群倾斜；④ 持久化慢。

**治理**：拆分（Hash 按字段分片）、压缩、设上限、用 `SCAN` 代替全量读。

### 5.6 缓存一致性：工程化的做法 ⭐⭐⭐

**先定义一致性级别**：

| 级别 | 允许的旧值窗口 | 实现 |
| --- | --- | --- |
| 强一致 | 0 | 不用缓存 / 缓存只读 + 版本校验 |
| 秒级最终一致 | < 1s | 先更 DB 再删缓存 + 短 TTL |
| 分钟级 | < 1min | Canal 订阅 binlog 异步删 |
| 天级 | — | 定时全量刷新 |

**Canal 方案（推荐）**：

```
MySQL binlog → Canal → MQ → 缓存失效服务 → 删 Redis + 广播本地缓存失效
优点：覆盖所有写路径（包括其他系统直接改库），与业务代码解耦
缺点：引入组件，有延迟（通常 < 1s）
```

**延迟双删的时间怎么估**：

```
延迟 > 一次读的耗时（读 DB + 回填缓存）+ 主从同步延迟
通常取 500ms ~ 1s；要按 P99 而不是平均值估
```

### 5.7 案例：一次缓存雪崩的复盘

```
现象：晚高峰 DB CPU 打满，大量慢查询，接口大面积超时
排查：
① Redis 监控：命中率从 98% 掉到 40%
② 看 key 过期分布：大量 key 在同一分钟过期（定时任务批量预热，TTL 统一设 1 小时）
③ 看流量：某个运营活动把 10 万条商品缓存同时刷新
④ 根因：批量预热 → TTL 对齐 → 同一时刻集体失效 → 请求全打到 DB

修复：
① 短期：紧急扩容 DB 从库 + 打开限流（Sentinel）
② 中期：TTL 加随机抖动（±20%）
③ 长期：
   - 多级缓存（本地缓存挡一层）
   - 预热任务分片执行（不要同一秒刷 10 万个 key）
   - 加 DB 熔断降级（返回兜底数据）
   - 加"缓存命中率"告警
```

## 六、Spring 源码与扩展点

> 深水区不问"什么是 IoC"，问的是：
> 「`refresh()` 里哪一步最容易被扩展？」「为什么 `@Async` 和 `@Transactional` 同时用会有问题？」「BeanFactoryPostProcessor 和 BeanPostProcessor 的区别？」

### 6.1 `refresh()` 的 12 步（能背前 8 步就够）⭐⭐

```java
// AbstractApplicationContext#refresh
① prepareRefresh()                    // 初始化上下文状态、环境变量
② obtainFreshBeanFactory()            // 创建/获取 BeanFactory，解析 XML 或注解
③ prepareBeanFactory()                // 添加后置处理器、注册可解析依赖
④ postProcessBeanFactory()            // 子类扩展（如 Web 容器）
⑤ invokeBeanFactoryPostProcessors()   // ★ 执行 BeanFactoryPostProcessor（改 BeanDefinition）
⑥ registerBeanPostProcessors()        // ★ 注册 BeanPostProcessor（改 Bean 实例）
⑦ initMessageSource()                 // 国际化
⑧ initApplicationEventMulticaster()   // 事件广播器
⑨ onRefresh()                         // 子类扩展（如 Tomcat 启动）
⑩ registerListeners()                 // 注册监听器
⑪ finishBeanFactoryInitialization()   // ★ 实例化所有非懒加载单例（Bean 生命周期在这里）
⑫ finishRefresh()                     // 发布 ContextRefreshedEvent
```

**追问**："哪一步最容易出问题？"
→ ⑤：`ConfigurationClassPostProcessor` 会解析 `@Configuration`/`@ComponentScan`/`@Import`，如果这里有循环依赖或类加载冲突，启动直接失败。
→ ⑪：所有单例在这里创建，**启动慢通常卡在这一步**（可以用 `-Ddebug` 看 Bean 创建日志）。

**追问**："`@Configuration` 类为什么要被 CGLIB 增强？"
→ 为了支持**方法间调用返回同一个 Bean**（`@Bean` 方法互相调用时，增强类会先查容器，避免创建多个实例）。

```java
@Configuration
public class Config {
    @Bean public A a() { return new A(b()); }   // 调用 b() 不会新建，而是从容器拿
    @Bean public B b() { return new B(); }
}
```

### 6.2 BeanDefinition 的注册时机 ⭐

```
@ComponentScan → ClassPathBeanDefinitionScanner
  → 扫描 classpath，生成 BeanDefinition
  → 注册到 BeanDefinitionRegistry（DefaultListableBeanFactory）

@Import → ConfigurationClassParser 解析
  ├─ ImportSelector        → 返回类名数组，批量注册（Spring Boot 自动装配就用它）
  ├─ ImportBeanDefinitionRegistrar → 手动注册（如 MyBatis 的 MapperScannerRegistrar）
  └─ 普通类                → 当配置类处理
```

**追问**："`BeanFactoryPostProcessor` 和 `BeanPostProcessor` 的区别？"

| | BeanFactoryPostProcessor | BeanPostProcessor |
| --- | --- | --- |
| 作用对象 | **BeanDefinition**（元数据） | **Bean 实例** |
| 时机 | 所有 Bean 实例化**之前** | 每个 Bean 初始化**前后** |
| 典型用途 | 改属性、注册新 BeanDefinition、占位符替换 | AOP 代理、`@Autowired` 注入、`@PostConstruct` |
| 例子 | `PropertySourcesPlaceholderConfigurer` | `AutowiredAnnotationBeanPostProcessor`、`AbstractAutoProxyCreator` |

### 6.3 三级缓存与 AOP 的时序（深水区追问）⭐⭐⭐

**核心矛盾**：AOP 代理是在 `postProcessAfterInitialization` 生成的，而循环依赖需要在**属性填充阶段**就暴露引用。

```
getSingleton(beanName, allowEarlyReference=true) 的逻辑：

① 一级 singletonObjects         → 完整 Bean
② 二级 earlySingletonObjects    → 早期引用（可能已代理）
③ 三级 singletonFactories       → ObjectFactory（延迟生成）
④ 都没有 → 从三级调用 getObject() → 放进二级，删除三级
```

**为什么必须是三级（关键论证）**：

- 如果只有二级，`getEarlyBeanReference` 必须在**放入二级时**就执行 → **所有 Bean 都会被提前代理**，即使没有循环依赖。
- 有了三级，`ObjectFactory` 只在**真的发生循环依赖**时才被调用 → 正常 Bean 不会提前代理，避免"提前代理 + 后续再代理"导致**两个不同代理对象**。

```java
// AbstractAutowireCapableBeanFactory#getEarlyBeanReference
protected Object getEarlyBeanReference(String beanName, RootBeanDefinition mbd, Object bean) {
    Object exposedObject = bean;
    for (BeanPostProcessor bp : getBeanPostProcessors()) {
        if (bp instanceof SmartInstantiationAwareBeanPostProcessor) {
            exposedObject = ((SmartInstantiationAwareBeanPostProcessor) bp)
                    .getEarlyBeanReference(beanName, mbd, bean);
        }
    }
    return exposedObject;
}
```

**追问**："`@Async` 为什么会破坏循环依赖？"
→ `@Async` 的代理由 `AsyncAnnotationBeanPostProcessor` 在**初始化后**创建，而 `getEarlyBeanReference` 阶段可能生成的是**普通代理或原对象**，最终注入的可能是未增强的引用。解决：`@Lazy`（注入代理，延迟解析）。

### 6.4 事务源码：从 `@Transactional` 到 `commit` ⭐⭐⭐

```
@Transactional
  → AbstractAutoProxyCreator 生成代理（TransactionInterceptor）
  → 调用方法时：
      TransactionInterceptor.invoke()
        → createTransactionIfNecessary()      // 根据传播行为决定新建/加入/挂起
        → invocation.proceed()                // 执行业务
        → commitTransactionAfterReturning()   // 或 rollbackOn
```

**传播行为的源码分支**（`AbstractPlatformTransactionManager#getTransaction`）：

| 传播行为 | 分支 |
| --- | --- |
| `REQUIRED` | 有事务 → 加入；无 → 新建 |
| `REQUIRES_NEW` | 挂起当前（`suspend`）→ 新建 |
| `NESTED` | 有事务 → `createSavepoint`；无 → 新建 |
| `MANDATORY` | 无事务 → 抛异常 |
| `NEVER` | 有事务 → 抛异常 |

**事务与线程绑定**：

```java
TransactionSynchronizationManager
  → ThreadLocal<Map<Object, Object>> resources   // 数据源 → ConnectionHolder
  → ThreadLocal<Set<TransactionSynchronization>> synchronizations
  → ThreadLocal<Boolean> actualTransactionActive
```

**这就是"多线程下事务失效"的根因**：子线程的 ThreadLocal 是空的。

**事务同步器（`TransactionSynchronization`）**：`beforeCommit` / `afterCommit` / `afterCompletion`。**发 MQ、发事件应该放 `afterCommit`**，否则事务回滚了消息却发出去了。

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override public void afterCommit() { mq.send(event); }   // 提交后才发
});
```

**追问**："`NESTED` 的回滚为什么能只回滚子事务？"
→ 用 **savepoint**（`rollbackToSavepoint`），同一个物理连接、同一个事务，只是回滚到保存点；而 `REQUIRES_NEW` 是**新连接、新事务**，两者完全独立。

### 6.7 案例：一个 `@Transactional` 失效的排查

```java
@Service
public class OrderService {
    @Transactional
    public void createOrder(Order o) {
        orderMapper.insert(o);
        this.sendCoupon(o.getUserId());      // ❌ 同类自调用，事务注解不生效？
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void sendCoupon(Long userId) { ... }
}
```

**问题**：`this.sendCoupon()` 走的是原对象，不经过代理，所以 `REQUIRES_NEW` 不生效，实际在同一个事务里。

**排查思路**：

```
① 确认是否自调用（看调用方是不是 this.）
② 打开事务日志：logging.level.org.springframework.transaction=DEBUG
③ 看连接是否同一个（TransactionSynchronizationManager.getCurrentTransactionName()）
④ 修复：注入自身 / AopContext.currentProxy() / 拆到另一个 Bean
```

**更隐蔽的坑**：`@Transactional` 加在 `private` 方法上、异常被 `catch`、`rollbackFor` 没配、类没被代理（`new` 出来的对象）。

## 七、分布式系统深水区

> 深水区的问题：
> 「你说最终一致，那中间不一致的窗口里，用户看到什么？」「Raft 的 commit index 怎么推进？」「异地多活，两个机房同时写同一个用户，怎么解决冲突？」

### 7.1 先把"一致性"说清楚 ⭐⭐⭐

面试时最容易含糊的就是"一致"。要能区分这几个层次：

| 模型 | 含义 | 例子 |
| --- | --- | --- |
| **线性一致（强一致）** | 所有操作像在单机上按时间顺序执行 | etcd、ZooKeeper、单机 MySQL |
| **顺序一致** | 所有线程看到相同的操作顺序，但不要求实时 | 较少单独使用 |
| **因果一致** | 有因果关系的操作保序 | 评论与回复 |
| **最终一致** | 停止写入后，最终所有副本一致 | 大多数互联网业务 |
| **读己之写** | 自己能读到自己刚写的 | 发完朋友圈立刻能看到 |
| **单调读** | 不会读到比之前更旧的数据 | 避免"刷新后内容倒退" |

**面试话术**："我们说的『最终一致』必须补两个限定：**收敛时间**（通常 < 1s）和**不一致期间的表现**（用户看到旧值还是报错）。这两点决定了要不要加兜底。"

### 7.2 Raft：工程化的共识 ⭐⭐

**三个子问题**：

```
① 领导者选举
   - 节点状态：Follower / Candidate / Leader
   - 选举超时（随机 150~300ms）→ 变 Candidate，term+1，拉票
   - 得到多数票 → Leader，定期发心跳维持权威

② 日志复制
   - 客户端请求 → Leader 追加日志（未提交）
   - 并行复制到 Follower
   - 多数派持久化后 → Leader 提交（commit index 推进）
   - 通知 Follower 提交 → 应用到状态机

③ 安全性
   - 选举限制：只有拥有最新日志的节点才能当选
   - 提交规则：只能提交当前 term 的日志（通过提交当前 term 的日志间接提交之前的）
```

**追问**："commit index 怎么推进？"
→ Leader 维护 `matchIndex[]`，取**多数派的 matchIndex 中位数**作为新的 commit index；并且**只能提交当前 term 的日志**（否则可能出现已提交日志被覆盖）。

**追问**："为什么选举超时要随机？"
→ 避免所有 Follower 同时变成 Candidate 导致选票瓜分、反复选举（活锁）。

**etcd 的工程实现**：

- **Lease**：租约，key 绑定 TTL，用于服务注册（心跳续约）。
- **Watch**：长连接监听 key 变化，用于配置中心。
- **MVCC**：每个 key 有 revision，支持历史版本读取。
- **线性一致读**：`ReadIndex` 或 `Lease Read`（避免每次读都走 Raft 日志）。

### 7.3 分布式事务的落地（不只是背方案）⭐⭐⭐

| 方案 | 一致性 | 性能 | 业务侵入 | 真实代价 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强 | 差 | 低 | 同步阻塞、协调者单点、连接占用长 |
| TCC | 强 | 中 | **高** | 要写三个方法 + 处理空回滚/悬挂/幂等 |
| SAGA | 最终 | 好 | 中 | 要写补偿，且补偿不一定可逆 |
| 本地消息表 | 最终 | 好 | 中 | 要建表 + 定时任务 + 重试 |
| 事务消息 | 最终 | 好 | 低 | 依赖 MQ 支持 + 回查实现 |
| 最大努力通知 | 最终 | 最好 | 低 | 只能保证"尽力"，需要人工兜底 |

**TCC 三个坑的正确解法**：

```java
// ① 空回滚：Try 没执行，Cancel 来了
//   → 记录事务状态表，Cancel 时若没 Try 记录，插入一条"空回滚"标记并返回成功
// ② 幂等：Confirm/Cancel 重复调用
//   → 状态机：只有 INIT 才能 Confirm，只有 INIT/CONFIRMED 才能 Cancel
// ③ 悬挂：Cancel 先到，Try 后到
//   → Try 执行前检查是否已有 Cancel 记录，有则拒绝
```

**"本地消息表"的完整流程**：

```
① 本地事务：业务表 insert + 消息表 insert（同一事务，保证原子）
② 定时任务扫描消息表 status=待发送
③ 发送 MQ，成功则 status=已发送
④ 消费者处理，幂等（唯一索引）
⑤ 失败重试（指数退避），超过阈值转人工
⑥ 对账：定时比对消息表与业务表，补偿丢失的
```

**面试话术**："我优先用本地消息表，因为**不依赖 MQ 的高级特性**，换 MQ 也不用改代码；缺点是有一张表和一个定时任务，但这对排查反而友好——出问题能直接查表。"

### 7.4 分布式锁的正确性边界 ⭐⭐

**核心问题：锁的持有者可能"已经失去锁但自己不知道"**。

```
场景：
① 客户端 A 拿到锁（TTL 30s）
② A 发生长时间 GC（40s）
③ 锁过期，客户端 B 拿到锁
④ A 恢复，以为还持有锁，继续写 → 数据错乱
```

**三种解法**：

| 方案 | 说明 | 局限 |
| --- | --- | --- |
| **看门狗续期** | 后台线程定期续期 | GC 停顿时续期线程也停，仍可能丢锁 |
| **Fencing Token** | 每次加锁返回递增 token，写存储时带上，存储拒绝旧 token | **需要存储侧支持**（如 ZooKeeper 的 zxid、数据库的版本号） |
| **租约 + 短临界区** | 锁内只做极短操作，配合业务幂等 | 治标 |

**Fencing Token 才是严格正确的方案**：

```
A 拿锁 → token=33 → 写存储（带 token=33）
B 拿锁 → token=34 → 写存储（带 token=34）
A 恢复 → 写存储（带 token=33）→ 存储发现 33 < 34，拒绝
```

**RedLock 为什么有争议**：它依赖"多个独立 Redis 的时钟"，而 GC 停顿、时钟漂移都会破坏假设。**如果业务需要严格互斥，用 ZooKeeper/etcd + fencing token，而不是 RedLock。**

### 7.5 时钟：分布式系统的隐形杀手 ⭐

| 时钟 | 说明 | 问题 |
| --- | --- | --- |
| 物理时钟（NTP） | 有漂移，可能回拨 | 不能用于判断事件先后 |
| 逻辑时钟（Lamport） | 单调递增，只保证因果 | 无法判断并发 |
| **混合逻辑时钟（HLC）** | 物理 + 逻辑，接近真实时间且保因果 | 实现复杂（CockroachDB 用） |
| **TrueTime**（Spanner） | GPS + 原子钟，给出误差区间 | 需要硬件，成本极高 |

**实践结论**：

- 不要用 `System.currentTimeMillis()` 做**跨机器的先后判断**（时钟回拨、精度问题）。
- 用**版本号/序列号**代替时间戳做排序。
- 雪花算法依赖时钟，必须处理回拨。

### 7.6 单元化与异地多活 ⭐⭐

**三种形态**：

| 形态 | 说明 | RTO | 成本 |
| --- | --- | --- | --- |
| 同城双活 | 同城两个机房，共享存储或同步复制 | 分钟级 | 中 |
| 两地三中心 | 同城双活 + 异地灾备（异步） | 小时级 | 高 |
| **异地多活** | 多地都能写，流量按用户路由 | 秒级 | 极高 |

**异地多活的四个核心问题**：

```
① 流量路由：按用户 ID / 地理位置分片，保证同一用户落同一单元
② 数据同步：DTS / binlog 订阅，单向或双向
③ 冲突解决：双向同步必然冲突
   - 按业务规避（如"用户数据只在一个单元写"）
   - LWW（最后写入获胜，依赖时钟，不可靠）
   - CRDT（可合并数据结构，适合计数器/集合）
   - 业务层合并（如购物车取并集）
④ 切流与回滚：DNS / 网关 / 客户端路由；要有"一键切回"
```

**面试加分**："异地多活的难点不是技术，而是**业务建模**——你必须证明『同一份数据永远不会在两地同时被写』，否则一致性无解。所以我们按 user_id 做单元化，把跨单元的写操作（如转账）收敛到单一单元。"

### 7.7 服务治理的工程细节 ⭐⭐

#### （1）超时与重试的正确姿势

```
超时：必须逐层递减（网关 3s > 服务 2s > RPC 1s > DB 500ms）
      否则内层还在跑，外层已经超时 → 资源浪费 + 雪崩

重试：
  - 只重试"幂等 + 可重试"的错误（网络超时、5xx），不重试 4xx
  - 指数退避 + 抖动（避免重试风暴）
  - 限制重试次数（2~3 次）和总超时
  - 重试要放在"最外层"或"幂等层"，不要在每一层都重试（会指数放大）
```

**"重试放大"的经典事故**：3 层服务各重试 2 次 → 下游实际收到 `3^3 = 27` 倍请求。

#### （2）负载均衡算法

| 算法 | 特点 | 问题 |
| --- | --- | --- |
| 轮询 | 简单 | 不考虑负载差异 |
| 加权轮询 | 按权重 | 权重静态 |
| 随机 | 简单 | 可能倾斜 |
| **最少连接** | 动态感知 | 需要状态同步 |
| **一致性哈希** | 节点变动影响小 | 需要虚拟节点解决倾斜 |
| P2C（Power of Two Choices） | 随机选两个，取较闲的 | **工业界最优解之一**（Envoy/gRPC 默认） |

#### （3）优雅上下线

```
上线：注册中心注册 → 健康检查通过 → 才开始接流量
下线：先从注册中心摘除 → 等待在途请求完成（30s）→ 再停进程
```

**面试话术**："很多『发布时短暂 5xx』的问题，根因都是**没有优雅下线**——进程收到 SIGTERM 直接退出，此时还有请求在处理。"

### 7.8 案例：分布式事务在"下单扣库存"的落地

```
业务：下单要同时 ①创建订单 ②扣减库存 ③扣减优惠券，跨 3 个服务

方案演进：
① 最初：同步调用三个服务，失败就回滚 → 超时导致数据不一致
② 改进：TCC（Try 预占库存/优惠券，Confirm 确认，Cancel 释放）
   问题：三个服务都要改造，且要处理空回滚/悬挂
③ 最终：本地消息表 + 最终一致
   - 下单服务：订单表 + 本地消息表（同一事务）
   - 消息驱动库存/优惠券服务扣减
   - 每个消费者幂等（唯一索引 order_id）
   - 定时对账：订单存在但库存未扣 → 补偿
   - 用户体验：下单成功立即可见，库存扣减延迟 < 1s

为什么放弃 TCC：
  团队规模小，维护三套接口成本高；业务能接受 1s 的最终一致
```

## 八、稳定性与可观测性（社招真正的分水岭）

> 3 年经验和 5 年经验最大的差距，不在算法，而在**"你能不能对系统的稳定性负责"**。
> 面试官会问：「你们的 SLO 是多少？」「出过最大的故障是什么？你怎么止损的？」「大促怎么保障？」

### 8.1 SLO / SLI / 错误预算 ⭐⭐⭐

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| **SLI**（指标） | 你实际测量的东西 | 请求成功率、P99 延迟 |
| **SLO**（目标） | 你承诺的内部目标 | "99.9% 的请求在 200ms 内成功" |
| **SLA**（协议） | 对客户的合同承诺 | "月度可用性 < 99.9% 赔付" |
| **错误预算** | `1 - SLO` | 99.9% → 每月 43 分钟不可用 |

**错误预算的用法**（这是"高级感"的来源）：

```
预算充足 → 可以激进发布、做实验
预算耗尽 → 冻结变更，优先修稳定性
```

**怎么定 SLO**：

```
① 选对 SLI：成功率用「成功请求 / 总请求」，延迟用 P99（不要用平均）
② 排除合理错误：4xx 用户错误不算服务端故障
③ 按业务重要性分级：核心链路 99.95%，非核心 99.9%
④ 定期 review：SLO 太松没意义，太紧会逼团队做无意义的优化
```

**追问**："P99 还是 P999？"
→ 看用户规模。1 万 QPS 下，P999 每分钟有 600 个慢请求，必须关注；100 QPS 下 P999 样本太少，不稳定。**大促用 P999，日常用 P99。**

### 8.2 容量规划：算清楚，别拍脑袋 ⭐⭐⭐

**四步法**：

```
① 业务指标 → 技术指标
   日订单 100 万 → 峰值 QPS = 100万 / 86400 × 峰值系数(5~10) ≈ 60~120
   大促再 × 5 → 600 QPS

② 单机容量 → 机器数
   压测单机 300 QPS（水位 70%）→ 需要 3 台（含冗余）
   + 1 台冗余 → 4 台

③ 各层分别算
   - 接入层（Nginx）：连接数、带宽
   - 应用层：线程数、CPU、内存
   - 缓存：内存容量、QPS
   - DB：连接数、IOPS、存储
   - MQ：分区数、堆积容量

④ 留冗余
   同城双活：每机房能扛 100% 流量
   单机房：N+2 冗余
```

**关键指标：水位**。CPU 长期 > 70%、内存 > 80%、连接池 > 80%、磁盘 > 80% 都应该扩容或优化。

**弹性伸缩的坑**：

- 冷启动慢（JVM 预热、连接池建立）→ 扩容跟不上突增。
- 缩容太激进 → 正在处理的请求被中断。
- **扩容不等于解决**：如果是 DB 瓶颈，加应用机器只会把 DB 打死。

### 8.3 混沌工程：主动制造故障 ⭐⭐

**核心思想**：与其等故障发生，不如**在可控范围内主动注入故障**，验证系统的容错能力。

**成熟度模型**：

```
L1：手动演练（运维拔网线、kill 进程）
L2：工具化（ChaosBlade / Chaos Mesh）
L3：常态化（每周自动演练 + 结果回归）
L4：生产环境演练（小流量、可回滚）
```

**常见实验**：

| 实验 | 验证什么 |
| --- | --- |
| 杀死实例 | 负载均衡、健康检查、优雅下线 |
| 网络延迟/丢包 | 超时设置、重试策略 |
| 下游返回错误 | 熔断降级是否生效 |
| CPU/内存打满 | 限流、降级、告警 |
| 时钟偏移 | 依赖时间的逻辑（雪花 ID、token 过期） |
| 依赖中间件不可用 | 缓存击穿、MQ 堆积的兜底 |

**面试话术**："我们做过一次『Redis 集群整体不可用』的演练，发现代码里没有任何降级逻辑，直接打穿到 DB。后来补了『本地缓存兜底 + DB 限流』，这也是我们后来加多级缓存的直接原因。"

### 8.4 故障处理：止损优先，定位其次 ⭐⭐⭐

**故障处理的铁律**：

```
① 先止损，后定位（用户还在受影响时，不要埋头查日志）
   止损手段：回滚、降级、限流、切流、扩容、重启

② 保留现场（限流/重启前先 dump：线程栈、堆、GC 日志、关键日志）

③ 信息同步（每 5 分钟同步一次进展，避免多人重复排查）

④ 恢复后 24~72 小时内复盘（趁记忆新鲜）
```

**复盘的正确写法（5 Whys）**：

```
现象：某接口 5xx 率 20%，持续 8 分钟

Why1 为什么 5xx？→ 线程池满了，任务被拒绝
Why2 为什么线程池满？→ 下游 RPC 变慢（RT 从 50ms 涨到 3s）
Why3 为什么下游变慢？→ 下游的 DB 出现慢查询
Why4 为什么有慢查询？→ 新上线的功能用了未加索引的查询
Why5 为什么没被发现？→ 上线前没有做 SQL review / 没有在预发压测

改进项（每条都要有 owner + deadline）：
- 技术：加索引、加超时、线程池隔离、DB 慢查询告警
- 流程：SQL 上线必须 EXPLAIN、预发压测、灰度发布
- 监控：增加下游 RT 和线程池队列的告警
```

**反面复盘**："因为某某同学写了个 bug" —— 这不是根因，是**流程缺失**。

### 8.5 可观测性：Metrics / Tracing / Logs ⭐⭐⭐

| 支柱 | 用途 | 技术选型 | 关键问题 |
| --- | --- | --- | --- |
| **Metrics** | 聚合指标、告警 | Prometheus + Grafana | 高基数（cardinality）爆炸 |
| **Tracing** | 单请求链路 | Jaeger / SkyWalking / OTel | 采样率、上下文透传 |
| **Logs** | 详细现场 | ELK / Loki | 成本、检索性能 |

#### （1）高基数是可观测性的头号杀手

```
❌ 不要给指标打高基数标签：
   http_requests_total{user_id="12345", url="/order/123"}

✅ 正确做法：
   http_requests_total{method="GET", uri="/order/{id}", status="200"}
   （URI 模板化，user_id 放日志/trace，不放 metrics）
```

**面试话术**："一次 metrics 爆炸把 Prometheus 打挂了，根因是有人给指标加了 `userId` 标签，导致每个用户一个时间序列。"

#### （2）OpenTelemetry 与上下文透传

```
traceparent: 00-<trace_id>-<span_id>-<flags>     // W3C 标准
```

**透传的三条链路**：HTTP header、RPC（Dubbo/Feign）、MQ（消息属性）。

**常见坑**：异步线程池丢上下文、MQ 消费端新建 trace、跨语言格式不一致。

#### （3）告警设计

```
好的告警：
  - 基于 SLO（错误预算消耗速率）而不是单点阈值
  - 有 runbook（收到告警知道第一步做什么）
  - 分级别（P0 电话、P1 群消息、P2 邮件）
  - 有抑制（避免一个根因触发 100 条告警）

坏的告警：
  - CPU > 80% 就打电话（半夜被叫醒，发现没事）
  - 没有聚合，告警风暴
```

### 8.6 变更管理：绝大多数故障来自变更 ⭐⭐

> 业界统计：**70%+ 的线上故障由变更引起**（发布、配置、DDL、扩缩容）。

**四道防线**：

| 防线 | 做法 |
| --- | --- |
| **灰度** | 按机器/用户/流量比例逐步放量（1% → 10% → 50% → 100%） |
| **可回滚** | 每次变更都能一键回滚（镜像、配置、DB 变更要单独设计） |
| **开关** | 新功能默认关闭，通过配置中心灰度开启（Feature Flag） |
| **观察** | 灰度期间对比核心指标（错误率、RT、业务指标） |

**数据库变更的特殊性**：**不可回滚**（删了列就没了）。所以 DDL 要"向前兼容"：

```
① 加列（可空，有默认值）→ 发版双写 → 回填数据 → 切读 → 删旧列
② 绝不 rename/drop 列（先停用，观察一个版本再删）
```

### 8.7 高可用设计的六个手段 ⭐⭐

| 手段 | 说明 | 典型实现 |
| --- | --- | --- |
| **冗余** | 多实例、多机房 | 集群、双活 |
| **隔离** | 故障不扩散 | 线程池隔离、机房隔离、租户隔离 |
| **限流** | 保护自己 | 令牌桶、Sentinel |
| **熔断** | 快速失败 | Sentinel、Resilience4j |
| **降级** | 有损服务 | 兜底数据、关闭非核心 |
| **超时** | 防止资源悬挂 | 逐层递减 |

**"隔离"是最高级的**：面试时能说出"我们把核心链路和非核心链路的线程池/连接池/集群都做了隔离"，比说"我加了限流"高一个层次。

```
四、值守（大促当天）
  - 作战室 + 值班表 + 每 30 分钟播报
```

## 九、中间件内核：MQ / ES / OLAP / Flink

> 深水区不问"怎么用"，问的是"它为什么这么设计"和"出问题时内部在干什么"。

### 9.1 Kafka：为什么能这么快 ⭐⭐

#### （1）存储结构

```
topic-partition/
├── 00000000000000000000.log        # 消息追加写
├── 00000000000000000000.index      # 稀疏索引（offset -> 物理位置）
├── 00000000000000000000.timeindex  # 时间索引
└── leader-epoch-checkpoint
```

- **分段（segment）**：默认 1GB 一个，便于删除旧数据（直接删文件）。
- **稀疏索引**：不是每条消息都建索引，而是每 4KB 建一条 → 索引小，能全放内存。
- **查找**：二分索引 → 找到最近的位置 → 顺序扫。

#### （2）零拷贝

```
传统 read+write：磁盘 → 内核缓冲区 → 用户缓冲区 → Socket 缓冲区 → 网卡（4 次拷贝，2 次上下文切换）
sendfile：      磁盘 → 内核缓冲区 ────────────────→ 网卡（2 次拷贝，0 次用户态）
```

**追问**："零拷贝为什么能用在 Kafka？" → 因为 Kafka 的消息**不需要在用户态修改**（直接转发给消费者），所以能 `sendfile`。

#### （3）ISR 与 HW

| 概念 | 含义 |
| --- | --- |
| **LEO** | Log End Offset，每个副本的最后一条消息位置 |
| **HW** | High Watermark，ISR 中最小的 LEO，消费者只能读到 HW 之前的 |
| **ISR** | 与 Leader 保持同步的副本集合 |
| **LSO** | Last Stable Offset（事务） |

**追问**："为什么消费者只能读到 HW？" → 为了保证**一致性**：HW 之前的消息已经在多数副本上，即使 Leader 挂了也不会丢；HW 之后的消息可能随 Leader 消失。

#### （4）Rebalance 的代价

```
触发：消费者加入/离开、分区数变化、订阅变化
过程：所有消费者停止消费 → 重新分配 → 恢复消费（STW）
```

**优化**：

- **Cooperative Sticky（2.4+）**：增量 rebalance，只迁移必要的分区。
- **静态成员（`group.instance.id`）**：重启不触发 rebalance。
- **合理设置 `session.timeout.ms` 和 `heartbeat.interval.ms`**：避免误判。

#### （5）Kafka 的"不丢"配置清单

```properties
# 生产端
acks=all
retries=Integer.MAX_VALUE
enable.idempotence=true          # 幂等生产者（PID + 序列号）
max.in.flight.requests.per.connection=5   # 幂等开启后可 >1

# Broker
replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false

# 消费端
enable.auto.commit=false         # 手动提交
```

### 9.2 RocketMQ：存储模型与事务消息 ⭐⭐

#### （1）存储结构（和 Kafka 完全不同）

```
CommitLog：所有 topic 的消息顺序写在一起（真正的顺序写）
ConsumeQueue：每个 topic-queue 一个索引文件，存 (offset, size, tagHash) 共 20B
IndexFile：按 key 哈希索引（用于按 msgId/key 查询）
```

**为什么这样设计？**

- Kafka 按 partition 一个文件 → **topic 多时磁盘随机写严重**（几百个文件并发写）。
- RocketMQ 所有消息写**同一个 CommitLog** → 顺序写性能极好，适合**Topic 数量多**的场景（电商）。
- 代价：读消息要先读 ConsumeQueue 再回 CommitLog（**读放大**），所以有 page cache 预热机制。

#### （2）事务消息回查

```
① 发半消息（对消费者不可见）
② 执行本地事务
③ Commit/Rollback
④ 如果 ③ 丢失 → Broker 定时回查（默认 60s 后，最多 15 次）
⑤ 生产者实现 checkLocalTransaction，查 DB 状态返回
```

**追问**："回查会不会有并发问题？" → 会，所以 `checkLocalTransaction` 必须**幂等且只读**，且要考虑"本地事务还在执行中"的中间态（返回 UNKNOW，让 Broker 稍后再查）。

### 9.3 ES：倒排索引与深分页 ⭐⭐

#### （1）写入链路

```
写入 → translog（保证不丢）+ 内存 buffer
     → refresh（默认 1s）：生成新 segment，写入文件系统缓存（可被搜索）
     → flush：fsync 到磁盘，清空 translog
     → merge：合并小 segment，物理删除标记删除的文档
```

**追问**："为什么 ES 是『近实时』？" → 因为 `refresh` 默认 1 秒，新文档要等 refresh 后才能被搜索到（可以手动 `?refresh=true`，但性能差）。

**追问**："`refresh` 和 `flush` 的区别？" → refresh 是**可搜索**（Lucene 段），flush 是**持久化**（fsync）。

#### （2）深分页

```json
// ❌ from + size 深分页：每个分片都要取 from+size 条，协调节点再排序
{ "from": 10000, "size": 10 }     // 默认 max_result_window=10000，超过报错

// ✅ search_after（游标，需要唯一的排序字段）
{ "size": 10, "sort": [{"timestamp": "desc"}, {"_id": "asc"}],
  "search_after": [1714567890000, "abc123"] }

// ✅ scroll（快照，适合导出，不适合实时翻页）
// ✅ Point in Time (PIT) + search_after（官方推荐）
```

#### （3）分片设计

```
分片数 = 数据总量 / 单分片建议容量（30~50GB）
分片过多 → 元数据开销、查询 fan-out 大
分片过少 → 无法水平扩展
副本数：至少 1（读扩展 + 高可用）
```

**面试话术**："ES 的分片数在索引创建时就固定了，后期只能 reindex，所以要在设计时按『3 年数据量』来算。"

### 9.4 ClickHouse / OLAP ⭐

| 特性 | 说明 |
| --- | --- |
| **列式存储** | 只读需要的列，压缩率高（同列数据类型一致） |
| **向量化执行** | 批量处理（SIMD），比逐行快一个数量级 |
| **MergeTree** | 按主键排序存储，后台合并 |
| **稀疏索引** | 每 8192 行一个索引标记 |
| **物化视图** | 预聚合，查询加速 |
| **不适合** | 高频点更新、事务、复杂 join |

**追问**："为什么 ClickHouse 快？" → 列存（IO 少）+ 高压缩（CPU cache 友好）+ 向量化 + 稀疏索引 + 并行。

**选型对比**：

| 场景 | 选型 |
| --- | --- |
| 实时明细查询、日志分析 | ClickHouse |
| 高并发点查、全文检索 | ES |
| 联邦查询、标准 SQL、更新 | Doris / StarRocks |
| 流式聚合 | Flink + ClickHouse/Doris |

### 9.5 Flink：状态与 Exactly-Once ⭐⭐

#### （1）Checkpoint 机制

```
① JobManager 定期插入 barrier 到数据流
② barrier 随数据流动，算子收到 barrier 就做快照（本地/远端）
③ 所有算子完成后，JobManager 确认 checkpoint 完成
④ 故障时从最近完成的 checkpoint 恢复
```

#### （2）Exactly-Once 的实现（两阶段提交）

```
① checkpoint 开始时，sink 预提交（写临时文件/事务未提交）
② checkpoint 完成时，sink 正式提交
③ 故障恢复时，回滚未提交的事务
```

**追问**："端到端 exactly-once 需要什么？" → source 可重放（Kafka offset）+ Flink checkpoint + sink 支持事务（Kafka 事务 / 幂等写）。

#### （3）状态后端

| 后端 | 适用 |
| --- | --- |
| HashMapStateBackend（内存） | 小状态、高性能 |
| **EmbeddedRocksDBStateBackend** | 大状态（TB 级），本地磁盘 + 增量 checkpoint |

2. HW 和 LEO 的区别？为什么消费者只能读到 HW？

### 10.0 高阶答题框架（比基础版多两步）

```
① 澄清与量化（3 min）

② 量级估算（2 min）

③ 架构草图（5 min）
   接入 → 服务 → 存储 → 依赖；先跑通主流程
④ 关键决策（15 min）  ★ 分水岭
   每个决策给「选项 → 判据 → 结论 → 代价」
⑤ 失败模式（5 min）  ★ 分水岭
```

### 10.1 设计一个 10 万 QPS 的 API 网关

**关键决策**：

| 决策点 | 选项 | 结论与理由 |
| --- | --- | --- |
| 网络模型 | Tomcat / Netty / WebFlux | **Netty**：每连接内存小，C10 万连接可行；Tomcat 线程模型撑不住 |
| 路由 | 静态配置 / 注册中心拉取 / 控制面推送 | **控制面推送 + 本地缓存**：网关不能依赖注册中心实时可用 |
| 限流 | 单机令牌桶 / Redis 集群限流 | **单机令牌桶为主**（无网络开销），集群配额按实例预分配 |
| 鉴权 | 每请求查 Redis / JWT 本地校验 | **JWT 本地校验 + 吊销名单**（短 TTL） |
| 协议转换 | HTTP → Dubbo/gRPC | 连接池复用，注意**超时逐层递减** |
| 动态配置 | 配置中心 + 长轮询 | 变更秒级生效，且要有**本地快照**（配置中心挂了也能启动） |

**失败模式**：

| 故障 | 检测 | 兜底 |
| --- | --- | --- |
| 控制面挂了 | 心跳 | 本地快照继续服务（**降级为静态配置**） |
| 某后端全挂 | 健康检查 | 熔断 + 返回兜底 |
| 突发流量 | QPS 突增 | 分层限流（IP/用户/接口/全局） |
| 慢请求占满连接 | RT 监控 | 超时 + 隔离 |

**加分点**："网关是**流量入口**，所以它的第一原则是『**永不成为单点**』：多实例 + 多可用区 + 客户端本地负载均衡（如 Nginx + VIP + DNS 兜底）。"

### 10.2 设计一个分布式任务调度平台

**核心问题**：

```
① 触发：定时（cron）、延时、依赖触发
② 选主：谁来调度？（避免多实例重复触发）
③ 分片：一个大任务怎么拆到多台机器并行
④ 失败：重试、告警、人工干预
⑤ 幂等：重复触发不能重复执行
⑥ 可观测：执行日志、耗时、成功率
```

**架构**：

```
调度中心（选主：ZK/etcd/DB 乐观锁）
  → 时间轮 / Quartz 触发
  → 任务分片（按分片数取模）
  → 下发到 Executor（RPC）
  → Executor 执行 → 回调上报 → 记录日志
```

**关键决策**：

- **选主**：ZK 临时节点 / etcd lease / DB 行锁（简单但性能差）。
- **分片**：`shardIndex = hash(id) % shardTotal`，支持**动态扩缩容**（rebalance）。
- **失败重试**：指数退避 + 最大次数 + 死信队列。
- **幂等**：`业务键 + 执行日期` 唯一索引。

**"重复执行"的经典坑**：调度中心以为 Executor 挂了（网络抖动），重新派发，但 Executor 其实还在跑 → **必须用执行状态表 + 心跳**，而不是超时就重派。

### 10.3 设计一个配置中心

**核心矛盾**：**推（实时）vs 拉（简单可靠）**。

```
方案 A：纯推（服务端主动推）→ 需要维护长连接，服务端不知道谁在线
方案 B：纯拉（客户端轮询）→ 实时性差，浪费请求
方案 C：长轮询（推拉结合）→ 客户端发起请求，服务端 hold 30s，有变更立即返回
       → 这就是 Nacos / Apollo 的做法
```

**关键设计**：

| 问题 | 方案 |
| --- | --- |
| 一致性 | 配置存储用 DB + 本地文件缓存 + 内存缓存 |
| 实时性 | 长轮询（30s）+ MD5 比对 |
| 灰度 | 按 IP/机器/标签下发不同版本 |
| 回滚 | 保留历史版本，一键回滚 |
| 客户端容灾 | 本地快照（配置中心挂了也能启动） |
| 安全性 | 加密敏感配置、权限控制、操作审计 |

**追问**："配置推送丢了怎么办？" → 客户端定时**全量比对**（如每 5 分钟），兜底最终一致。

### 10.4 设计一个 IM 系统

**核心难点**：

```
① 长连接（百万级）：Netty + 多协议（TCP/WebSocket）
② 消息可靠：不丢、不重、有序
③ 多端同步：同一账号多设备，消息状态一致
④ 离线消息：用户离线时的消息暂存
⑤ 在线状态：心跳、上下线通知
⑥ 群消息扩散：大群（万人）的写放大
```

**架构**：

```
客户端 → 接入层（长连接网关，无状态）→ 路由层（uid → 网关地址，Redis）
                                    → 消息服务（seq 生成、存储）
                                    → 推送服务（在线直推 / 离线存储）
```

**关键决策**：

| 问题 | 方案 |
| --- | --- |
| 消息 ID | 会话内自增 seq（保证有序）+ 全局 msgId（去重） |
| 可靠性 | 客户端 ACK + 服务端重推 + 拉取补偿（**推拉结合**） |
| 有序 | 同一会话串行写（按会话 ID 路由到同一实例） |
| 多端同步 | 每个端维护自己的已读位点（read offset） |
| 大群扩散 | 写扩散 → 读扩散（拉取时聚合），或按活跃度分级 |

**追问**："消息重复怎么办？" → 客户端按 `msgId` 去重；服务端用会话 seq 保证幂等。

### 10.5 设计一个支付清结算系统

**核心概念**：

```
支付（收钱）→ 账务（记账）→ 清分（分给谁）→ 结算（打款）→ 对账
```

**关键设计**：

| 要点 | 说明 |
| --- | --- |
| **账务模型** | 复式记账（借贷必相等），每个账户有余额和流水 |
| **状态机** | 待支付 → 支付中 → 成功/失败/退款，**只能单向流转** |
| **幂等** | 商户订单号唯一索引；回调重复直接返回成功 |
| **对账** | T+1 与渠道逐笔比对，差错进差错池 |
| **一致性** | 账务与支付**最终一致** + 定时对账；核心扣款用本地事务 |
| **安全** | 金额用**分/整数**，绝不用 double；签名验签；防重放（nonce + 时间戳） |

**追问**："支付成功但账务失败怎么办？" → 本地消息表 + 重试 + 对账补偿；用户侧显示"处理中"，不要显示成功。

### 10.6 设计一个订单系统

**核心问题**：分库分表 + 状态机 + 幂等 + 查询维度多。

| 问题 | 方案 |
| --- | --- |
| 分片键 | **user_id**（C 端查询都带用户） |
| 商家维度查询 | 异构索引表（商家 ID → 订单 ID），或同步到 ES |
| 订单号 | 雪花 ID（趋势递增，利于 B+ 树） |
| 状态机 | 待支付→已支付→已发货→已完成；**每次流转带版本号**（乐观锁） |
| 超时取消 | 延时消息 + 状态校验（见基础版 10.5） |
| 幂等 | `order_id` 唯一索引 + 状态机校验 |
| 冷热分离 | 3 个月前订单归档到历史库 / OLAP |

**追问**："用户要查 3 年前的订单怎么办？" → 归档库查询（异步/降级提示），不要为了少数查询把热库撑大。

### 10.7 架构设计的通用加分句

面试时把这些话嵌进去，立刻显得有经验：

- "这里我加一个**本地缓存**，因为依赖不能是强依赖。"
- "这个调用必须**幂等**，因为上游会重试。"
- "超时要**逐层递减**，否则内层还在跑外层已经放弃了。"
- "我会给它配一个**熔断 + 兜底**，宁可降级也不能雪崩。"
- "这个方案在**数据量涨 10 倍**时会先崩在 X，所以 V2 我会做 Y。"
- "这里有个**取舍**：强一致会牺牲可用性，我选最终一致因为业务能接受 1s 的延迟。"

## 十一、AI 应用后端（2025-2026 新增考点）

> 现在很多 JD 会写"有 LLM 应用落地经验优先"。面试官不会考你训模型，但会考：
> **「你的 RAG 怎么做的？召回率多少？」「token 成本怎么控？」「大模型返回慢，你的接口怎么设计？」**

### 11.1 LLM 应用的四种形态

| 形态 | 说明 | 后端关注点 |
| --- | --- | --- |
| **Prompt 应用** | 拼 prompt 调 API | 超时、重试、成本、内容安全 |
| **RAG** | 检索增强生成 | 切分、向量化、召回、重排、上下文长度 |
| **Agent** | 工具调用 + 多步推理 | 编排、状态机、失败重试、可观测 |
| **微调/自部署** | 私有模型 | 推理服务、GPU 调度、显存、吞吐 |

### 11.2 RAG 全链路（能讲清每一步的取舍）⭐⭐

```
文档 → 解析（PDF/HTML/表格）→ 切分（chunk）→ 向量化（embedding）
    → 向量库（Milvus/Qdrant/pgvector）
用户问题 → 向量化 → 检索（topK）→ 重排（rerank）→ 拼上下文 → LLM 生成
```

| 环节 | 关键决策 | 常见问题 |
| --- | --- | --- |
| **解析** | PDF 表格/图片怎么处理 | 解析丢结构 → 召回不准 |
| **切分** | 固定长度 / 按语义 / 按标题层级 | 切太碎丢上下文，切太大噪声多（常用 300~800 token + overlap） |
| **向量化** | 模型选择（bge/m3e/text-embedding-3） | 中英文、领域词效果差异大 |
| **检索** | 纯向量 / 关键词（BM25）/ **混合检索** | 纯向量对专有名词、编号不敏感 → 必须混合 |
| **重排** | Cross-encoder rerank | 提升精度但增加延迟 |
| **生成** | 上下文塞多少、引用标注 | 上下文过长 → 贵且"迷失在中间" |

**面试话术**："我们做了混合检索（向量 + BM25）+ rerank，召回率从 62% 提到 85%；切分上按标题层级而不是固定长度，因为合同类文档的条款是天然语义单元。"

**追问**："怎么评估 RAG 效果？"

```
离线：构建评测集（问题 + 标准答案 + 证据片段）
      指标：召回率@K、MRR、答案准确率、忠实度（有无编造）
在线：用户点赞/点踩、追问率、人工抽检
```

### 11.3 Agent 编排（后端视角）

```
ReAct 循环：Thought → Action（调工具）→ Observation → 继续
工程问题：
① 工具调用的幂等与超时
② 多步执行的**状态持久化**（断了能恢复）
③ 最大步数限制（防死循环）
④ 成本控制（每步都要 token）
⑤ 可观测（每一步的输入输出都要记录，否则没法排障）
```

**架构建议**：不要把 Agent 逻辑写死在业务代码里，用**状态机/工作流引擎**编排（如自研 DAG 或 Temporal），这样才能重试、回放、调试。

### 11.4 工程化难点（这些才是后端面试的考点）

| 难点 | 方案 |
| --- | --- |
| **LLM 响应慢（几秒~几十秒）** | **流式输出（SSE）** + 前端增量渲染；接口超时要单独设置（不能沿用 3s） |
| **流式下的错误处理** | 首包前可返回错误码；首包后只能发 `event: error` 让前端提示 |
| **token 成本** | 提示词缓存（同前缀复用）、模型分级（简单问题用小模型）、限制上下文长度、语义缓存 |
| **限流** | 按 **RPM（请求数）和 TPM（token 数）** 双维度；租户级配额 |
| **计费** | 按 token 计费要**精确统计**（输入/输出分别计），并处理流式中断 |
| **幻觉** | 强制引用来源、置信度低时拒答、结构化输出（JSON schema） |
| **Prompt 注入** | 用户输入与系统提示隔离、工具权限最小化、输出过滤 |
| **幂等/重试** | LLM 调用**不幂等**（同样的输入可能不同输出），重试要记录并选首次结果 |
| **降级** | 模型服务挂了 → 降级到规则/模板回复，或排队 |

**SSE 实现要点**：

```java
@GetMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@RequestParam String q) {
    SseEmitter emitter = new SseEmitter(0L);          // 0 = 不超时（自己控制）
    executor.execute(() -> {
        try {
            for (String chunk : llmClient.stream(q)) {
                emitter.send(SseEmitter.event().data(chunk));
            }
            emitter.complete();
        } catch (Exception e) {
            emitter.completeWithError(e);
        }
    });
    return emitter;
}
```

**坑**：Nginx 要关缓冲（`proxy_buffering off`）、网关超时要放大、连接要心跳。

### 11.5 怎么讲"我落地了 AI"（项目包装）

## 十二、技术判断力与影响力

> 5 年经验往上，面试官开始考察"**你能不能做技术决策**"，而不是"你能不能实现"。

### 12.1 技术选型的正确姿势（决策矩阵）

不要只说"A 更好"，要给**判据 + 权重 + 结论**：

| 维度 | 权重 | 方案 A（Redis） | 方案 B（本地缓存） |
| --- | --- | --- | --- |
| 性能 | 30% | 3（网络开销） | 5（纳秒级） |
| 一致性 | 25% | 4 | 1（多机不一致） |
| 容量 | 15% | 5 | 2 |
| 运维成本 | 20% | 3 | 5 |
| 团队熟悉度 | 10% | 4 | 4 |
| **加权** | | **3.55** | **3.35** |

**面试话术**："我列了五个维度、给了权重，两个方案得分很接近，所以我的结论是**组合使用**——本地缓存挡热点，Redis 做兜底。"

**比矩阵更重要的是"知道什么时候不该选"**：

- 数据量小（< 10 万行）→ 别上 ES，MySQL 够用。
- QPS 低（< 100）→ 别上 MQ，同步调用更简单。
- 团队没人懂 → 再好的技术也是负债。

### 12.2 方案评审怎么讲（面试中的"技术汇报"）

```
① 背景与目标（1 分钟）     现状、痛点、量化目标
② 方案对比（3 分钟）       2~3 个方案，每个给优缺点
③ 推荐方案（2 分钟）       选哪个、为什么、代价是什么
④ 详细设计（3 分钟）       核心流程、数据结构、接口
⑤ 风险与兜底（2 分钟）     失败模式、降级、回滚
⑥ 落地计划（1 分钟）       里程碑、人力、灰度策略
```

**面试官最看重 ② 和 ⑤**——因为这两块能证明你想过别人的方案和失败场景。

### 12.3 跨团队推动（行为面高频）

**STAR 模板**：

```
S：我们和推荐团队对接，接口联调拖了 3 周，双方都说是对方的问题
T：我需要在 2 周内上线
A：
  ① 先把接口契约固化（OpenAPI 文档 + mock），消除"口头约定"
  ② 建了一个双方都在的群，每天同步进度和阻塞
  ③ 发现根因是双方对"字段含义"理解不一致 → 拉了一次对齐会
  ④ 推动加了一个契约测试（CI 里跑），防止以后再漂移
R：提前 3 天上线，后续 3 个月零接口故障
```

**关键**：不要讲"我很努力地沟通"，要讲**你建立了什么机制**。

### 12.4 带人（4~5 年会被问）

| 场景 | 做法 |
| --- | --- |

### 15.4 四种高效的训练方法

#### 方法 1：三档答案练习（最有效）

```
任选一个知识点，限时 5 分钟，分别写出：
  ① 及格版（50 字）
  ② 良好版（150 字）
  ③ 优秀版（400 字 + 数字 + 代价）
写完对比，找出"优秀版缺的那部分"——那就是你的缺口。
```

#### 方法 2：造轮子（验证理解）

| 造什么 | 验证什么 |
| --- | --- |
| 简易 RPC 框架 | 动态代理、序列化、连接池、负载均衡 |
| 简易 MQ | 存储、顺序写、消费位点、重试 |
| 简易 IoC 容器 | 反射、注解、依赖注入、循环依赖 |
| 简易网关 | Netty、路由、限流 |
| 限流器（4 种算法） | 算法理解 |

> **不求可用，只求跑通**。造过一次，源码就看得懂了。

#### 方法 3：故障注入（最接近实战）

```
在测试环境：
① 用 ChaosBlade 注入延迟/异常/CPU 满
② 观察系统反应，记录"哪个保护机制没生效"
③ 补上，再演练一次
```

#### 方法 4：模拟面试（必须做）

```
找同事/朋友，按真实节奏：
  - 45 分钟，白板/共享屏幕
  - 随机抽 3 道 ★★★
  - 全程录音，回放听自己哪里啰嗦、哪里含糊
```

**没有模拟面试的备考，等于没备考。** 你会发现自己"以为会了"的东西，一开口就散。
