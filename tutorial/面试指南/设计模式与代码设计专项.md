> ① 你能不能识别代码里的坏味道；② 你能不能用合适的手段重构；③ 你知不知道**什么时候不该用**。

## 零、面试到底怎么考

### 0.1 四种问法

| 问法 | 例子 | 你要答什么 |
| --- | --- | --- |
| **识别** | "Spring 里用了哪些设计模式？" | 模式 + 具体类 + 为什么 |
| **设计** | "支付渠道有 10 个，怎么设计？" | 策略/工厂 + 扩展点 |
| **重构** | "这段 if-else 怎么优化？" | 坏味道 + 模式 + 代价 |
| **取舍** | "什么时候不该用设计模式？" | 过度设计的危害 |

### 0.2 一个反直觉的结论

```
面试官更欣赏"知道什么时候不用"的人，
而不是"能把所有代码都套上模式"的人。
```

**最常见的失分**：把简单逻辑套上三层抽象，说"这样符合开闭原则"——面试官会追问"这个抽象现在有几个实现？未来真的会扩展吗？"

## 一、六大设计原则

### 1.1 SOLID + 两个补充

| 原则 | 一句话 | 反例 |
| --- | --- | --- |
| **S** 单一职责 | 一个类只做一件事 | `OrderService` 里既下单又发短信又算报表 |
| **O** 开闭原则 | 对扩展开放、对修改关闭 | 每加一个支付渠道就改 `if-else` |
| **L** 里氏替换 | 子类能替换父类且行为不变 | 子类抛父类没有的异常 |
| **I** 接口隔离 | 接口要小而专 | 一个 `UserService` 塞 30 个方法 |
| **D** 依赖倒置 | 依赖抽象不依赖实现 | Service 直接 `new MySQLDao()` |
| 迪米特法则 | 少知道别人的内部 | `a.getB().getC().doX()` |
| 合成复用 | 优先组合而非继承 | 为了复用代码继承一个不相干的类 |

### 1.2 面试怎么用这些原则

**不要背定义，要能举例 + 说代价**：

```
"开闭原则听起来很好，但抽象是有成本的。
 如果这个 if-else 只有两个分支、且半年没变过，
 我倾向先不抽；等第三个分支出现、或者变化频繁时再抽。"
```

**这段话比背十条原则更加分。**

## 二、12 个高频模式

> 每个模式给：意图 → 结构 → 代码 → 框架应用 → 追问 → 易错。

### 2.1 单例（Singleton）

**意图**：全局唯一实例。

```java
public class Config {
    private Config() {}
    private static class Holder { static final Config INSTANCE = new Config(); }
    public static Config getInstance() { return Holder.INSTANCE; }
}
```

**框架应用**：Spring 单例 Bean（容器管理，不是模式意义上的单例）、`Runtime.getRuntime()`。

**追问**：

- 怎么防反射/序列化破坏？→ 枚举最安全；序列化加 `readResolve`。
- Spring 的单例和 GoF 单例的区别？→ Spring 是"容器内唯一"，类本身可以 new。

**易错**：DCL 忘写 `volatile`。

### 2.2 工厂方法（Factory Method）

**意图**：把"创建哪个实现"的决定交给子类/工厂。

```java
public interface PayChannel { void pay(BigDecimal amount); }

public class AlipayChannel implements PayChannel { ... }
public class WechatChannel implements PayChannel { ... }

public class PayChannelFactory {
    private static final Map<String, PayChannel> MAP = new HashMap<>();
    static {
        MAP.put("alipay", new AlipayChannel());
        MAP.put("wechat", new WechatChannel());
    }
    public static PayChannel get(String type) {
        PayChannel channel = MAP.get(type);
        if (channel == null) throw new IllegalArgumentException("不支持的支付渠道: " + type);
        return channel;
    }
}
```

**框架应用**：`BeanFactory`、`Calendar.getInstance()`、`DriverManager.getConnection()`。

**追问**：

- 简单工厂 vs 工厂方法 vs 抽象工厂？→ 一个产品/一类产品/产品族。
- 新增渠道要改哪里？→ 加类 + 注册（可以用 SPI 消除注册代码）。

### 2.3 抽象工厂（Abstract Factory）

**意图**：创建**一组**相关产品（产品族）。

```java
interface Button { void render(); }
interface Checkbox { void render(); }

interface UIFactory {
    Button createButton();
    Checkbox createCheckbox();
}

class DarkFactory implements UIFactory { ... }
class LightFactory implements UIFactory { ... }
```

**追问**：什么时候用？→ 需要保证一组产品风格一致（主题、数据库方言、云厂商 SDK）。

**易错**：只有一个产品时用抽象工厂 → 过度设计。

### 2.4 建造者（Builder）

**意图**：分步构造复杂对象，避免超长构造器。

```java
public class Order {
    private final String userId;
    private final List<Item> items;
    private final String couponId;

    private Order(Builder b) { ... }

    public static class Builder {
        private String userId;
        private final List<Item> items = new ArrayList<>();
        private String couponId;

        public Builder userId(String v) { this.userId = v; return this; }
        public Builder addItem(Item v) { this.items.add(v); return this; }
        public Builder coupon(String v) { this.couponId = v; return this; }
        public Order build() {
            if (userId == null) throw new IllegalStateException("userId 必填");
            return new Order(this);
        }
    }
}
```

**框架应用**：`StringBuilder`、Lombok `@Builder`、`Request.Builder`（OkHttp）。

**追问**：和工厂的区别？→ 工厂关注"创建什么"，建造者关注"怎么一步步创建"。

### 2.5 代理（Proxy）

**意图**：在不改目标对象的前提下增强行为（访问控制、延迟加载、日志、事务）。

```java
// JDK 动态代理
public class LogHandler implements InvocationHandler {
    private final Object target;
    public LogHandler(Object target) { this.target = target; }

    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        long start = System.nanoTime();
        try {
            return method.invoke(target, args);
        } finally {
            System.out.println(method.getName() + " cost " + (System.nanoTime() - start) + "ns");
        }
    }
}

UserService proxy = (UserService) Proxy.newProxyInstance(
        target.getClass().getClassLoader(),
        target.getClass().getInterfaces(),
        new LogHandler(target));
```

**框架应用**：Spring AOP、MyBatis Mapper、RPC 客户端、`@Transactional`。

**追问**：

- JDK 代理和 CGLIB 的区别？→ 接口 vs 子类；CGLIB 不能代理 final。
- 自调用为什么失效？→ 不走代理。
- 静态代理的缺点？→ 每个类都要写一个代理类。

### 2.6 装饰器（Decorator）

**意图**：在不改变接口的前提下，动态叠加功能。

```java
public interface Notifier { void send(String msg); }

public class SmsNotifier implements Notifier { ... }

public abstract class NotifierDecorator implements Notifier {
    protected final Notifier delegate;
    protected NotifierDecorator(Notifier delegate) { this.delegate = delegate; }
}

public class RetryDecorator extends NotifierDecorator {
    public void send(String msg) {
        for (int i = 0; i < 3; i++) {
            try { delegate.send(msg); return; } catch (Exception ignored) {}
        }
    }
}
```

**框架应用**：`java.io`（`BufferedInputStream(new FileInputStream())`）、Servlet Filter、Spring `HttpMessageConverter`。

**追问**：和代理的区别？→ 装饰器**接口不变、层层包装**；代理**控制访问**，通常一个目标一个代理。

### 2.7 适配器（Adapter）

**意图**：把不兼容的接口转成目标接口。

```java
public class LegacyPayAdapter implements PayChannel {
    private final LegacyPayService legacy;
    public void pay(BigDecimal amount) {
        legacy.doPay(amount.multiply(new BigDecimal("100")).longValue());  // 元 → 分
    }
}
```

**框架应用**：`InputStreamReader`（字节→字符）、SLF4J（日志门面适配多种实现）、`HandlerAdapter`（SpringMVC）。

**追问**：和装饰器的区别？→ 适配器**改变接口**，装饰器**不改变接口**。

### 2.8 策略（Strategy）

**意图**：把可互换的算法/规则独立出来，运行时选择。

```java
public interface DiscountStrategy {
    BigDecimal apply(BigDecimal price);
}

public class FullReduction implements DiscountStrategy { ... }
public class Percentage implements DiscountStrategy { ... }

public class PriceCalculator {
    private final DiscountStrategy strategy;
    public PriceCalculator(DiscountStrategy strategy) { this.strategy = strategy; }
    public BigDecimal calc(BigDecimal price) { return strategy.apply(price); }
}
```

**框架应用**：`Comparator`、Spring 的 `Resource` 策略、`LoadBalancer` 算法、限流算法。

**追问**：

- 策略和 if-else 的区别？→ 策略把分支变成对象，便于测试和扩展；**但只有 2 个分支时不值得**。
- 策略怎么选？→ 工厂 + 注册表 / Spring 注入 `Map<String, Strategy>`。

### 2.9 责任链（Chain of Responsibility）

**意图**：把请求沿着处理链传递，每个节点决定处理或放行。

```java
public abstract class Handler {
    protected Handler next;
    public Handler setNext(Handler next) { this.next = next; return next; }
    public abstract void handle(Request req);

    protected void next(Request req) {
        if (next != null) next.handle(req);
    }
}

public class AuthHandler extends Handler {
    public void handle(Request req) {
        if (!req.isLogin()) throw new UnauthorizedException();
        next(req);
    }
}
```

**框架应用**：Servlet Filter、Spring Interceptor、Netty Pipeline、Sentinel Slot Chain、MyBatis 插件。

**追问**：

- 和装饰器的区别？→ 责任链是**多个处理器中的一个处理**，装饰器是**全部叠加**。
- 链太长怎么办？→ 控制顺序、短路、异步。

### 2.10 观察者（Observer）

**意图**：一对多依赖，状态变化时通知所有观察者。

```java
public class OrderService {
    private final List<OrderListener> listeners = new CopyOnWriteArrayList<>();

    public void addListener(OrderListener l) { listeners.add(l); }

    public void create(Order order) {
        // ... 落库
        for (OrderListener l : listeners) {
            try { l.onCreated(order); } catch (Exception e) { log.error("listener error", e); }
        }
    }
}
```

**框架应用**：Spring `ApplicationEvent` + `@EventListener`、JDK `EventListener`、Guava `EventBus`。

**追问**：同步还是异步？→ 默认同步（影响主流程），建议异步 + 失败隔离；重要事件用 MQ（可靠）。

### 2.11 模板方法（Template Method）

**意图**：父类定义骨架，子类实现可变步骤。

```java
public abstract class ImportTask {
    public final void run(String file) {
        List<Row> rows = parse(file);       // 可变
        validate(rows);                     // 可变
        save(rows);                         // 可变
        afterRun();                         // 可选钩子
    }
    protected abstract List<Row> parse(String file);
    protected abstract void validate(List<Row> rows);
    protected abstract void save(List<Row> rows);
    protected void afterRun() {}
}
```

**框架应用**：`AbstractList`、`JdbcTemplate`、`HttpServlet#service`、Spring `AbstractApplicationContext#refresh`。

**追问**：为什么用 `final` 修饰骨架方法？→ 防止子类改变流程。

### 2.12 门面（Facade）

**意图**：为复杂子系统提供一个简单入口。

```java
public class OrderFacade {
    public Result create(CreateOrderCmd cmd) {
        userService.check(cmd.userId());
        inventoryService.lock(cmd.skuId(), cmd.qty());
        Order order = orderService.create(cmd);
        couponService.use(cmd.couponId());
        return Result.ok(order);
    }
}
```

**框架应用**：SLF4J（日志门面）、Service 层、BFF。

**追问**：和微服务网关的区别？→ 门面是**代码级**封装；网关是**进程/网络级**。

### 2.13 其他模式速查

| 模式 | 一句话 | 框架例子 |
| --- | --- | --- |
| 组合 | 树形结构统一处理 | `CompositeByteBuf`、菜单树 |
| 享元 | 共享细粒度对象 | 线程池、连接池、`Integer` 缓存 |
| 桥接 | 抽象与实现分离 | JDBC 驱动、日志实现 |
| 状态 | 状态决定行为 | 订单状态机 |
| 命令 | 把请求封装成对象 | `Runnable`、撤销操作 |
| 中介者 | 集中协调 | 消息总线、注册中心 |
| 解释器 | 表达式求值 | SpEL、规则引擎 |
| 迭代器 | 统一遍历 | `Iterator`、`ResultSet` |

## 四、重构实战：消灭 if-else

### 4.1 场景：支付渠道

```java
// ❌ 坏味道：每加一个渠道就改这里
public void pay(String type, BigDecimal amount) {
    if ("alipay".equals(type)) { ... }
    else if ("wechat".equals(type)) { ... }
    else if ("unionpay".equals(type)) { ... }
    else throw new IllegalArgumentException();
}
```

**问题**：

- 违反开闭原则
- 方法过长、难测试
- 新增渠道要改核心类

### 4.2 重构：策略 + 工厂 + 注册

```java
public interface PayChannel {
    String type();
    PayResult pay(PayCommand cmd);
}

@Component
public class AlipayChannel implements PayChannel {
    public String type() { return "alipay"; }
    public PayResult pay(PayCommand cmd) { ... }
}

@Component
public class PayChannelRegistry {
    private final Map<String, PayChannel> map;

    public PayChannelRegistry(List<PayChannel> channels) {
        this.map = channels.stream().collect(Collectors.toMap(PayChannel::type, c -> c));
    }

    public PayChannel get(String type) {
        PayChannel c = map.get(type);
        if (c == null) throw new BizException("不支持的渠道: " + type);
        return c;
    }
}
```

**收益**：新增渠道 = 新增一个类，核心代码不动。

### 4.3 什么时候**不**重构

| 情况 | 建议 |
| --- | --- |
| 只有 2 个分支，且长期不变 | 保留 if-else，更直观 |
| 分支逻辑差异极小 | 用参数化，不要为每种情况建类 |
| 团队不熟悉模式 | 简单优先，可读性 > "设计感" |
| 性能敏感的热点路径 | 虚方法调用/Map 查找有开销，需实测 |

**面试话术**："我会先看变化频率和分支数量。如果半年没变过，我不会为了'开闭原则'提前抽象——**抽象也是有维护成本的**。"

### 4.4 审批流：责任链 vs 状态机

```
简单审批（固定 3 级）→ 责任链
复杂审批（可配置、可回退、并行）→ 状态机/工作流引擎
```

**追问**："责任链怎么处理'某级跳过'或'加签'？" → 责任链适合固定链路；复杂规则用状态机/规则引擎。

### 4.5 消息处理：策略 + 工厂

```java
public interface MessageHandler {
    String type();
    void handle(Message msg);
}

@Component
public class MessageDispatcher {
    private final Map<String, MessageHandler> handlers;
    // 构造注入所有 handler
    public void dispatch(Message msg) {
        MessageHandler h = handlers.get(msg.getType());
        if (h == null) { log.warn("unknown type"); return; }
        h.handle(msg);
    }
}
```

## 五、反模式与过度设计

### 5.1 六个常见反模式

| 反模式 | 表现 | 后果 |
| --- | --- | --- |
| **过度抽象** | 一个实现配三个接口 | 阅读成本高、改动牵一发动全身 |
| **上帝类** | 一个 Service 几千行 | 不可维护、冲突多 |
| **贫血模型** | 只有 getter/setter，逻辑全在 Service | 领域知识散落 |
| **隐式依赖** | 方法里 `new` 依赖 | 无法测试、无法替换 |
| **异常吞掉** | `catch (Exception e) {}` | 问题被掩盖 |
| **复制粘贴** | 相似代码到处是 | 改一处漏三处 |

### 5.2 过度设计的三个信号

```
① 抽象只有一个实现，且没有明确的第二个实现计划
② 为了"以后可能扩展"增加了大量配置和间接层
③ 新人需要读 5 个类才能看懂一个简单流程
```

### 5.3 简单优先的原则

```
YAGNI：不需要的功能不要提前做
KISS：能简单就不复杂
DRY：重复三次以上再抽象（Rule of Three）
```

**面试话术**："我更看重**演进式设计**：先写简单能跑的版本，等变化真的出现，再重构出模式。**模式是重构的结果，不是设计的起点。**"

## 六、DDD 基础与落地边界

### 6.1 核心概念

| 概念 | 说明 | 例子 |
| --- | --- | --- |
| **限界上下文** | 业务边界，一个上下文一个模型 | 订单上下文、库存上下文 |
| **实体** | 有唯一标识、生命周期 | `Order`（orderId） |
| **值对象** | 无标识、不可变 | `Money`、`Address` |
| **聚合** | 一致性边界，通过聚合根访问 | 订单 + 订单项 |
| **聚合根** | 外部只能引用根 | `Order` |
| **领域服务** | 跨实体的业务逻辑 | 价格计算、库存扣减 |
| **仓储** | 聚合的持久化接口 | `OrderRepository` |
| **领域事件** | 领域内发生的事 | `OrderPaid` |
| **防腐层** | 隔离外部模型 | 对接第三方支付 |

### 6.2 聚合设计的四条规则

```
① 聚合内强一致，聚合间最终一致
② 通过聚合根访问内部实体
③ 聚合尽量小（一个事务只改一个聚合）
④ 聚合间用 ID 引用，不用对象引用
```

### 6.3 DDD 什么时候值得用

| 场景 | 建议 |
| --- | --- |
| 业务复杂、规则多、长期演进 | 值得 |
| CRUD 为主、变化少 | 不值得（贫血模型够了） |
| 团队没有 DDD 经验 | 先做模块化，别硬套 |
| 需要跨团队统一语言 | 值得（限界上下文） |

**面试话术**："DDD 的价值在**边界**和**语言**，不在那些名词。我们实际落地时只用了聚合和限界上下文，没上完整的事件溯源。"

### 6.4 CQRS 与事件溯源（了解）

```
CQRS：写模型（命令）与读模型（查询）分离
事件溯源：存事件而不是存状态，通过重放得到状态
```

**注意**：复杂度高，**只在确有收益时用**（审计、时序分析、复杂读模型）。

| 模式 | 一句话 |
| --- | --- |

| 工厂 | 把创建逻辑收起来 |
| 建造者 | 分步构造复杂对象 |
| 代理 | 不改目标、增强访问 |
| 装饰器 | 接口不变、层层叠加 |
| 适配器 | 转换接口 |
| 策略 | 把分支变成对象 |
| 责任链 | 请求沿链传递 |
| 观察者 | 状态变化通知多方 |
| 模板方法 | 父类定骨架、子类填步骤 |
| 门面 | 复杂系统一个入口 |

## 写在最后

设计模式的面试，本质在考**判断力**：

1. **能识别坏味道**（重复、过长、强耦合）。
2. **能选对手段**（模式、参数化、拆分、还是不动）。
3. **能说清代价**（抽象成本、间接层、调试难度）。
4. **知道什么时候停**（简单优先，演进式设计）。

如果只记一句话：**"模式是重构出来的，不是设计出来的。"**
